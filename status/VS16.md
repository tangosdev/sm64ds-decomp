### THE ACTUAL WALL, stated precisely

`mPlayerNo` is two bits **on the unpack from the spawn-flag word only**, not in
storage. `src/_ZN6Player13InitResourcesEv.cpp:72`:

```c
a = *(unsigned int*)(c + 8);
*(u8*)(c + 0x6d8) = (a >> 6) & 3;
```

The destination is a **whole byte**. The flag word is what is two bits wide:
bits 0..2 character, 3..5 f1, 6..7 player number, 8..11 sublevel
(`hal/level_boot.cpp:4356` packs exactly that). So slot 5 cannot be *expressed
in the spawn flags*, but it can be *stored* and *indexed by* perfectly well.

The one consequence inside `InitResources` is at `:105`:

```c
Lac:
    if (*(u8*)(c + 0x6d8) == data_0209f250) { ...local player binding... }
```

In VS mode (`data_0209f2d8 == 1`) the rest of the function's `mPlayerNo` uses
are skipped -- the `data_02092128` rewrite block at `:79-91` is inside
`if (t == 0)` and `t` is `(data_0209f2d8 == 1)`. So the identity problem reduces
to two things and nothing else:

1. make the ROM's own local-player test at `:105` reach the right answer for
   each spawning slot, and
2. repair `*(u8*)(actor + 0x6d8)` to the true slot after `Actor::Spawn` returns.

Both are doable **entirely in the port's spawn caller**, with no `src/` edit.
That is the phase 2 design and it is written up below the table.

### THE PREMISE HOLDS -- proceeding to phase 2

Nothing in this sweep overturns the plan. Three things make it *cheaper* than
the map predicted (the scores are already wide, the results-screen OOB does not
bind, and most ROM loops are already generic), and one thing makes it
*sharper*: the identity problem is not "the ROM cannot store slot 5", it is
"the ROM's spawn-flag word cannot carry slot 5 and one ROM branch reads the
truncated value". That has a clean fix in the port's own spawn caller.

### The phase 2 design, in one place

1. **Wire.** `kCommsMaxPlayers` 4 -> 16; `Packet.live` `unsigned char` ->
   `uint16_t`; `blocks[16][0x20]`; `kPacketBytes` 0x90 -> 0x210. Bump the
   packet `version` byte and **refuse** a mismatched version rather than
   half-parse it. Old client meets wide session: refused with a named reason.
   The default path must produce byte-identical behaviour at 2P/4P.
2. **Identity.** Around each `Actor::Spawn` for slot `i`, the port sets
   `data_0209f250` so the ROM's own `:105` test reaches the right answer, then
   writes the true slot into `*(u8*)(actor + 0x6d8)` after the call. No `src/`
   edit. Every ROM reader that indexes by the identity byte then sees the true
   slot, and the host arrays are wide enough to be indexed.
3. **Hosted widths.** Table C, mechanically, with the two guarded bands
   (`vsstar`, `ready`) and their guards moved together.
4. **Spawns.** Replace the `i < 4` stand-in with deterministic ring placement
   around each real entrance record; document per arena.
5. **Names + colours.** The coordinated 16-field move at the new contract
   version, across `star_flow.cpp` / `fs_mods.cpp` / `server.py` `VERB_FIELDS`
   / the launcher, in one commit set.
6. **HUD.** Correct counts for N; display defaults to the simplest honest
   thing; capture 2-3 layout options for the owner and never judge them here.

### 1. THE WIRE: two of them, and which one a session speaks is not a branch

`port/hal/comms_loopback.cpp`. The design in one paragraph: a session of four
or fewer speaks **wire version 2 at 0x90 bytes**, byte for byte what this port
has always sent; five or more speaks **version 3 at 0x214 bytes**, sixteen
blocks and a 32-bit live mask. The header is identical in both -- magic,
version and type at the same three offsets -- so a receiver classifies before
it assumes a layout, and the **length is still the frame check**, it just names
two frames now.

- `Packet` grew `live_wide` at the TAIL (offset 0x210), not inside the header.
  `have` is not spare: an ACCEPT carries `0x80000000|slot` and the input delay
  in bits 8..15, and stealing bits from it would have put the slot assignment
  and the live mask in one word -- which is how a broadcast accept collapses
  two players onto one seat.
- Four `static_assert`s pin the v2 shape: `kPacketNarrowBytes == 0x90`,
  `offsetof(blocks) == 0x10`, `offsetof(live) == 0x07`,
  `offsetof(live_wide) == 0x210`. A padding change anywhere before `blocks`
  breaks the build rather than every shipped peer.
- **One normalisation point.** `dispatch` fills `live_wide` from `live` for a
  narrow datagram, so no reader downstream knows which wire it came off.
- **The refusal is sent, not only logged.** A narrow build cannot receive a
  532-byte datagram at all (its read buffer is 256 bytes; on Windows that is
  WSAEMSGSIZE and a lost packet, not a truncation), so it would sit in silence
  for the ROM's whole twenty-second wait. A wide parent answering a narrow JOIN
  therefore replies with a **narrow-length packet carrying version 3**, and the
  shipped build's own version check -- unchanged, already loud -- prints the
  whole diagnosis in the log of the person holding the stale build. It is
  deliberately not a new packet type: a new type is something an older build
  has to already know about.
- Buffers widened with it: the socket read buffer and the latency-induction
  ring both hold `kRawMaxBytes` now. The ring mattered more than it looks --
  induced latency is the rig the desync proofs run under, so an aux-sized ring
  would have dropped every wide packet **inside its own test**.
- The width comes from `SM64DS_VS_PLAYERS`, read once at install. Absent or
  4 or below is narrow, which is every existing deployment and every existing
  proof.

### 2. IDENTITY: the wall was narrower than the map said

`mPlayerNo` is two bits **only where the spawn flags pack it**. The destination
(`Player + 0x6d8`) is a whole byte and every ROM reader indexes off that byte.
So the mod is two moves in the port's own spawn caller and **no `src/` edit**:

- `port_load1` now clamps the ROM's entrance loop to **four**, always
  (`hal/level_boot.cpp`). Not because a level runs out of records -- because at
  `i == 4` the ROM's `(i << 6)` lands on bit 8, where the sublevel lives, so a
  fifth pass would spawn a player into the wrong sublevel and number him zero.
  That clamp IS the boundary between the cartridge's protocol and the mod.
- `port_vs_spawn_extra_players` seats 4..15. It packs the flag word's slot
  field as `((i-1) % 3) + 1`, which is **exactly `i` for i in 1..3** (so 2P, 3P
  and 4P pack the identical word) and is **never 0** -- port_load1 holds
  `data_0209f250` at 0 across the load, and InitResources' one in-VS use of the
  truncated value is the local-player binding at `:105`, so packing 0 would
  have handed the camera and the HUD to the fifth player on every wide boot.
- Then `*(u8*)(actor + 0x6d8) = i`, the true slot, immediately. `Actor::Spawn`
  calls `InitResources` synchronously, so between the call returning and that
  store there is no frame, no tick and no other reader.

### 3. HOSTED WIDTHS

`port/hal/vs_width.h` is new and is the one place the two numbers are written
(`kPortNarrowPlayers` 4, `kPortMaxPlayers` 16), with a `static_assert` against
the transport's pair so one cannot be edited without the other.

Widened: the Ctrl band (`data_0209f498`, `f4a2` / `f4a4` / `f4a6` to
`0x18 * 16`), the per-slot `Player*` table (`f394`), the ready bytes (`fc5c`
and `fc5d`), the slot map (`fc64`), coins (`f358`), red coins (`f30c`), the
stylus modes (`f350`), the carried actor (`f33c`), the raw pad records
(`020a0e58` and `0e5a`) and the touch band (`020a0de8`..`deb`).

**Two of those are placed grouped-section bands and only the TAIL member grew**
-- `data_0209fc5d` and `data_020a0deb`. Every offset `gxband_guard.py` checks
is an offset from the head to a member that did not move, so the `ready` band
stays green by construction rather than by luck. `data_0209f310` needed nothing:
the host already gives it 32 bytes as a guarded pair, and the ROM's own summing
reader (`src/NumVsStarsObtained.c`) already walks `data_0209f21c` rather than
four.

**Sweep correction, on the record.** Phase 1's row C11 called the `[4]` arrays
in `hal/level_boot.cpp:2784-2887` per-player records needing widening. They are
not -- they are SCALARS hosted with the file's four-byte slack (`data_0209f254`,
`data_02092114` and the rest are written as bare scalars by the ROM). Nothing
was widened there and nothing needed to be. The row was wrong and this says so
rather than quietly dropping it.

### 4. SPAWNS: generated, not authored

`port_vs_extra_start` places slots 1..15 on **concentric rings of five** around
the level's real start for slot 0: radii 96, 192 and 288 world units, each ring
rotated half a step (36 degrees) against the one inside it so no two slots share
a bearing. 96 units is 2.4 body cylinders, so the chord between inner-ring
neighbours is about 113 against a combined radius of 80 -- nobody spawns
overlapping and the solver has nothing to untangle.

The old stand-in put extras 40 units apart along +x and its own comment said
OVERLAP; that was RIGHT for two bodies (it made frame 1 a decisive collision
proof) and is wrong for sixteen, which would have been a 600-unit queue with
its far end outside the level.

It is deterministic and identical on every peer, which is the property that
matters: sixteen machines put sixteen bodies in sixteen identical places with
nothing on the wire. **It is not level data**: a 288-unit ring on a small arena
can put a body in a wall and only the ROM's ground raycast catches that.
Authored sixteen-player starts are still owed, per arena.

### 5. NAMES AND COLOURS: the coordinated move, all five readers in one commit set

(colours), `app/server.py` (`build_names` and `build_colors`), and the
launcher's `NamesValid` and `ColorsValid`.

**The grammar is exactly 3 commas or exactly 15. Nothing between.** That is
what keeps the property the ruling exists to protect -- one shape cannot be
mis-parsed as the other, settled in one pass with no count prefix. The launcher
suite walks **every count from 1 to 17** and asserts names and colours agree
about which are legal.

The field count comes from `name_field_count(room)`, one function, read by both
builders, decided by the dial and nothing else.

**Contract v3 on the service**, and it is a real version rather than a number
that went up: the FIELD `match_players` stays a v2 optional, but its RANGE is
gated -- `dial_max_for(ver)` caps a v2 caller at four. Two holes closed with it:
a room default width is now bounded by its HOST version (a v2 host on a
sixteen-player deployment would otherwise have got a sixteen-wide room without
touching the dial it is not allowed to move), and a v2 client joining a wide
room is refused `needs_newer_client` **at the door** rather than seated, armed,
and then failing at spawn -- which would have taken the whole match down with
it, because `failed` returns the room to lobby.

**ONE CEILING COULD NOT BE MOVED AND IT IS COSMETIC.** `yoshi_all_16p_pl` is
128 bytes -- four rows of sixteen colours, size-checked exactly -- and the game
reads one row per player out of that one palette. Above four players the rows
repeat: slot 4 wears slot 0's colours. Growing it means growing an asset the
game allocates from its own data, not a host array the port hosts, so it is out
of this lane's reach. The reader says so in one line at load. Identity is
mPlayerNo and the name string, never the colour. Sixteen authored palette rows
are owed.

### 6. HUD: mechanically exact, deliberately basic, three options banked

**The ROM's four-column band does not bind** (phase 1, finding 2), so there was
no ROM layout to fight. What the port draws is its own winner banner.

The mechanical half is exact at every N: the winner, the draw test, the score
latch, the star-target scan and the readiness census all run over the players
actually in the match. **The marker `scores=` field carries every player**,
always -- it is the machine-readable record, and a summary there would be a lie
to the launcher and the crash pipeline. Four is the floor, so the shipped
parser's four-number case is untouched.

The DISPLAY has three modes behind `SM64DS_VS_BANNER`, and **the default is the
least of them**:

| mode | line |
|---|---|
| `basic` (default) | `MATCH OVER  -  tango WINS  9   you 4   (16 players)` |
| `top4` | `MATCH OVER  -  tango WINS  9 - 7 - 4 - 2  (16 players)` |
| `all` | `MATCH OVER  -  tango WINS  9,7,4,2,2,1,...` |

At four players or fewer **all three collapse to the exact
`%d - %d - %d - %d` line the banner has always printed**, byte for byte.
Captures of all three at sixteen are for the owner's eyes; none of the three is
chosen here as the right one.

## 2026-09-01 -- CHECKPOINT, PHASE 3: THE PROOF LADDER

### The rig

`port/tools/vs16_ladder.sh N frames map` -- VS4P's four-window script,
generalised. Quiet and muted per the standing rule (minimized, never activated,
volume 0), PID-derived port bases stepped by 20 so a sixteen-slot span cannot
interleave with a neighbouring lane's, clear of 51765 and the 58434-58733 band,
desync tracker armed at `SM64DS_VS_STATE_HASH=2` on every window.

Two things it does that `four.sh` did not, both learned by getting them wrong
first:

1. It exports `SM64DS_VS_PLAYERS`. That is the number the carrier reads to pick
   which of the two wires the session speaks, so a run that forgets it forms a
   narrow session and looks like a bug in the wide one.
2. **The parent's budget is the children's plus the whole join window.** Given
   every window the same budget, the parent spends its own run WAITING and
   sends BYE while the last joiner is still booting -- a last window whose
   round counter is pinned and whose hash diverges, which reads exactly like a
   real desync and is not one. That artefact is now designed out and written
   down in the script.

### What sixteen windows actually did

Sixteen instances on one box, all launched, all booted, all paired.

| N | wire | live mask reached | port-supplied starts | slots 0-3 first frame | slots 4+ first frame |
|---|---|---|---|---|---|
| 2 | v2, 0x90 | `0x3` | 0 | round 1 | n/a |
| 4 | **v2, 0x90 (no WIDE banner)** | `0xf` | 0 | round 1 | n/a |
| 5 | v3, 0x214 | `0x1f` | 1 | round 1 | **round 1180 (last)** |
| 8 | v3, 0x214 | `0xff` | 4 | round 1 | **round 1560 (last)** |
| 16 | v3, 0x214 | **`0xffff`** | 12 | round 1 | **round 1840 (last)** |

**Sixteen players form a real session.** The parent's own readout at 16 is
`live=0xffff round=1 ... dropped=0` -- a sixteen-bit live mask on a wire that
had eight bits for it this morning, at 532 bytes against the relay's 700-byte
cap. Every slot from 4 to 15 gets a generated ring start with the **true wide
identity written into it**: `port-supplied start for slot 15 ... wire_slot=3
mPlayerNo=15` is the whole identity mod in one log line -- the ROM saw a 2-bit
3, the actor carries a 15.

### Desync tracker: clean where lockstep exists

`port/tools/dhdiff.py` over every pairing it can compare:

| rung | pairings | verdict |
|---|---|---|
| 2 windows | p0-p1 | **NO DIVERGENCE**, 400 of 400 frames |
| 4 windows | all 6 | **NO DIVERGENCE** on every pair |
| 8 windows | slots 0-3, all 6 | **NO DIVERGENCE** on every pair |
| 16 windows | slots 0-3, all 6 | **NO DIVERGENCE** on every pair |
| 5/8/16 windows | any pair involving slot 4+ | **REFUSING TO COMPARE** -- misaligned, see below |

The tool refusing to compare is the tool working. It checks that two logs are
at the same point in the session before it reports a divergence, precisely so a
misalignment cannot be dressed up as a defect. Slots 4+ are not misaligned by a
constant offset; their whole run sits at the session's last round.

### THE WALL, found by the ladder and named exactly

**`src/func_0203ea5c.c` -- the ROM's own wireless exchange and unpack loop --
is what stops a fifth player playing.** Nine hard-coded `< 4` bounds at
`:310, 326, 347, 352, 367, 403, 428, 471, 499`.

The behaviour is precise and reproducible at 5, 8 and 16, and it is
SLOT-INDEXED, not join-order (at 8 windows it is slots 4,5,6,7 together, not
just the last one to arrive):

- The peer pairs and is accepted. `accepted as slot 15 ... live mask 0xffff,
  players 16`.
- Its transport works. `sent=1194 recvd=1215 dropped=0 round=1180` -- it
  completed the entire run's worth of exchanges.
- Its world boots correctly, in the right place, with the right identity, and
  spawns every other player's body correctly too.
- And then its WORLD never enters lockstep: its first hashed frame is at the
  session's LAST round. It sits in the ROM's own wait until that wait's bound
  expires and then runs on alone.

I ruled out the two things that would have been my fault before naming the
ROM. The wide parent's refusal path was instrumented and fired **zero** times
across every rung, so the BYE a late slot receives is the parent's ordinary
close, not my version gate. And it is not the harness stagger: the pattern is
byte-identical at a 1-second stagger, a 0.25-second stagger and no stagger at
all.

**It cannot be fixed in this lane.** That function is byte-matched ROM code and
`src/` is untouchable here. Moving it means HOSTING it -- replacing that one
function in the port's host layer the way the port already hosts many others.
That is a deliberate deviation of exactly the kind the owner has already
approved for online play, and it is the next lane's whole job.

### One real defect the ladder found and this lane DID fix

`port/tests/walk_window.cpp:6806` still read `me >= 4`. A five-player session
paired, spawned the fifth body and filled `data_0209f394[4]` -- and the harness
threw all of it away and drove slot 0's body instead. It announced itself in
its own log line on every run (`local player index 4 has no actor; the harness
is falling back to slot 0`), which is the only reason it cost minutes rather
than hours. Fixed, and the wide parent's refusal counter now prints a line
instead of only incrementing.

That is a **phase-1 sweep miss and it is on the record as one**: the sweep
covered `port/hal`, `src/`, the service and the launcher, and did not cover
`port/tests/`. The brief named "proofs/rungs that assert 4" as a sweep category
and I under-covered it.

### 2P and 4P regression: unchanged, and the inertness is visible

The narrow path is inert by construction and the logs show it: at 2 and 4
players there is **no `WIDE SESSION` line at all**, the wire stays version 2 at
0x90 bytes, and every pairing is desync-clean over the full run. The mod arms
only when the session says more than four, which is what the whole two-wire
design exists to guarantee.

- **A full match to MATCH OVER with sixteen scores in the marker.** Blocked by

  are not in lockstep. The marker's wide format is proved by the launcher's own
  parse tests (a sixteen-score line parses and keeps all sixteen) and by the
  service suite, not by a played match.
- **Screen captures of the three HUD options at sixteen.** Same reason. The

  `C:\tmp\vs16-out\HUD-OPTIONS.md`, labelled as formats rather than captures,

- **Anything over the relay at sixteen.** Everything above is loopback. The
  relay's own seat knob is proven at 15 by SEAT16 and the 532-byte datagram

  relay.
