## Findings and measured experiments

- `BOMROOM-READ-01` - fixed: misleading 16-byte subarray and 0x10000-byte wrapper models are removed. The typed bomb census and descriptive state/grid locals improve this owned slice while preserving its full unisolated object.
- `BOMROOM-CODEGEN-01` - measured constraint: the bounds-correct byte-base forms need four new, tightly scoped `#pragma opt_strength_reduction off` brackets. All eleven pre-existing positional optimization brackets and `defer_codegen off` remain. The four new brackets surround only `020d6278`, `020d63ac`, `020d65c8`, and `020d669c`; their push/pop scope is explicit. The compiler-default experiments below failed, so adding these local brackets is deliberate rather than a claim that default optimization already supports the cleaner expressions.
- In `typed-bombs-flat-rows.{cpp,o,json}`, directly indexing `sceneBytes[slot * 16 + offset]` grows each dispatcher from 104 to 120 bytes and each clearer from 40 to 56 bytes. In `flat-row-scoped-base.*`, introducing `slotBase = sceneBytes + slot * 16` without the new brackets still grows dispatchers to 120 and clearers to 48 bytes.
- `flat-row-pointer-walk.*` increments the byte pointer by 16 per iteration: dispatchers grow to 116 bytes; clearers retain 40-byte sizes but their instructions differ. `flat-row-integer-address.*` uses an integer address plus `(slot << 4)` and also yields 116-byte dispatchers and different 40-byte clearers. Neither alternative is accepted.
- `flat-row-strength-off.*` retains the scoped byte-base expression with the four new local brackets and restores complete object identity. `readable-locals-opaque-pmf.*` confirms identity after the remaining local cleanup. The four final-source variants `no-new-strength-6278.*`, `-63ac.*`, `-65c8.*`, and `-669c.*` each remove exactly one new bracket: only that function changes, with dispatcher +16 bytes or clearer +8 bytes. These isolate each bracket's necessity and preserve the other functions' output.
- `BOMROOM-CODEGEN-02` - measured constraint: replacing the two `*(volatile u32*)&scene->unk_0bc = scene->unk_0bc + 1` stores with `++scene->unk_0bc` changes only `020d6784`, growing 292 to 300 bytes and changing relocation placement. `direct-score-increment.{cpp,o,json}` preserves this rejected experiment; the explicit volatile stores remain.

All 41 functions still have C-linkage helper identities, not genuine class methods. Many byte offsets, provisional field/global names, PMF receiver bridges, local declarations and fixed-point expressions remain. Their retention is the explicitly bounded first-pass scope, not a claim that every remaining bridge is a measured compiler wall. A later header-owning task should investigate the UI and scene layouts, then class/lifecycle reconstruction.
