# Partitioned translation units: experiment reference

Use this reference when a candidate needs text partitioning, non-text ownership
proof or compiler-output policy investigation. Start normal promotion work at
[TU promotion: workflow and review conventions](tu-promotion-conventions.md);
use [agents/LAUNCH.md](agents/LAUNCH.md) for assignments and resumption.

The commands here are intermediate experiments within that task. They do not
require a separate shadow PR or permission to continue an already assigned
production promotion. An explicitly research-only task still stops at its agreed
scope. Preserve an existing candidate instead of starting a second copy.

Boundary evidence is in [tu-boundaries.md](tu-boundaries.md); destructor experiments
are in [dtor-migration.md](dtor-migration.md). The original text-only pilot is
[tu-reconstruction-pilot-report.md](tu-reconstruction-pilot-report.md), and
`ov002/daObjAbuku_c` supplies a historical partitioned text-plus-data example.

## Ownership model in one minute

A TU is an original compiler input, not a class and not merely a directory grouping.
The ROM exposes a TU indirectly as a contiguous linker contribution plus its emitted
code, data, relocations, RTTI, vtables, and compiler helpers.

- One TU may contain several interleaved classes.
- One class may have methods in more than one TU.
- A vtable usually belongs to the TU containing the class's key function or destructor,
  not to every TU that contains one of the class's methods.
- `src/` is production source. Its delinks entries decide what contributes to the ROM.
- `src_tu/` is a shadow/incubator tree. It contributes through explicit scratch or
  opt-in generated-profile builds, not ordinary production enrollment.
- `config/tu_manifest.d/` licenses exact artifacts and address ranges. It does not
  enroll a file by itself.
- `build/tu/` contains generated objects and reports and is never committed.

Destructor suffixes are ABI variants for the same class, not inheritance levels:

- `D0` is the deleting destructor generated by the compiler;
- `D1` destroys a complete object;
- `D2` destroys the base subobject during another destructor's inheritance-chain work.

A real `Class::~Class()` definition may emit all three. The manifest must account for
each variant the candidate actually emits. An extra variant requires an exact,
evidence-backed output policy; do not infer its existence from another class.

## Proof states are not task endpoints

| Result | What it proves | What it does not prove |
| --- | --- | --- |
| `text-verified` | Declared functions match in one TU context | Whole link, owned data, production enrollment |
| partial link verified | One TU compile yields exact derived text contributions | A whole object can replace legacy objects |
| `partitioned-link-verified` | Licensed derived text and non-text output reproduce the tested module and ROM | Default production enrollment or retirement of legacy sources |
| `promoted` with normal build proof | A canonical production TU replaces absorbed sources | Complete source reconstruction, independent acceptance, or Git merge |

Current tooling supports some intact-object production promotions, including
explicitly admitted non-text and compiler-output policies. The opt-in
`rombuild.py --partitioned-tu <id>` profile is different: it retains legacy sources
as controls and is not default enrollment. Check the actual `tu_promote.py` plan;
unsupported retargeting, aliases or layout remain real blockers. Do not bypass a
refusal, or rely on the older `tubuild.py promote` planner as the final authority.

## 1. Resume safely and establish the control

Follow [PIPELINE](agents/PIPELINE.md) for v2 ownership and exact accepted input,
and [worktree-inputs.md](worktree-inputs.md) for isolated toolchain/build state.
Before interpreting a candidate failure, establish that its baseline is valid:

```powershell
python tools/rombuild.py -j16 --no-rom
```

Record the tested baseline and resolve toolchain/control failures before claiming
a regression. The strict partitioned experiment below also compares a complete
scratch ROM against its stock control; a module-only result is not that proof.

## 2. Select a small TU

Start with a high-confidence overlay boundary whose functions are already matched.
Avoid heavily under-segmented modules, low-confidence cuts, many pragma regimes,
multiple inheritance, static initialization, or several unowned data bands on the
first attempt.

Generate or refresh the TU map when needed:

```powershell
python tools/rtti_extract.py
python tools/rtti_vtables.py
python tools/tu_map.py
python tools/tu_map.py --check
python tools/tu_map.py --module ov002 --verbose
python tools/tubuild.py list
python tools/tubuild.py inspect ov002/daObjAbuku_c
```

`tu_map.py --check` is a diagnostic report: read every printed `PASS`/`FAIL` line
instead of treating process exit status as the verdict. Do not select a module whose
relevant boundary control is failing until that drift is understood on current main.

The `inspect` command should show:

- an exact text span and ordered function list;
- the current legacy source for every function;
- every legacy contribution marked `complete`;
- boundary confidence and independent evidence;
- compiler/version verification for every existing function;
- complications such as destructors, vtables, RTTI, pragmas, or missing sources.

Class-name grouping alone is not TU evidence. Use the interval-overlap and boundary
rules in `tu-boundaries.md`, and record uncertainty rather than inventing a clean
one-class-one-file boundary.

## 3. Build a readable shadow TU

For a new manifest-backed shadow:

```powershell
python tools/tubuild.py create <module/TU-id>
```

If `create` cannot split a legacy body wrapped in `extern "C" { ... }`, curate
that candidate and use `tubuild.build_manifest_entry` for the manifest schema.
The splitter failure does not justify changing linkage or inventing another owner.

The generated file is a starting point, not the readability goal. Curate it under
`src_tu/`:

- keep the first line exactly `//cpp`;
- include the real class/header chain where it is trustworthy;
- use real `Class::Method` definitions and named fields;
- use structured control flow instead of flattened compiler-shaped code when it still
  reproduces;
- keep local layout types local until a shared-header claim is independently safe;
- define functions in the order required by measured compiler section output, which
  may differ from increasing ROM address order;
- explain only codegen artifacts that remain necessary;
- keep unproved experiments out of production; once proved, continue through
  the canonical promotion workflow rather than leaving a duplicate shadow.

Shared-header changes widen the verification surface. Reserve the headers and
affected consumers within the task's scope, then run `tools/affected_src.py` and
the header-consumer gates required by `AGENTS.md`. Separate an independent header
dependency when its scope warrants it.

### Diagnosing combined compilation

Read function order from ELF section indices: `st_value` is normally zero in
these per-function sections. Distinct functions can appear in reverse source
order, while destructor variants follow their own emission rules; see
[class-form observations](cpp-class-form.md).

A pragma can affect the whole TU rather than the following function. The
[codegen notes](mwccarm-codegen.md) record `opt_propagation` and
`optimize_for_size` experiments. Compare the whole owned scope after a change;
a diagnostic subset is not promotion of the full TU.

When separate declarations meet, preserve required declaration order, remove
duplicates and reconcile conflicts against definitions, call sites and ROM
behavior. A shared `decl_common.h` declaration can be wrong. In a disposable
probe, C linkage can reveal conflicting declarations that C++ treated as
overloads; do not retain blanket C linkage as a substitute for real methods.

`999 word(s) differ` can indicate a size mismatch, including destructor variant
emission. Inspect the object before assuming a type mismatch.

## 4. Prove text before claiming data

Run `tubuild.py verify` for the candidate. Standalone `compile`, `partial`, and
`linkcheck --partial` are optional diagnostics when isolating a failure. Once the
candidate and control are ready, run the link mode required by its ownership model.
The diagnostic commands are:

```powershell
python tools/tubuild.py compile <module/TU-id>
python tools/tubuild.py verify <module/TU-id>
python tools/tubuild.py partial <module/TU-id>
```

Inspect all three parts of `verify`'s result, for example:

```text
byte comparison   : 7/7 MATCH
objisolate check  : clean
Result: 7/7 MATCH, objisolate clean, reloc-destinations clean -> TEXT-VERIFIED
```

A wrong destination appears on the offending symbol's row and degrades the
verdict. Missing audit coverage is not a pass. Record whether a failure is:

- wrong function order or section size;
- ordinary instruction mismatch;
- wrong relocation type, addend, symbol, module, or destination;
- an unexpected helper/destructor variant;
- compiler-generated RTTI/vtable/data;
- a header, language-mode, or pragma-state difference.

`match.py`-style comparisons wildcard relocated words. A byte match is not sufficient
when calls, globals, RTTI, or vtables are present. `objisolate`, relocation auditing,
scratch linking, and final module comparison are mandatory.

For a partial-link diagnostic, establish its no-substitution control first:

```powershell
python tools/rombuild.py -j 16
python tools/tubuild.py linkcheck <module/TU-id> --baseline -j 16 --clean
python tools/tubuild.py linkcheck <module/TU-id> --partial -j 16 --clean
```

The first command creates the independent `build/sm64ds.nds` oracle. Without it, a
later scratch ROM may build successfully but cannot earn `matchesStockRom: true`.

The baseline may expose pre-existing `dsd check symbols` errors. Do not hide them and
do not automatically blame the candidate. Preserve the baseline report; later runs
must produce no new error and must remain content-bound to the same config, linker,
dsd, and baseline linked ELF. Rerun the baseline after any relevant input changes.

## 5. Inventory and license non-text output

Only proceed after text is stable. Inventory every live section, symbol, and relocation
in the compiled TU object. Add a manifest range only when the original TU's ownership
and exact placement are evidenced independently.

Common cases:

### Own class RTTI, type name, descriptor, and vtable

Establish the candidate's configured homes for class typeinfo, type-name storage,
spawn descriptor and vtable before claiming the band. Record exact addresses and
sizes from that candidate; a neighboring class's layout is not ownership proof.

For an Itanium-style vtable, mwcc's `_ZTV...` definition begins at storage including
the two-word preamble, while this repository may configure `_ZTV...` at the public
function-slot address point, eight bytes later. Record both
`emitted_storage_address` and `address_point_bias`; do not move one convention globally
to make one object easier.

If the baseline linked ELF carries a separate global symbol for the storage prefix,
use a manifest `storage_alias` row and require exact name, address, size, binding, type,
visibility, section, and baseline fingerprint. Do not suppress the symbol-table
difference or create a size-zero linker label.

### Externalize inherited vague RTTI copies

The compiler may emit base-class `_ZTI`/`_ZTS` records as `STB_LOPROC` duplicates even
though their canonical storage belongs to ARM9 or another module. Use
`externalized_output` only for a dedicated named section whose bytes and every
relocation match one unique configured canonical home. It is an exact allow-list, not
a wildcard for “compiler noise.”

### Account for compiler-only destructor output

Use `compiler_only_output` only for an exact emitted function with a measured reason.
For an unconfigured duplicate destructor variant, prove the required byte and
relocation identity and absence of inbound relocations under the current tool's
policy. A configured, referenced or unexplained helper must fail.

### Refuse uncertain BSS and cross-section mapping

BSS has no retail byte oracle. Require independent configured symbol homes and boundary
anchors; a manifest-authored address that merely agrees with its own scratch LCF is not
proof.

Partitioned mode currently requires the emitted input section and licensed output
section to agree. Do not claim `.data` for a source definition emitted in `.rodata` and
assume the linker will place it. Change the source declaration only if the compiler
then emits the measured retail section and the relocation-aware verifier passes.

## 6. Run the strict partitioned proof

After adding exact `.data`/`.rodata`/`.bss` claims and any explicit policies:

```powershell
python tools/rombuild.py -j 16
python tools/tubuild.py linkcheck <module/TU-id> --baseline -j 16 --clean
python tools/tubuild.py linkcheck <module/TU-id> --partitioned -j 16 --clean
```

Do not use `--no-rom` for the final claim. It is useful while debugging but cannot
earn the strict status.

`PARTITIONED-LINK-VERIFIED` requires all of the following in one attempt:

1. The shadow TU is compiled once with the expected pin.
2. Every declared legacy text function is derived and contribution-identical.
3. Every expected legacy object path is actually replaced exactly once.
4. The LCF has exactly the expected ROM-ordered text selectors and one allowed
   non-text TU selector, with no hidden whole-TU text selector.
5. Compiler-only and externalized policies verify before their sections are removed.
6. The reduced non-text object retains only licensed content.
7. Owned bytes and relocation type, symbol, addend, module, and destination all match.
8. Any vtable storage alias and public address point match the baseline linked ELF.
9. The linked text and data ranges match retail.
10. The affected module and all repository modules reproduce.
11. Symbol checking adds no error relative to the content-bound baseline.
12. The scratch ROM is identical to the independently built stock ROM.
13. No file escapes the scratch tree or changes shared build output.

The persistent `partitioned_link` record keeps compact hashes and evidence in
`config/tu_manifest.d/`; the complete report remains under the ignored
`build/tu/<id>/link-partitioned/linkcheck.json`.

Run the commands above against the assigned candidate and its pinned manifest.
Abuku is already promoted as a text-only TU and is not a runnable partitioned
control; do not recreate its retired sources to replay an old experiment.

## 7. Continue through promotion or record the measured blocker

Return to [the canonical promotion workflow](tu-promotion-conventions.md) after
this experiment. Use `python tools/tu_promote.py <module/TU-id> --dry-run` to
inspect the actual production plan. A passing scratch link is not proof that the
normal build can consume all of its policies, and a successful plan is not a byte
verification result. Apply a supported promotion, retire the absorbed sources,
and verify the final default build before independent review.

When the plan refuses a needed policy, preserve the exact experiment, refusal,
owned ranges and remaining production changes. Schedule the required tooling
repair separately and name the source continuation owner. Publish a bounded
evidence-only result only when the assignment or a concrete blocker justifies it;
label it as incomplete production work. Do not weaken ownership or source coverage
to make the promotion tool accept it.
