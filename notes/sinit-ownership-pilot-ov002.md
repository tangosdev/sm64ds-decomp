# Static-initializer ownership pilot: `ov002/dEnemyBase_c`

## Verdict

**CONFIRMED ownership:** `__sinit_ov002_02100938` belongs to the original
`dEnemyBase_c` translation unit and was generated by two non-const, eight-element
arrays of pointer-to-member functions (PMFs).

This confirms the ownership row; it does **not** make the reconstructed TU ready
for production promotion. The original names of sixteen member functions remain
unknown behind `func_ov002_*` symbols, one text function in the TU is unmatched,
and the existing vtable/RTTI alias issues remain independently unlicensed.

## `.ctor` and neighbour audit

Overlay 2 has 26 `__sinit` functions and exactly 26 `.ctor` entries. This
initializer is ordinal 1; `.p__sinit_ov002_02100938` at `0x021080d4` relocates to
it. The immediately preceding initializer is the ambiguous shared-resource
initializer `__sinit_ov002_02100560`. The immediately following initializer,
`__sinit_ov002_02100adc`, independently resolves high-confidence to
`ov002/OneUpMushroom`, the next substantial class TU after the small
`0x020aedbc..0x020aee40` tail/destructor records. No adjacent initializer proposes
the `dEnemyBase_c` tables and this row has no conflict blocker.

## Organic compiler proof

The pilot block at the end of `src_tu/actors/Enemy.cpp` is excluded normally and
enabled only by `-DSINIT_OWNERSHIP_PILOT`. It declares two ordinary non-const PMF
arrays and deliberately contains no `__sinit` function. Under pinned mwccarm
2004/b56, the compiler generates:

- one `.init` function, `__sinit_Enemy.cpp`, size `0x1a4`;
- one four-byte `.ctor` entry with `R_ARM_ABS32`, addend 0, to that initializer;
- sixteen separate eight-byte `.data` PMF descriptors, each with one
  `R_ARM_ABS32` function relocation at offset 0, addend 0, and a zero adjustment
  word at offset 4;
- two separate 0x40-byte `SHT_NOBITS` tables;
- eighteen `.init` `R_ARM_ABS32` relocations, all addend 0, at offsets
  `0x15c, 0x160, ... 0x1a0`.

The generated `.init` result is exact in three independent comparisons:

1. Against the ROM at `0x02100938`: `MATCH`, size `0x1a4`, zero non-relocation
   divergences.
2. Against the compiled hand transcription in
   `src/__sinit_ov002_02100938.c`: all 420 raw object bytes and all eighteen
   relocation offsets are identical.
3. In the full Enemy shadow object: all thirty admitted text functions remain
   raw-byte identical to the normal shadow object and all thirty functions'
   relocation `(offset, type, symbol, addend)` signatures remain identical.

The normal, flag-disabled shadow TU still passes `tubuild verify`: 30/30 text
matches, `objisolate` clean, relocation destinations clean. Its known partial
result remains 29/30 because `dEnemyBase_cD2Ev` uses the existing co-address
`data_ov002_021081e4` / `_ZTV12dEnemyBase_c` alias; the pilot did not alter that.

## Remaining blockers

- The sixteen target functions still have address-derived `func_ov002_*` names.
  C++ needs the original member names/signatures to emit their exact mangled
  descriptor targets; CodeWarrior rejects casting an `extern "C"` free-function
  pointer to a PMF. The probe therefore proves codegen, representation, order,
  relocation type/addend, and TU ownership while using stand-in member spellings.
- `_ZN12dEnemyBase_c14UpdateYoshiEatER10dBgCh_Actr` at `0x020ade78` remains an
  unmatched hole, so the complete `0x020ad838..0x020aedbc` text span cannot yet
  be whole-range linked from one TU.
- The TU's vtable/RTTI output and the co-address vtable alias remain separately
  unlicensed. No production `src/`, delinks, symbols, or manifest ownership rows
  were changed by this pilot.
