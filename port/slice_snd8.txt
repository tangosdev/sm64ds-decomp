# sd_sound_frame_host and sd_sound_fade_host, that between them transcribed
# src/func_0204f03c.cpp and src/func_020132d8.cpp with five calls SKIPped. Each

#   func_020508a0   the streamed-sound frame       R8
#   func_020522c4   the four streamed-sound players R8
#   func_02013078   the swim-state reporter        R10 (already linked)

#   func_020490b0   the filter's per-frame ramp    R10

# ROM's own phase 9 -- at the point sdat_host_tick already occupies.
#
# ---------------------------------------------------------------------------
# R8, THE STREAMED-SOUND FRAME, AND WHAT IT ACTUALLY DOES TODAY: NOTHING, AND
# THAT IS THE HONEST STATE RATHER THAN A DEFECT.
#
# func_020508a0's first line is `if (*(s32 *)(data_020a5634 + 0) == 0) return;`
# and func_020522c4 walks four 0x12c-byte records at data_020a5bd4 whose +0xf0
# flag word gates every branch. Both objects are zero, because standing a stream
# up needs the 1MB sound heap (rung R2), the SDAT opened off the card (R4) and
# the ARM9 sound thread (R5) -- the three held for Tango's word. So the ROM's
# frame runs and finds no stream, which is exactly what it does on hardware with
# no stream playing. The seat is worth taking anyway: it is the ROM's own
# reference graph reaching these TUs, and it is what lets func_0204f03c (R9) be
# called whole instead of transcribed with two holes in it.
#
# FOUR TUs BELOW ARE ON THE SCOUT'S R6 LIST AND COME IN HERE. rungs.tsv put
# func_0205abb8, func_0204f0b8, func_0204f15c and func_020502b8 (and behind them
# func_0204f11c, func_0205a958, func_0205aa9c, func_0205b504) under R6, the 3D
# voice pool and capture layer. They are not capture: they are the STOP path a
# stream frame reaches (func_020508a0 -> func_020502b8 when a stream's own stop
# flag is set, func_020522c4 -> func_02052208 -> func_0204ff9c -> func_0204fde8),
# and R8 does not link without them. Measured with port/tools/closure.py over
# the whole set before a line was written. R6's real content -- DS sound CAPTURE
# and the 24-tap echo DSP, which the host mixer models nowhere -- is untouched.

# R10: THE UNDERWATER MUSIC FILTER, which this port has never had.
#
# One mechanism in three parts, and consumer.cpp was right that it had to be
# taken as a unit: func_02013078 (already linked) reports a CHANGE in the
# player's swim state and latches its answer in data_0208e438, so running it
# alone consumes the state changes the other two need to see; func_020494cc
# programs a two-channel ramp table (data_020a4c48/4c/54) from that state; and
# func_020490b0 advances the table each frame and pushes it at the music player
# through func_0204f82c -- command 0x04 parameter 0x0a, the per-track
# attenuation the consumer already honours.
#
# WHAT UNBLOCKED IT: five words. func_020494cc reads data_02082200, _02082204,
# _02082208, _0208220c and _02082210 and not one was defined anywhere in the
# port. They are arm9 .data, four bytes each by the delta rule, with ZERO
# relocations in any of the five spans (checked against config/arm9/relocs.txt:
# no `from:` row exists anywhere in 0x020821f0..0x02082214), so they are read
# out of the cartridge by port/tools/romdata.py's NAMED list rather than
# written down.
src/func_020494cc.c
