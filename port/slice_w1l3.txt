# ---- wave 2: the shadow list, one static of two -----------------------------
# Wave 1 parked the shadow-list files below as "they come in with Stage, not
# before it". The ROM callers really are only the three Stage methods --
#   from:0x0202b99c -> 0x02015d38  ShadowModel::RenderAll, inside Stage::Render
#   from:0x0202bc38 -> 0x02015e14  ShadowModel::CleanAll,  inside Stage::Behavior
#   from:0x0202c20c -> 0x02015e14  ShadowModel::CleanAll,  inside Stage::Behavior
#   from:0x0202d484 -> 0x02015e14  ShadowModel::CleanAll,  in Stage::InitResources
# -- but the port already TRANSCRIBES Stage::Render and Stage::Behavior by hand
# in tests/walk_window.cpp, in the ROM's own order, and both transcriptions had
# simply skipped these calls. So no Stage seat is needed to reach them.
#
# CleanAll goes in, above port_actor_tick. It is Stage::Behavior's LAST
# statement but it belongs before the other actors tick, because the three
# ShadowModel TUs describe a freeze protocol -- InitModel refuses while
# data_0209ceec is set, RenderAll sets it, CleanAll clears it -- and the
# registrations come from actors' own Behavior methods. The ROM gets that
# ordering from the Stage's behaviour priority of 3 (spawn record 0x0209213c);
# the port gets it from where the call sits.
#
# RENDERALL DOES NOT GO IN, and this is measured, not assumed. Seated between
# RenderModel and RenderModelTransparent, walk_window takes an access violation
# on frame 1: FAULT c0000005 at +0x000893c8 (eight bytes into func_02046120)
# from +0x000892b1 (inside RenderAll), accessing 0 -- `self->sub->count` with
# self null, self being the node's ModelComponents at +0x08.
#
# The shadow list is NOT empty on the port. Actor::DropShadowRadHeight's C
# spelling resolves to the matched src/ body, which calls ShadowModel::InitModel
# for real, and Butterfly::Behavior takes that path every frame on this level.
# (This paragraph used to open by contrasting that against Actor::DropShadow
# ScaleXYZ, "a host no-op in hal/cxxname_bridge.cpp". True when written, wrong
# now: the wave-4 block at the end of this file gives DropShadowScaleXYZ the
# matched body too, so both siblings feed the list. The RenderAll fault below
# is unaffected -- it is about what is IN the nodes, not how many.)
# The node that lands has data == 0 because ShadowModel::InitCuboid IS stubbed
# -- the cuboid template BMD is static .data in overlay 1 at 0x020ad524, and
# the port's ov001 mount is per-symbol and covers only 0x020ab800..0x020abb00,
# the HUD's sprite templates (port/ov001_syms.txt). Guarding the loop would be
# inventing behaviour the ROM does not have, so RenderAll and its two callees
# func_02046088 / func_02046120 wait for the shadow half of ov001.
#
# Worth recording: RenderAll ran green when CleanAll sat at the END of the
# behaviour phase, because the list was force-emptied after the actors filled
# it and before RenderAll read it. That is the wrong order and would draw no
# shadows at all once ov001 lands, so that green run was not a seat.
#
# CleanAll's only other listing is slice_gate36.txt, which port/CMakeLists.txt
# reads into SLICE36_SOURCES and then never adds to a target, so it compiles
# nothing and this line is the one that does the work.
src/_ZN11ShadowModel8CleanAllEv.cpp

# Fader::AdvanceInterp drags one name with it: it calls the 20.12 approach
# helper by the ROM spelling func_0203ae58, which only hal/shims.cpp defines and
# walk_window does not link that file. fader_wipes.cpp supplies it as an
# alternatename onto the C face of the matched ApproachLinear, so a target that
# DOES link shims.cpp keeps its own strong definition and nothing collides.
#
# NOT TAKEN, and this is the interesting half. FaderBrightness's SetForwardTime
# / SetBackwardTime / IsBetweenStartAndEnd are matched too and are NOT seated,
# because each ENDS IN A VIRTUAL CALL. Under mwcc IsAtStart/IsAtEnd are ROM
# slots 5 and 6; MSVC folds the two destructor slots into one, and HalFaderWipe
# spends two slots holding ROM byte order, so a FaderBrightness slot-4 dispatch
# lands on HalFaderWipe::SetForwardTime -- which takes two ints under
# __thiscall, so a no-argument virtual arriving there unbalances the stack.
# Slot 5 is merely the wrong predicate. Seating those three needs the wipe table
# to BE a FaderBrightness, which is the ROM-class swap below, not a slice line.
#
# THE ROM-CLASS SWAP (data_0209f324 = the ROM's own construction) -- wave 4+.
# Stage::InitResources builds the array as
#     data_0209f324 = func_02073470(7, 0x60, 8, FaderWipe::FaderWipe,
#                                               FaderWipe::~FaderWipe);
# and every piece of that now exists: func_02073470 has a host body in
# hal/actor_vtables.cpp, and FaderWipe's ctor, both dtors, AdvanceFade and
# LoadAndSetFile are all matched under src/engine/fader/. Three things block it,
# and only the third is hard:
#   1. _ZTV9FaderWipe (arm9 0x0208ea9c) is not hosted anywhere in the port. Its
#      ten slots resolve, by config/arm9/relocs.txt, to FaderWipe D1/D0/
#      AdvanceFade then seven FaderBrightness bodies -- all matched -- so a
#      hal_fill_* over hosted storage would seat it in ROM order and, unlike a
#      host class, SOLVE the dtor-fold skew rather than work around it.
#   2. slice_gate36.txt already lists the FaderWipe ctor/dtor/LoadAndSetFile,
#      but port/CMakeLists.txt reads it into SLICE36_SOURCES and never adds it
#      to a target, so it compiles nothing.
#   3. THE FADE WOULD STOP RENDERING, which is why this was not forced here.
#      The matched FaderWipe::AdvanceFade writes the MAIN engine's blend
#      register (0x4000050) only on its cur == 0x1000 branch, and writes the SUB
#      engine's (0x4001050) on the common path. The port's compositor reads
#      0x4000050 / 0x4000054 (port_fader_blend_state, below), so through most of
#      a fade it would see nothing and the screen would not darken. The host
#      AdvanceFade writes BOTH engines every step, and that divergence is what
#      makes the fade visible. The matched body also calls ModelComponents::
#      Render on a Model that FaderWipe::LoadAndSetFile fills from the stage
#      filesystem the port does not mount -- the same null-sub shape that
#      faulted ShadowModel::RenderAll in wave 2. A working fader is
#      player-facing; this wants a compositor decision, not a slice line.

# ---- wave 4: the shadow the port was NOT dropping ---------------------------

# exists and never reaches the binary.
#
# THE REFERENCE EDGE IS ALREADY THERE, which is why this is one line and no
# seat. /OPT:REF keeps a matched TU only if something names it, and nine TUs in
# walk_window.map already call this symbol by its C spelling: SignPost::Behavior
# and ArrowSignRight::Behavior plus func_ov015_021114f0, func_ov015_021123c8,

# AND THEY FIRE, counted rather than assumed, because a swap nothing calls is
# not a swap. A scratch build put a call counter in the fallback in
# hal/cxxname_bridge.cpp and held this line out so walk_window resolved onto

# castle-grounds boot alone (five SIGN_POST spawn there). The empty body was

# reverted; no counter is in the tree.
#
