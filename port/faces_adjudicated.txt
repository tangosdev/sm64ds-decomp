# faces_adjudicated.txt
#
# A RULING PER FACE. linkage.py's FACES bucket is every symbol where a host
# file defines the ROM's C name AND the matched TU of that name is also in the
# binary. Its own docstring refuses to call that bucket either work or not
# work, and is right to:
#
#   "A map cannot prove forwarding. All this bucket knows is that both
#    definitions are linked. That is consistent with a face that forwards into
#    the matched body, and equally consistent with a host body that duplicates
#    it while the matched TU is kept alive by some other caller."
#
# 210 symbols sat in that state, inside the published 43.5%. Every one of them
# is read here and ruled.
#
#   FORWARDS    the host definition calls the matched body. The decompiled code
#               is what runs and the face only carries the ROM's C name to it.
#               Not work.
#   DUPLICATES  the host definition does the work itself. The matched TU is in
#               the binary for some other reason and the decompiled code is NOT
#               what runs on the C-name path. Replacement work.
#   UNCLEAR     read and not settled. None so far; a row that cannot be settled
#               belongs here rather than being rounded to FORWARDS.
#
# FORMAT:  <symbol>  <ruling>  <file:line> -- <evidence>
#
# The file:line is the host DEFINITION, so a reader can check the ruling
# against the same text it was made from. Regenerate with
#
#     python port/tools/faces_adjudicate.py --ledger
#
# APPEND-ONLY, like inferred_stub_adjudicated.txt. A ruling that turns out
# wrong is corrected by a new dated section saying so, not by editing the row:
# the point of the file is that a claim can be traced to when it was made and
# on what evidence.
#
# ---------------------------------------------------------------------------
# HOW THE 210 WERE READ, and what the reading can and cannot see.
#
# 178 of them are one statement whose only call names the same class and the
# same method the symbol demangles to -- `((Trap *)self)->Trap::Behavior()`.
# That is a forward by construction. The class name is required and not just
# the method name, because dropping it is what makes the wrong-target trap
# invisible: _Z14ApproachLinearRsss forwarded to ApproachLinear2, a sibling
# differing only in s16 wrap, and shipped with signs spinning forever. Both
# ApproachLinear faces are re-checked by hand in this pass and both now name
# their own target.
#
# The other 32 were read individually and carry a hand-written reason. The
# recurring shape is the SHADOW-CLASS IDIOM: the host declares a local
# one-method class and aliases its mangling onto the real one, so the body
# names `StarMarkerFace::SpawnRedCoinStarIfNecessary` and only the
# /alternatename pragma beside it says where that goes.
#
# WHAT THIS PASS DOES NOT PROVE. It reads C, not emitted bytes. A face that
# names the right class and method can still be wrong on ARITY or on RECEIVER
# delivery, and the checklist at the top of port/hal/method_faces.cpp asks for
# all three checked from the emitted code. Target is what is settled here.
#
# ---------------------------------------------------------------------------
# run linkw wave C (lane cat-arm9), 2026-08-15, at 459f21a07 + this lane.
# gate.py GREEN, battery ALL GREEN, linkage 4888 / 11243.
#
# RESULT: 209 FORWARDS, 1 DUPLICATES, 0 UNCLEAR.
#
# The one duplicate is _ZN8dActor_c17TrackInDeathTableEv. Everything else in the
# bucket is a real bridge, so the 210 faces are not hidden scaffolding inside
# the linked percentage, which is what this pass was asked to find out.
# ---------------------------------------------------------------------------
