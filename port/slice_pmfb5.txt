# THREE OF THE NINE ov006 CANDIDATES REFUSE ON ROM EVIDENCE, and the refusals
# are the useful part of this batch. The census gives each of them a `table`
# column, and at the row's own address none of the three indexes that table:
#
#   func_ov006_020ed18c (dScMgHanachan_c, "table" data_ov006_02141fcc).
#     The pool word at 020ed25c IS 02141fcc, so a reader that only checks for
#     the constant would pass it. The body then does `ldrh r5,[r2]` /
#     `add r0,r5,#0x800` / `strh r0,[r2]` -- it uses that address as a
#     SIXTEEN-BIT COUNTER, not as a table of pairs -- and takes its member
#     pointer from `r3 = r4 + 0x4660`, an OBJECT FIELD. There is no shift-scaled
#     add anywhere in the body. It is an object-field row and belongs to the
#     writer lane.
#
#   func_ov006_021214f8 (dScMgTrampoline_c, "table" data_ov006_02140588).
#     Same shape. The pool word at 02121570 is 02140588 and the body does
#     `ldr r4,[r1]` on it once -- a plain global pointer read -- then takes the
#     member pointer from `r3 = r5 + 0x5004`, an OBJECT FIELD. No shift-scaled
#     add. The census's own reason column says as much ("a member pointer held
#     in the field at c+0x5004"); the table column contradicts it and the ROM
#     settles it.
#
#   func_ov006_02107db8 (dScMgRoulette_c, "table" data_020a0e68).
#     NO POOL WORD IN THE BODY MATCHES 020a0e68 AT ALL. The dispatch is
#     `ldr r1,[r4,#0x20]`... `ldr r1,[r0]` / `ldr r1,[r1,#0xc]` / `blx r1` off
#     `r0 = r4 + 0x10` -- a VIRTUAL call on slot 3 of a vtable held at
#     this+0x10, which is what the census's own reason column calls "a
#     virtual-shadow dispatch". There is no member-pointer table here to seat.
#
# A FOURTH IS MEASURED AND STILL NOT TAKEN, for a witness reason rather than a
# ROM one. func_ov006_0212a2e0 (dScMgSnowball_c, data_ov006_02143038, 3 slots,
# arity 1) passes every ROM test: `add r3,r4,r0,lsl #3` at 0212a308 on the pool
# word 0212a3b4 = 02143038, emitted [eax*8]/[eax*8+4], three source pairs all
# {code,0} whole-pair at src/__sinit_ov006_021333e0.c's own addresses. What
# stops it is that its host copy is the ONLY place that can compute
# g_snw_live_last -- "%u live element(s) on the last Behavior pass" in
# hal/scene_mg_snowball.cpp's exit census -- because that is a PER-PASS
# aggregate over the fifty-element array and every face runs per DISPATCH. A
# face cannot see a pass boundary, so retiring the copy would silently zero a
# census field with nothing wrong. Every other witness in this batch moved into
# the faces exactly (see below); this one cannot, and inventing a pass boundary
# from the loop index is a guess that is wrong whenever two consecutive passes
# each dispatch exactly one element at an increasing index. LEFT FOR A LANE
# THAT OWNS hal/scene_mg_snowball.cpp: change that one printf to read a total
# rather than a per-pass count, and the row costs nothing.
#
# THE RECORD STRIDE, ROM SIDE, read at each body's OWN address out of
# extracted/overlays/overlay_0006.bin at ov006 base 0x020bfec0
# (runs/link100/out/PMFB5/rom_gate1.txt):
#   020e0204  add r3, r4, r0, lsl #3 at 020e0230  pool 020e02ec = 02141870
#   020e4800  add r3, r4, r0, lsl #3 at 020e4860  pool 020e48c8 = 02141988
#   02104ac4  add r3, r1, r0, lsl #3 at 02104ae8  pool 02104b20 = 021427bc
#   0210bcb0  add r3, r4, r0, lsl #3 at 0210bcd0  pool 0210bd94 = 02142bdc
#   021254c0  add r3, r4, r0, lsl #3 at 021254e0  pool 02125514 = 02142f94
# -> EIGHT on all five. THE OTHER SHIFTED ADDS IN THOSE BODIES ARE NOT THE
# TABLE: 020e4800 carries the fifty-element `add r6,r6,#0x24` walk and 020e0204
# the three-frame animation walk off data_ov006_0213c0d8. The record stride is
# the add whose base register is the one the literal pool loaded with the table
# address, and that is the add quoted above in each case.
#
# THE RECORD STRIDE, EMITTED SIDE, off each matched TU's own /FAsc listing under
# the port's own flags (runs/link100/out/PMFB5/emit_gate1_out.txt and
# listings/): [eax*8] and [eax*8+4] on all five. ROM 8 == emitted 8.
#
# NO /Zp4 ON THIS BATCH, measured and not omitted. Lane PMFB1's lever is that
# MSVC aligns any struct CONTAINING a pointer to member to eight, which rounds a
# twenty-byte record to twenty-four and makes every state after state 0 read the
# wrong record silently. Each of these five TUs was compiled both ways for this
# lane and the two listings are IDENTICAL except for the TITLE line naming the
# .obj -- zero real diff lines -- so R10a's own rule applies and the option is
# left off rather than claimed.
#
# THE THIRTY-SIX SOURCE PAIRS ALL READ {code, 0} at the addresses each owning
# __sinit copies them from, read out of the overlay image rather than taken from
# a seat's runtime assertion, and every one is a WHOLE-PAIR copy. All three of
# the spellings lane PMFB4 found are present across the five constructors
# (`TAB.pN = SRC`, `TAB[N] = SRC`, `TAB.p[N] = SRC`) and the reader reads all
# three; a field-form fill would be `.pN.a =` / `.p[N].a =` and there is not one
# anywhere in this batch. The per-slot tables are beside each installer.
#
# THE DISPATCH SHAPE, and the arity comes from each row's OWN listing. All five
# emit `mov ecx, tab[i*8+4] / mov eax, tab[i*8] / add ecx, <this> / call eax`
# with NO `add esp, N` after it -- a __thiscall indirect, receiver in ecx,
# callee cleanup -- so a plain cdecl body cannot go in the code word. Two of the
# five push one argument before the call (020e4800 pushes edi, its own loop
# counter; 02104ac4 pushes a literal 0, which is its src's own `(0)`) and three
# push nothing. PMFC2's `note` column says "0 stack argument(s)" for all nine
# candidates including the two that push one; it is the same class of error lane
# PMFB4 recorded against it, so every arity here is read off that row's own
# listing. THIRTY-SIX FACES in all, one per CELL and not one per body.
#
# TWO /alternatename DIRECTIVES, each mangling read off the object with
# dumpbin /symbols:
#   ?data_ov006_02141988@@3PAP8C@@AEXH@ZA     (unmatched/MgCurling2_StateDispatch.cpp)
#   ?data_ov006_02142bdc@@3PAP8Obj@@AEXXZA    (unmatched/MgSlot3_StateDispatch.cpp)
# The other three TUs declare their tables inside their own extern "C" blocks
# and come in as the plain C name the ov006 mount already defines.
#
# THE UNDEF SWEEP RAN BEFORE THE LINK, not after it. Lane PMFB4's gate 2 lost an
# exe to a C++-decorated external nobody had predicted, so every object in this
# batch was dumped with dumpbin /symbols and every UNDEF read before the tree

# directive in the tree: ?data_0209d4b8@@3HA (hal/scene_mg_faces_gen.cpp:11),
# ?data_0209d45c@@3EA (unmatched/MgMemory2_Faces.cpp:196) and
# ?data_0209e650@@3HA (hal/cxx_aliases.cpp:1656). That is why this batch adds
# two directives and not five.
#
# EVERY ROW READS EXACTLY ONE TABLE, checked the way PMFB4's gate-3 finding says

# EXTRNs, not only the one the census names. None of the five reads a second
