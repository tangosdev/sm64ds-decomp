SEATING dScDSMT_c: the ov007 TITLE SCREEN and FILE SELECT, scene id 1. What the
ROM says its vtable is, what the spine's two caveats turned out to be, how far
the boot gets and exactly what stops it. Run link60, lane L2.

Baseline this was measured against: 0d81b845c, walk_window 4950/11243 linked
(44.0%), battery ALL GREEN, gate skips [scene 4 with SM64DS_SCENE_SLOT9=0]. No
exe hash is quoted on purpose -- the link embeds build-location state, so a
sha256 from one worktree is not something another worktree reproduces. The
attestation is the gate manifest's git_sha plus git_dirty.


1. WHAT THIS IS, AND WHAT IT IS NOT
-----------------------------------

The S1 spine lane brought up ov003's star select and wrote down two caveats for
whoever seated the next scene. The e-ov007-mount lane hosted ov007's 716 data
symbols. This lane seats the class those two were built for.

IT IS NOT A SLICE OF ov007, IT IS VERY NEARLY THE OVERLAY. A relocation BFS
from dScDSMT_c's eight entry points -- the factory plus the seven overridden
vtable slots, expanding any ov007 data symbol a load reaches whose words are
relocated into ov007 .text -- reaches ALL 548 of ov007's functions through 165
such code tables. There is no smaller honest unit: the title screen is what
ov007 is for.

IT DOES NOT RUN. Section 5 is the blocker and it is a hole in the decomp, not
in the port. Read section 4 for what IS proven before deciding how much that
costs.


2. THE VTABLE, DERIVED, AND THE WIDTH QUESTION ANSWERED
--------------------------------------------------------

THE TABLE ADDRESS comes from the ROM twice over and neither route is a guess.
config/arm9/relocs.txt has `from:0x02090868 kind:load to:0x02103264
module:overlay(7)`, and 0x02090868 is ACTOR_SPAWN_TABLE + 4, the slot for actor
id 1. The record at 0x02103264 reads, out of extracted/overlays/overlay_0007.bin
at (addr - 0x020ad660):

    +0  d0 ca 0c 02    0x020ccad0   the factory, func_ov007_020ccad0
    +4  01 00          1            the actor id, which the registry cross-checks
    +6  03 00          3
    +8  "9dScDSMT_c\0\0"            the Itanium type name, inline

and one word into that factory's literal pool is 0x021032e8. The other route is
the Itanium layout: 0x021032e4 relocates to 0x02103278, which is a
__si_class_type_info record (vtable+8 at 0x0209a764, name 0x0210326c reading
"9dScDSMT_c", base 0x020914d4), and a typeinfo pointer sits one word below slot
0. Both say the table starts at 0x021032e8.

THE WIDTH IS 18, and vtspan's three routes agree with no disagreement to report:

  1. RELOC RUN. Eighteen CONSECUTIVE relocated words, 0x021032e8 through
     0x0210332c, and then it stops: 0x02103330, 0x02103334, 0x02103338 and
     0x0210333c carry no relocation in config/arm9/overlays/ov007/relocs.txt.
  2. SYMBOL BOUND plus the ROM bytes. dsd's next symbol is 0x02103340, which is
     the .bss base, so the symbol is 88 bytes -- 22 words -- and words 18..21
     read 0x00000000 in the image. Trailing zeros, not slots. This is the route
     vtspan.py warns can truncate; here it over-counts instead, and the bytes
     settle it.
  3. SEMANTIC TAIL. Every one of the eleven non-overridden slots holds the same
     arm9 address ov003's three classes hold, byte for byte. dScDSMT_c is
     _ZTV5Scene with seven slots overridden and adds no virtual of its own.

So scene_fill_shared's hardcoded eighteen-slot shape HOLDS and was left alone.
The caveat is discharged by measurement, not by widening: a width parameter with
one caller and one value would be ceremony, and the next scene that disagrees is
the one that should add it. THAT SCENE IS STILL COMING -- ov006's minigame
classes derive from dScMgBase_c, which derives from Scene, and nothing here says
anything about their shape.

what resolve the placeholder spellings). This is the eleven-bodies-of-work the
ov003 write-up called "mechanical, not hard", done for a different overlay, and
it reached the same verdict lanes w13 and w16 reached: the marker records how
the NAME was recovered and says nothing about where the BODY came from.

THE PLACEHOLDER BLOCKER, the other thing that stopped dScTitle_c, also cleared.
The dtor pair spells its vptr restores with per-TU stand-ins, and the ROM words
are in each body's literal pool: _ZTV9dScDSMT_c and VT0 are 0x021032e8,
_ZTV8dScene_c and VT1 are 0x02092680 (_ZTV5Scene), _ZTV7dBase_c and VT2 are
0x0208e4b8 (_ZTV12ActorDerived), G0 is 0x020a0eac. Two of the six needed a face
and four resolve to storage that already exists; hal/scene_boot.cpp has the
full reasoning, including the one that is a KNOWN DIVERGENCE rather than a fix.

WHERE THE TABLES LIVE, and it is the one real difference from the ov003 seat.
ov003's class table is a fresh host array because port/ov003_syms.txt leaves it
out of the mount. ov007's mount hosts BOTH tables (data_ov007_021032e8,
data_ov007_021032b0) as ordinary byte arrays carrying the ROM's raw DS code
addresses, so a second host array of the same name would be a duplicate symbol
and leaving the mounted one alone would leave live wild pointers in a table the
factory installs. The fill therefore writes host thunks INTO the mount's own
storage. That is the right treatment when the table is inside a mounted span,
and it is what the next whole-overlay scene mount should do.


3. THE TWO SPINE CAVEATS, AUDITED
----------------------------------

CAVEAT 1, the 18-slot hardcode: answered in section 2. Width 18, three routes
agreeing, scene_fill_shared unchanged.

CAVEAT 2, the sublevel write. port_scene_run wrote data_02092110 on EVERY run
and its own comment asked the ov007 lane to audit that rather than inherit it.
THE ANSWER IS THAT dScDSMT_c DOES NOT READ IT, and the evidence is counted both
ways so the negative is a measurement and not a failure to find something:

    relocations into 0x02092110 from anywhere in ov007      0
    relocations into 0x02092110 from anywhere in ov003      6
      0x020ae0a0, 0x020ae194, 0x020ae344   dScStarSel_c's Render closure
      0x020aefcc                            its Behavior
      0x020af824                            its InitResources
      0x020b041c                            dScGameOver_c's

and no ov007 source TU among the 527 names data_02092110, SublevelToLevel or
SUBLEVEL_LEVEL_TABLE.

SO THE WRITE IS GATED, on a per-class reads_sublevel column in
port_scene_classes. It is worse than inert for id 1, which is why this is a gate
and not a tidy-up: hal/level_change.cpp reads the SAME BYTE as "the next level,
-1 = nothing pending", and port_level_change_pending() is literally
`data_02092110 >= 0`. The title screen is what comes up at boot before any level
is pending, and writing 6 there parked a level change the ROM would never have
parked. Nothing consumes it in a scene run today -- port_scene_run does not
return to walk_window's level loop, which is the only caller of
port_level_change_pending -- so this is latent cross-talk closed before it
fired, not a bug that was firing. The run prints what it did instead:

    [scene] sublevel NOT written (SCENE_TITLE does not read data_02092110;
            0 relocations from ov007). It holds -1.

A CORRECTION THAT COMES OUT OF THE SAME AUDIT. port/scene_boot_map.txt section
6 and the header block in hal/scene_boot.cpp both say "data_02092110 starts at
0". IT STARTS AT -1. build/port/host-src/romdata.c emits
`data_02092110[4] = { 255,0,0,0 }`, and the ROM agrees: extracted/arm9_dec.bin at
(0x02092110 - 0x02004000), the base port/tools/romdata.py documents, reads
ff 00 00 00. The star-select lane's CONCLUSION is untouched -- an unsupplied
sublevel is still invalid and the scene still walks an uninitialised star count
-- but the sentinel it lands on is SUBLEVEL_LEVEL_TABLE[-1], one byte before the
table, not the table's index 0. (Index 0 IS 0xff, which is where the confusion
came from; the same read gives [6] = 0, Bob-omb Battlefield, which is what the
star-select run prints.) The comment in hal/scene_boot.cpp is corrected in
place; port/scene_boot_map.txt is not this lane's file and is flagged instead.

A THIRD CAVEAT NOBODY HAD WRITTEN DOWN, found by running it. Scene::SetFaders
is called by dScDSMT_c::InitResources and by NOTHING dScStarSel_c does, so this
lane is the first caller in the port's history, and it opens
`if (data_0209f5bc) { data_0209f5bc->vt->f14(...); }`. hal/fader_wipes.cpp
PRE-SEATS that word to &hal_wipes[0] because two level-path functions deref it
with no null check. config/arm9/symbols.txt has data_0209f5bc as kind:BSS, so
the DS clears it at boot and the ROM's own guard is FALSE at title time; the
pre-seat is a level-path invention that makes a ROM `if` take a branch the real
machine does not. port_scene_run restores the zero before spawning, prints that
it did, and routes the real fix (ROM-shaped vtables on the wipe objects) to the
fader lane.


4. THE BOOT, AND WHAT IS PROVEN
--------------------------------

TWO RUNS, AND THEY ARE KEPT APART ON PURPOSE. An earlier version of this
section printed ONE transcript carrying both the fault and the "spawned" and
"tree root" lines. THAT BLOCK WAS NOT REPRODUCIBLE and it is the kind of error
this whole file is supposed to be proof against: on the bare run the fault
happens INSIDE Scene::SpawnIfNecessary, and port_scene_boot prints "spawned"
only after that call RETURNS, so those two lines cannot exist in a bare run's
output. They were the SLOT0=0 run's. Every fact the old block asserted survives
-- review re-derived from the ROM that func_020433b8's tree insert really does
precede the slot-0 dispatch in func_02043098's spine, so the scene IS the root
by the time InitResources runs -- but the two runs print different things and
are now shown printing them.

RUN A, THE BARE ONE. This is what the battery runs and what SCENE_BLOCKED
checks. walk_window.exe, SM64DS_SCENE=1 SM64DS_SCENE_FRAMES=300

THERE IS NO "spawned" LINE AND NO "tree root" LINE IN RUN A, and that absence

RUN B, SM64DS_SCENE_SLOT0=0 ADDED. Same command otherwise, stdout, verbatim,
also exit 0xC0000005 but for the different reason in section 5:

      [scene] 2 scene classes registered (ov003, ov007)
      [scene] sublevel NOT written (SCENE_TITLE does not read data_02092110;
              0 relocations from ov007). It holds -1.
      [scene] 1 = SCENE_TITLE
      [scene] spawned 307FFF9C, vptr 00BAEB08
      [scene] tree root 307FFFB0, scene node 307FFFB0 (the scene IS the root),
              pending id 0x187, latch 1

READ THE "tree root" LINE, NOT THE "spawned" ONE, for the same reason the
star-select write-up gives: "spawned" only says an object exists. What says the
chain is LIVE is func_0203b438's no-parent branch having written the scene's own
SceneNode into data_020a4b6c[0], and on a level run that slot holds the Stage.
The pending id 0x187 and latch 1 are Scene::SpawnIfNecessary's own bookkeeping,
so a second call would decline: the scene spawns exactly once.

WHY RUN B IS EVIDENCE ABOUT RUN A, since it is a different run with a slot
switched off. The two differ ONLY in slot 0's contents. Everything run B prints
happens BEFORE slot 0 is dispatched -- the registry seat, the factory, the tree
insert -- so run B is a direct readout of run A's state at the moment slot 0 is
entered. What run B cannot speak for is anything after that point, and it does
not: its own fault is in the Render, on an object InitResources never touched.

WHAT IS PROVEN, precisely, and it is most of the seat:

  - the registry cross-check passes: the mounted SpawnInfo's +4 halfword reads
    back 1, the id the arm9 spawn table indexes it by;
  - Scene::SetSceneToSpawn -> Scene::SpawnIfNecessary -> func_02013edc ->
    func_02042fe4 -> func_02043098 ran, all matched arm9, the port adding
    nothing to the chain;
  - the ROM's own factory ran and returned an object whose vptr is the filled
    mount array;
  - the object became the scene tree root;
  - SLOT 0 WAS DISPATCHED. The fault is INSIDE func_ov007_020cc4c0, three calls
    down, not before it. The eighteen-slot fill and the +0x50 sub-object vptr
    are exercised, not merely written.

WHAT IS NOT PROVEN: everything after InitResources. No frame completed, the
Behavior never ran, the Render never ran, nothing was drawn, and the 2D
questions port/ov004_ov007_2d_map.txt section 7 asks about ov007 are exactly as
unmeasured as they were before this lane. NOBODY HAS SEEN A TITLE-SCREEN PIXEL.

THAT IS THE WHOLE STORY. ov007 has 548 functions and 528 have a matched src TU.
func_ov007_020c9688 (0x020c9688, 768 bytes) is one of the twenty that do not:
there is no C for it anywhere in the tree, config/arm9/overlays/ov007/delinks.txt
has no block covering its address, and no src file mentions it except its caller
src/func_ov007_020b6d40.c. hal/scene_boot.cpp stands a NAMED TRAP there rather
than a plausible body, because a plausible body is exactly the guess
port/tools/inferred_stub_guard exists to refuse. func_ov007_020b6d40 hands the
trap's 0 upward and func_ov007_020ade58 dereferences it at +0xc.

THE FIX IS A DECOMP, NOT A PORT CHANGE. Nothing in hal/ can make this run.

TWENTY-FOUR TRAPPING SITES ARE STANDING, all named in hal/scene_boot.cpp
section 3, and they count as 23 L2_UNMATCHED bodies (19 ov007, 4 arm9/itcm/
cross-overlay) plus the twelve slots of data_0208ea6c, which all point at one
shared trap and are the 24th site rather than twelve more. The run reports how
many were entered so "none of them fired" is a measurement.

ONE UNMATCHED ov007 FUNCTION HAS NO TRAP AND THAT IS CORRECT.
func_ov007_020c49bc (0x020c49bc, 0x440 bytes) has no C either, so ov007's
unmatched count is TWENTY and the trap list covers nineteen of them. Nothing in
the 619-TU slice references it, so the linker never asks for the symbol and a
trap would be a definition with no caller. The omission cannot go quiet: a
future slice that reaches it fails the link with an unresolved external.

In run A above, three sites fired:

    func_ov007_020c9688       6   the blocker
    func_02054c80             1   an arm9 address with no symbol and no C
    data_0208ea6c slot        1   a dispatch through a hosted arm9 vtable this
                                  lane trap-filled rather than leaving raw

The other twenty were not reached. THE data_0208ea6c HIT IS ITS OWN FINDING and
is the reason trap-filling was chosen over ROM bytes: something really does
dispatch through the +0x54 member's vtable, and had it been left carrying raw
DS addresses the run would have jumped to 0x02017254 interpreted as a host
address instead of saying so. Three of that member's four tables are now
trap-filled here (data_0208ea6c, data_0208eacc, data_0208eb2c) and the fourth,
data_0208eafc, still ships raw ROM bytes because nothing asked for it. FILLING
THEM FOR REAL IS TWELVE MORE BODIES PER TABLE AND IS NOT THIS LANE'S.

WHAT WAS TRIED AND REFUSED. SM64DS_SCENE_SLOT0=0 exists as the direct analogue
of the star select's SLOT9=0 and it does NOT make a battery entry: with
InitResources no-op'd the Render faults instead (func_ov007_020cc2b0 ->
func_ov007_020b7040 -> func_ov007_020bcf90, accessing 0x00000004), which is what
an uninitialised object should do. A skip that green-lit that would have been a
green over nothing. The knob stays for diagnosis and the scene goes in
port/tools/battery.py's new SCENE_BLOCKED table instead -- which is STRICTER
than a skip, not weaker: it asserts the blocker is still there, fails the
battery if the scene fails for any OTHER reason, and prints BLOCK RETIRED the
day the bare run completes.

TWO EARLIER FAULTS WERE FIXED RATHER THAN RECORDED, and both are worth reading
because both are traps the next lane will meet:

  a. A CALLING-CONVENTION MISMATCH DRESSED AS A VTABLE BUG.
     `?SetFaders@Scene@@QAEXPAUFaderBrightness@@@Z` is __thiscall and the
     matched TU defines a __cdecl function with one stack parameter. An
     /alternatename between them LINKS, and then the callee reads the stack
     argument as `this`: InitResources calls it with this = self+0x54 and
     fb = self+0x50, so the body ran against self+0x50, whose vptr is the
     FOUR-slot graphCallback_c table, and dispatched slot 9 of it -- eight
     words past the end, into the RTTI name string at 0x021032c0. The fault
     read eip 0x61226c6c accessing 0x61626c6c, which is the bytes "llba" out of
     "graphCallback_c", and it looked exactly like a mis-sized vtable. AN ALIAS
     CANNOT CHANGE A CALLING CONVENTION. Where the conventions differ the answer
     is a face that re-lands the arguments, which is hal/scene_actor_faces.cpp's
     veneer lesson in a new dress.
  b. SIX MORE MOUNT WORDS THAT ARE DISPATCHED. port/ov007_binding_diff.txt
     section 3 counts eighteen pointer words the mount leaves holding DS
     addresses and asks "is it dereferenced" of each. THE ANSWER FOR ALL
     EIGHTEEN IS NOW YES: 7 are the class vtable's own slots, 2 the
     graphCallback table's, 1 the SpawnInfo factory word, 6 are
     data_ov007_02103290 (a graph-callback table InitResources passes to
     func_ov007_020b7138 as an ARGUMENT, which is why no vtable sweep would
     find it) and 2 are data_ov007_02103254 / _02103258. All eight of the last
     group are filled by scene_fill_title now. The one that caught it was a
     fault at eip 0x01cccab4 accessing 0x020ccab4 -- func_ov007_020ccab4's DS
     address dispatched as a host one.

    0042ED4B  push edi              <- an ARGUMENT
    0042ED50  call 00425C40            func_ov007_020ae834
    0042ED58  add  esp,8            <- and it IS cleaned

The same instruction, `push`, twice, and the epilogue tells them apart. A save
is never cleaned and is followed by the function reading its own frame; an
argument is cleaned by the caller because this is cdecl. add3c has only the
first kind before its call, and that is the whole defect.

ONE REFINEMENT ON THE REVIEW'S VERSION OF THIS, re-derived rather than
restated: the review described the cleanup as `add esp,4`. In this build it is
`add esp,8` at 0042ED58, because MSVC coalesced the cleanup for TWO argument
pushes -- 0042ED3F's and 0042ED4B's, feeding two different calls -- into one
adjustment. Four or eight does not touch the point (arguments get cleaned,
saves do not), but the listing is what it is.

AND THE SLOT HAS A NAME. Walking the pushes with the caller's frame pointer at
X, the same way 5b walks its seam:

    push ebp      [X]      add3c's saved ebp
    mov  ebp,esp  ebp = X
    push esi      [X-4]    add3c's SAVED ESI
    call          [X-8]    return address
    push ebp      [X-12]   ae558's saved ebp, and ae558's ebp = X-12

so inside ae558, [ebp+8] is X-4 and is add3c's saved esi. THE IDENTICAL FAILURE
SHAPE AS THE SEAM THIS LANE JUST RETIRED: a saved register read as an argument,
not a data seam and not a relocation.

THE ARITHMETIC CLOSES TRIVIALLY, and trivially is the point. The faulting
instruction is a bare `mov ecx,[ebx]` with no displacement and no index, and
the fault reports accessing 000000a4, so the accessed address IS the garbage
slot's contents. There is nothing to reconstruct. Deterministic across four
runs: same offset, same accessed address, every time.

AND THE GARBAGE HAS A MEANING, WHICH THE REVIEW SUPPLIED AND THIS LANE HAD NOT
LOOKED FOR. 0xA4 is not arbitrary. src/func_ov007_020aed98.cpp ends in three
loops over data_ov007_0210342c, and the middle one is

    for (i = 0; i < 9; i++)
        func_ov007_020add3c(*(int*)(gg + i * 4 + 0xa4));

so the caller walks 0xA4, 0xA8 ... 0xC4 and stops where the next loop's 0xC8
begins. MSVC keeps that running byte offset in esi. add3c's `push esi` is
therefore saving THE LOOP COUNTER, ae558 reads that slot as `self`, and 0xA4 is
the value on ITERATION ZERO. THE FAULT IS THE FIRST ITERATION: add3c has never
completed once.

THE FAULT REPORT CORROBORATES IT IN THE REGISTERS, which is the part that makes
this a measurement rather than a story. The probe prints

    ebx=000000a4  esi=000000a4

ebx is the value ae558 loaded out of [ebp+8] and esi is the live register it
inherited. THE SAME NUMBER IN BOTH, from the caller's frame and from the
register file at once, is what proves the stack slot IS the saved esi rather
than merely resembling it.

THIS IS WHAT PROVES THE RULING BELOW, and it is a stronger argument than the
one this lane wrote before the review. Because the forwarded value CHANGES ON
EVERY ITERATION -- nine different pointers out of nine different slots -- no
host copy of the callee supplying a constant could be right more than once. The
value has to come from the caller. That is not a preference between two
defensible seats; it is the only seat that can work.

registers set, and it books as `load` because the pool word is what carries the
relocation. ADDRESS-TAKEN AND TAIL-BRANCHED ARE THE SAME RELOC KIND AND

is to read the instruction at the `from` address: a pool word feeding a `bx` is
a call, a pool word feeding a store into a table is not.

not depend on arity at all. It depends on whether MSVC gave the frame that

    `bx ip` and `bl`-with-live-registers exactly, and the value arrives

5F'S OPEN QUESTION IS ANSWERED AND THE FRAME HAS A PICTURE IN IT. 5f measured
three colours and said "WHY the ROM's drawing does not land is the next
question on this path and no lane has opened it". The answer is three port
seams stacked on one path, none of them a decomp hole, and with all three
closed the same 300 frame run produces 472 distinct colours.

NOTHING HERE WAS GUESSED BEFORE IT WAS MEASURED, and the instruments were
already in the tree. port/ntr/ppu_audit.cpp (Stage 3 lane W2D, write up in
port/ppu_gap_audit.txt) samples both engines' whole 2D register file, the OAM

READ THAT TABLE BEFORE READING ANY EXPLANATION OF IT. The assets ARE loaded,

WHAT PROGRAMMED THAT STATE, from the ROM's own matched sources. Every register
above is written by one function, src/func_ov007_020b7138.c, which
dScDSMT_c::InitResources calls. It runs func_ov007_020bd648(1), whose SECOND
switch is

    case 1:
      DISPCNT     = (DISPCNT     & ~0x1f00) | 0x1b00;
      DISPCNT_SUB = (DISPCNT_SUB & ~0x1f00) | 0x1c00;

and then, thirteen statements later, undoes it:

    G2x::SetBlendBrightness(0x4000050, 0x3f, -0x10);   BLDCNT 00ff, BLDY 0010
    G2x::SetBlendBrightness(0x4001050, 0x3f, -0x10);
    *(u32 *)0x4000000 &= ~0x1f00;
    *(u32 *)0x4001000 &= ~0x1f00;

That is correct ROM behaviour and not a defect: the title screen comes up black
with every layer off, behind a fade, and something later turns it on. The BGxCNT
values in the table are bd648's own case 1, which is how this lane knows bd648
ran at init at all.

WHAT WAS MEANT TO TURN IT BACK ON. The last call in that chain,
func_ov007_020b6544, sets data_ov007_0210342c->f1c = 1, a PENDING GRAPHICS MODE.
Its only reader is src/func_ov007_020b6eb4.c, and that function is reached from
exactly one place: dScDSMT_c's graphCallback_c slot 2.

    src/func_02019144.c, the ROM's once per frame display sync, called from
    IRQ::VBlankHandler, OPENS with

        UnkObj *p = data_0209d4a8;
        if (p != 0) { if (p->vt->func8(p) == 0) return; }

    and dScDSMT_c::InitResources parks its own graphCallback_c sub-object
    there (`data_0209d4a8 = self + 0x50`). Slot 2 of that block's table is
    func_ov007_020cc0f4, and that is the ROM's own relocation rather than a
    reading of the port's seat: config/arm9/overlays/ov007/relocs.txt has
    from:0x021032b8 kind:load to:0x020cc0f4 module:overlay(7). cc0f4 calls
    func_ov007_020b6eb4 and RETURNS 0.

SO THE TITLE SCREEN SUPPRESSES THE FRAMEWORK'S DISPLAY SYNC AND DOES ITS OWN,
which is the fact every seam below turns on. func_02019144's tail (OAM::Flush,
OAM::Load, both layer mask publishes, the eight BG scroll registers) does not
run on this scene at all. func_ov007_020b6eb4 replaces it: the fade beat
(func_ov007_020bf690), the display capture (func_ov007_020bd4e8), the layer
setup (func_ov007_020bd648 with the pending mode) and its own OAM upload
(func_ov007_020b72a0 to func_ov007_020b7384, which is func_020566dc and
func_02056674 writing 0x400 bytes each to 0x07000000 and 0x07000400, both
engines' OAM) plus its own BG map uploads and scroll writes
(func_ov007_020c03b0 to func_ov007_020c076c). The Render slot BUILDS the two
OAM shadow buffers every frame (func_ov007_020bc9c8) and the callback UPLOADS
them. Render also sets data_ov007_02103430, the flag b6eb4's whole body is
gated on, so the two halves are one mechanism.

  B. THE PENDING MODE IS DROPPED BY AN ARM REGISTER RIDE THROUGH.

     screened this exact row as a candidate and named this exact frame as the

  C. THE PORT RAN THE TAIL IT SHOULD HAVE SKIPPED. Stage 5 lane VP1 correctly

GAP ONE: THE PROJECTION MATRIX HAS A ZERO X SCALE
--------------------------------------------------

THE MEASUREMENT FIRST, off the START COMMIT binary, last frame of 300:

    triangles   96
    drawable    0      (on-screen and not degenerate)
    offscreen   0
    degenerate  96
    bbox        x 256.000 .. 256.000   y 137.880 .. 223.766
    proj          0.000000     0.000000     0.000000     0.000000
    proj          0.000000     3.748047     0.000000     0.000000
    proj          0.000000     0.000000    -1.005127    -1.000000
    proj          0.000000     0.000000    -2.005127     0.000000

READ THE BOUNDING BOX BEFORE ANY EXPLANATION OF IT. Every vertex of every
triangle is at x 256.000 on a 512 wide framebuffer, and y is spread normally.
That is not off-screen geometry and it is not a culled frame: it is clip x = 0
for every vertex, which is what a projection whose first ROW is zero does and
nothing else does. The rest of the matrix is a correct G3i::PerspectiveW_
result -- proj[5] the cotangent, proj[10] and proj[14] the depth row, proj[11]
the W scale -- with one term missing.

5H'S THREE CANDIDATES ARE ALL WRONG AND THE CENSUS RETIRES THEM BY NAME.
VIEWPORT_SETS 0 is real and is not the cause: ntr::gx_reset restores a
full-screen rectangle and the census reads VIEWPORT_W 512 VIEWPORT_H 384 on all
300 frames, so the geometry has the whole panel to land on and lands on a line
anyway. SWAP_BUFFERS 0 is real and is not the cause either; the port renders
from the assembled list rather than from a latched buffer. And gx_reset
throwing the matrix state away once a frame is not the cause: PROJ_IDENTITY
reads 0 on all 300 samples and PROJ_FP is the same fingerprint on all 300, so
the projection is REBUILT every frame and the reset costs nothing.

THE ARGUMENT ARRIVES ZERO. With the flight recorder off, the host copy at
port/unmatched/G3i_PerspectiveW.cpp reports its own inputs:

    [persp] sin=1056 cos=3958 aspect=0 n=4096 f=1638400 scaleW=4096 flag=1
            -> cot=15352(3.7480) xx=0(0.0000)

cot 15352 is 3.748047, which is the proj[5] in the table above, so this is the
call that built the live matrix. `xx` is mtx[0] and it is a division of the
cotangent by `aspect`. The host stack, resolved against walk_window.map:

    G3i::PerspectiveW_
      func_ov007_020c0078        the title's own perspective setup
      func_ov007_020b1fa4
      func_ov007_020b0a20
      func_ov007_020aed98
      func_ov007_020cc4c0        dScDSMT_c::InitResources

and the same binary's OTHER PerspectiveW_ caller, the ROM's generic
Initialise3dGraphics, passes aspect 5461 on the same boot and gets it right.
5461 is 0x1555, which is 4/3 in 20.12. So the port can carry an aspect; the
title's own one is zero.

WHERE THE TITLE'S ASPECT COMES FROM, out of the matched sources.
src/func_ov007_020c0078.c reads it as

    (int)(*(long long*)(c + 0xbc) >> 0x14)

and src/func_ov007_020c0128.cpp, which func_ov007_020b1fa4 calls at its head
(line 12, against the c0078 call at line 45 of the same function, with the
switch between them), is the only writer of that field:

    long long l = _ZN4cstd4ldivEii(0x4000, 0x3000);
    *(int *)(c + 0xbc) = (int)l;
    *(int *)(c + 0xc0) = (int)(l >> 32);

0x4000/0x3000 is 4/3, cstd::ldiv returns (a << 32) / b, and (4/3 << 32) >> 20
is 0x1555. The ROM's aspect is the same 5461 by construction. The port's was 0
because cstd::ldiv RETURNED A DEAD WORD.

AND THAT IS THE DEFECT, one raw MMIO caller and not a graphics bug at all.
src/_ZN4cstd10fdiv_asyncE5Fix12IiE5Fix12IiE.c reaches DIVCNT, DIV_NUMER and
DIV_DENOM through plain literal-address stores and src/_ZN4cstd4ldivEii.c reads
DIV_RESULT the same way. ntr maps real memory across the DS I/O window, so
those stores latch in ordinary memory and ntr::run_divide is never entered --
the identical shape port/tools/hostgen.py's own header records for MTX_SCALE
("it latches, the geometry engine never sees it"). Both translation units were
compiled RAW.

THE FIX IS THE TREATMENT THE PORT ALREADY USES FOR THIS, and it costs nothing
in the ledger. port/CMakeLists.txt routes both through hostgen.py, which
rewrites the derefs to NTR_MMIO and so through ntr::io_write; src/ is not
edited and the two matched TUs stay matched, exactly as
_ZN4cstd11fdiv_resultEv, _ZN4cstd4sqrtEy and Camera::Render are already
handled. The plain slice entries are cut in the same block that adds the
generated ones, with a count guard. THE GUARD IS A message(STATUS) AND NOT A
REFUSAL, so read it as a signpost rather than a net: the real net is the
LINKER, which answers a slice that stopped listing one of them with an
undefined symbol and a slice that started listing a third copy with a duplicate
one. The message exists so a reader looking at a failed link knows which block
to look at first, which is what the CMakeLists comment beside it says.

THE BLAST RADIUS IS ONE CALLER AND IT WAS SWEPT RATHER THAN ASSUMED.
cstd::fdiv, the divider's other client and the one every level uses, is a HOST
FACE in port/hal/cstd_div.c and src/_ZN4cstd4fdivEii.c is not in the link at
all (the map has __ZN4cstd4fdivEii from cstd_div.c.obj). cstd::ldiv's only
caller anywhere in src/ is func_ov007_020c0128, and fdiv_async's only callers
are cstd::fdiv and cstd::ldiv. The only live path this changes is the title
screen's camera init.

is not "why did nobody write the map" but "why was the buffer empty", and the
second row answers it on its own: THE SOURCE IS 0x02104598, A DS ADDRESS. The
port hosts that global in .dsstate, and the MultiCopy32Bytes census shows the
real buffer being filled at the same moment, at the HOST address:

    00c75fac -> 00c76bac  1536 bytes  srcnz 1533  x1
    00c75fac -> 00c765ac  1536 bytes  srcnz 1533  x1

0x00c76bac is hosted data_ov007_02104598 (the offsets check: 0x00c76bac minus
0x00c75fac is 0xC00, and 0x02104598 minus 0x02103998 is 0xC00). So
src/func_ov007_020b8548.c fills the buffer through func_ov007_020c0308 and
copies it exactly as the ROM does, and the upload then reads a different
address entirely.

THE ROW, AND IT IS A DECOMP DEFECT RATHER THAN A PORT ONE. Three one-line
matched translation units spell a relocated ROM word as a bare decimal:

    src/func_ov007_020b84e8.c   return 34617752;   0x02103998
    src/func_ov007_020b84f4.c   return 34619288;   0x02103f98
    src/func_ov007_020b8500.c   return 34620824;   0x02104598

THE ROM SAYS THEY ARE ADDRESSES, not constants, and says it three times.
config/arm9/overlays/ov007/relocs.txt:

    from:0x020b84f0 kind:load to:0x02103998 module:overlay(7)
    from:0x020b84fc kind:load to:0x02103f98 module:overlay(7)
    from:0x020b8508 kind:load to:0x02104598 module:overlay(7)

Each of those three source addresses is the literal-pool word of the
corresponding accessor, and each carries a RELOCATION to the data symbol. A
relocated word is an address reference by definition; the decimal spelling is
byte-identical on ARM and loses the reference. src/func_ov007_020adc08.c then
stores the result into the BG node's buffer pointer:

    case 6:
      *(int*)(obj+0x10) = func_ov007_020b8500();

and func_ov007_020c076c uploads obj+0x10 into the screen base.

THE PROPOSED CRACK IS THREE LINES AND SHOULD STILL MATCH:

    return (int)&data_ov007_02103998;      in func_ov007_020b84e8
    return (int)&data_ov007_02103f98;      in func_ov007_020b84f4
    return (int)&data_ov007_02104598;      in func_ov007_020b8500

mwccarm emits the same `ldr r0, =X / bx lr` either way and the relocation is
what the ROM already has, so this is a spelling correction rather than a
rewrite. THIS LANE DID NOT TAKE IT. Matched TUs are read-only to it and a
three-way displacement into port/unmatched/ would cost three linked rows and
needs a ruling; the row is routed with the evidence instead.

8a. THE TAIL-JUMP FLOOR IS GUARDED (run link60 Stage 5 lane TJG)
-----------------------------------------------------------------

SECTION 8'S "NOTHING GUARDS IT" IS STRUCK AND THIS IS THE CITATION. The tool
is port/tools/tailjump_guard.py. It runs twice in port/build-port.cmd: its
fixture battery before configure, its map check after link, over EVERY map in
the build directory rather than walk_window's alone, for gxband_guard's
reason -- /MAP is on CMAKE_EXE_LINKER_FLAGS and three targets host this slice.

WHAT IT ASSERTS. For each classified frame it reads that frame's own byte span
out of the linked image, at the address the map published, and looks for two
five-byte forms whose four displacement bytes resolve EXACTLY to the callee's
address: E8 rel32, a near call, and E9 rel32, a near jump. No disassembler, so
nothing can desynchronise on the data islands 5d already got bitten by.

    CLASS A      7 frames   must contain an E8 to the callee and NO E9
    CLASS C      5 frames   must contain an E9 to the callee and NO E8
    VENEER      22 frames   the same, and DERIVED rather than listed

    32 distinct frames (two are in both the hand Class C list and the derived
    veneer set, and the guard cross-checks that the two name the same callee
    AND the same form, refusing if either disagrees). 96 assertions on this
    tree, over smoke_player, walk_window and walk_window_hires. Those 32
    frames are 16 distinct byte spans per map, not 32, because ICF folds the
    seventeen c3d1c veneers onto one address; the unproven-items list below
    carries what that does and does not cost.

    THOSE ARE TJG'S NUMBERS AND THE TREE HAS MOVED BELOW THEM TWICE. Every
    number in this section that says 96 or "all 32 frames" was true when TJG
    wrote it and has been moved twice since, in the same way and by the same
    mechanism: a DISPLACEMENT RETIRES A ROW. The guard refuses to assert
    anything about a frame whose matched TU is not the thing the binary
    compiled, and it says so by name rather than falling silent. The
    arithmetic is the three HOSTING maps named above, one assertion each, so a
    retirement takes 3 off the total. (The guard's own line says "over 21
    map(s)", which is how many maps it SCANS, not how many host these frames.)

        TJG      32 frames asserted   96 assertions   RETIRED 0
        AE1      31                   93              RETIRED 1  add3c
        TS1      30                   90              RETIRED 2  add3c, b6eb4

    The 93 and the 90 are both read off the guard's own line in this lane's
    own two builds, the base one at 7f994ccdb and the tip one, not carried
    from a review.
    AE1's move was already unrecorded here when this lane arrived; recording
    both is cheaper than recording one and leaving the other for the next
    reader to rediscover.

    THE b6eb4 ROW IS LEGITIMATELY OBSOLETE AND NOT SUPPRESSED, which is the
    distinction that matters for a guard. The row asserted that the frame's
    call to func_ov007_020bd648 compiles to an E8 and never an E9, because on
    a tail jump the ROM's r0 would ride into the callee and the port's would
    not. Section 5h displaces the frame: port/unmatched/Ov007_BdPending_-
    020b6eb4.cpp SPELLS the argument, so the value arrives in a push and no
    longer depends on the call's form at all. There is nothing left for the
    assertion to protect. The guard reaches that conclusion by itself, from
    the map, and re-listing src/func_ov007_020b6eb4.c would re-arm it in the
    configure that noticed.

THE UNIT IS THE FRAME AND NOT THE ARITY ROW, which is why the guard can be
exact where this file has to say "roughly fifty". A row is a (declaring TU,
callee) pair and counting those means tokenizing C declarations, which is what
produced 5d's 49-versus-46. A frame is a linker symbol. The 22 veneer frames
cover every one of those rows whichever tokenizer is right, because the
property belongs to the frame: if the veneer tail-jumps, all of its callers
ride through, and if it does not, none of them do.

THE VENEER SET IS DERIVED ON EVERY RUN, not written down. The guard scans
extracted/overlays/overlay_0007.bin at base 0x020ad660 for the three-word shape

    E59FC000   ldr ip, [pc]
    E12FFF1C   bx  ip
    <target>

and resolves both ends against config/arm9/overlays/ov007/symbols.txt and
config/arm9/symbols.txt. It finds 22, which is 5d's number, and 17 of them
target _ZN6Player17St_EndingFly_MainEv, which is also 5d's. The 22 is DECLARED
as a tripwire: a different count REFUSES rather than asserting a different set
than the one written down. Two of the 22 leave the overlay, to Deallocate and
LoadFile.

THE MEASURED SEPARATION IS PERFECT AND THAT IS THE EVIDENCE THE METHOD WORKS.
Every one of the 32 frames on this tree returns exactly one hit of the form its
class requires and ZERO of the form it forbids. Not one frame is ambiguous, and
that reproduces the review's twelve-row proof of concept and extends it to 32.
(32 WAS THE COUNT WHEN TJG MEASURED IT. Two of those frames are displaced now
and the guard retires them rather than asserting; 30 are asserted on today's
tree. The separation claim is unaffected, because a retired row is one the
guard declines to read, not one that came back ambiguous. See the correction
block above.)

THE BREAK-PROOF, ON REAL BUILDS RATHER THAN FIXTURES. Three mutations, each
built, each observed, each restored byte-identical (sha256 checked, git clean):

  1. A STATEMENT ADDED BEFORE THE CALL DOES NOT BREAK IT, and this is the
     correction to 5d. src/func_ov007_020aef78.c is a one-line forwarder to
     func_ov007_020b9640. A `static volatile int` store inserted BEFORE the
     call left the frame 16 bytes and left the transfer an E9. The guard
     stayed green and it was RIGHT to: MSVC can still tail-jump, because the
     store needs no stack frame and ESP is unchanged at the transfer. So
     "add one statement to any of those forwarders" overstates it.
  2. THE SAME STATEMENT AFTER THE CALL BREAKS IT. The body is no longer a call
     in tail position, MSVC emits the call and then the store, and the guard

         TAIL JUMP LOST: func_ov007_020aef78 -> func_ov007_020b9640
              frame  0042ad00..0042ad10 (16 bytes)
              wanted an E9 rel32 to the callee and NO E8 rel32 to it
              found  1 E8 call (0042ad00)

     build-port.cmd exited 1. 3 frame/map pairs broken.
  3. THE /Od SHAPE IS NOT FIXTURE-ONLY. A throwaway
     set_source_files_properties COMPILE_OPTIONS "/Od" over all 32 declared

     tail-jump frames became real calls in all three targets, 75 frame/map

         THE WHOLE TAIL-JUMP CLASS FLIPPED in walk_window.map -- all 25
         hosted forwarders became real calls. That is not 25 separate
         regressions. One change does this: the optimisation level.

     ON THE SINGLE-TU /Od the E8 sits at frame+3, after `push ebp / mov
     ebp,esp`, which is the real-prologue signature 5d predicted, and the
     tail-jump build's E8-free frame is what it replaced.
     AND THE BOTH-SIDES DISCIPLINE HELD UNDER IT: /Od never turns a call into
     a jump, so all seven Class A rows stayed green through the flip. 75 is
     25 x 3 exactly, with zero SEAM IS NO LONGER A CALL.

THE add3c ROW SURVIVES ITS OWN SEAT, MECHANICALLY. Class A row 1 is
func_ov007_020add3c, which is being displaced by another Stage 5 lane while
this guard was written. Every row declares the SOURCE that must have produced
its frame's object, and the guard reads back whether it did: the map's
Lib:Object column says which object defines the frame, and the build
directory's build.ninja says which source produced that object. If the source
is not the declared one the row RETIRES -- named and counted on the guard's own
output line, never silently -- and putting the matched TU back re-arms it in
the same build. No hand edit either way.

AND A MISTYPED tu IS NOT A RETIREMENT, which the review had to point out. A
`tu` retyped to ANOTHER REAL src/ FILE used to disarm its row at exit 0: it was
named on the green line, but it read as a legitimate retirement rather than as
the typo it is. The two are now told apart by where the source the build REALLY
used lives, which is a fact rather than a convention. A displacement moves a
frame OUT of the decomp, to a host copy under port/; a typo moves nothing, and
the build is still compiling src/ or hostgen's rewrite of it for that frame.
Real source still decomp source and not the declared one is a MISDECLARED ROW
and fails the build.

THE COUNT PIN THE REVIEW OFFERED WAS THE OTHER WAY TO CLOSE IT AND IT IS THE
WRONG ONE HERE, said plainly because it was the reviewer's own suggestion.
Pinning the expected assertion count, or asserting zero retirements on a clean
tree, would make the ae558 seat fail the build on the day it merges, until
somebody hand-edited this guard to accept the one retirement the whole
mechanism exists to produce. The discriminator above asks the question the
count was standing in for and stays quiet for a real seat.

IT IS TWO FACTS AND NOT ONE FOR THE REASON port/tools/objsrc_check.py RECORDS:
an MSVC map names an object by its BASENAME ALONE, and this tree has had
eighteen cases where a host copy and a matched TU carried the same basename.
The map alone cannot tell them apart; build.ninja can. That is also 5d's own
ruling about which artifact is the authority on what is compiled, applied to a
different question.

AND IT IS A STRONGER FORM THAN THE PREDICATE IT COPIES. The RT1 and PC2 markers
in port/CMakeLists.txt read a regex over a src/ file plus a CMake variable set
by the cut. Both are build INPUTS: they describe what the build was asked to
do. This reads the linked map and the generated build.ninja, which are what the
build DID, so a configure that silently failed to apply a cut satisfies the
CMake predicate and fails this one.

WHAT LANE TJG DID NOT DO, AND WHAT THE GUARD DOES NOT PROVE

  - NO SEAT, NO SLICE EDIT, NO CMAKE CHANGE THAT SHIPS. The gate at this tip is
    the gate at the start commit: 5833/11250 (51.8%), ALL GREEN, the one ae558
    skip, delta 0. The two throwaway edits above were restored and verified by
    sha256, not by eye.
  - IT PROVES THE SHAPE SURVIVED, NOT THAT THE SHAPE IS CORRECT. Whether the
    argument riding through a given tail jump is the right argument is 5d's
    reading of the ROM and this guard takes it as given. It is a regression
    guard on a measured property, not a re-derivation of the classification.
  - THE 32 IS NOT THE ~50. The mapping from frames to arity rows is 5d's and
    stays method-dependent. What is exact is the frame count.
  - rel8 IS NOT SCANNED. x86 COFF has no 8-bit relocation, so a transfer to a
    separately linked symbol is always rel32 and an EB inside a frame is an
    intra-function branch. Scanning for it would also cost more than it bought:
    one displacement byte matches by accident about once per 65,536 positions,
    which over a 700-byte Class A frame is a false failure roughly one run in a
    hundred.
  - A FIVE-BYTE FORM IS NOT PROVED TO BE AN INSTRUCTION. It is matched only
    when its four displacement bytes resolve exactly to the callee, so a false
    hit needs five specific bytes at one position. That has never fired and the
    hit counts print under --report, but the probability is not zero.
  - ICF CUTS BOTH WAYS AND THE FRAME SIDE IS WHERE THE HEADLINE LIVES.
    /OPT:ICF is on. On the CALLEE side, "resolves to the callee" means
    "resolves to the address the callee shares", so a transfer to a different
    function folded onto the same bytes would read as a transfer to the
    callee; the guard prints the fold count for any callee address carrying
    more than one name so the ambiguity is visible, and cannot remove it. On
    the FRAME side, the 32 declared frames are NOT 32 distinct byte spans: the
    seventeen c3d1c veneers fold onto ONE address in every hosting map, so
    each map reads 16 distinct spans and the 96 assertions are 32 row-checks
    per map over 16 spans rather than 96 independent readings. Measured on all
    three hosting maps, 32 hosted and 16 spans in each. (96 and 32 are TJG's
    numbers; two frames are displaced and retired now and the tree reads 90
    and 30. The span arithmetic is unchanged: neither retired frame is one of
    the folded c3d1c veneers.)
    THIS COSTS THE GUARD NOTHING, and the reason is the folding rule: ICF
    folds only IDENTICAL bodies, so a veneer that grows one statement stops
    being identical to its twins and unfolds into a span of its own. Folding
    is a property of the healthy state and the regression breaks it before the
    guard has to see through it.
    A SECOND NAME AT AN ADDRESS IS ALSO NOT ALWAYS A FOLD. A fired
    /alternatename and MSVC's decorated C++ spelling both publish another name
    at one address, which is the same thing gxband_guard's arm C excuses. The
    guard does not tell an alias from a fold, so a printed fold count is an
    upper bound on how many distinct functions share those bytes.
  - FRAME SPANS COME FROM THE NEXT MAP SYMBOL IN THE SAME IMAGE SECTION. A
    frame is measured from its own map address to the next STRICTLY GREATER
    one, which is what makes the ICF-folded veneers measurable at all, and the
    section scoping is measured rather than tidiness: on this tree's
    walk_window.map the last symbol in each image section is 96 to 4096 bytes
    short of the first symbol in the next, so a globally sorted span would
    hand the last function in .text a 2336-byte window running into .rdata.
    That cannot make a false green -- over-scanning only adds bytes -- but it
    can make a false failure. Where the linker leaves a gap the span still
    includes padding, which is 0xCC and cannot produce a hit. It is a bound,
    not a measurement of the function's real length.
  - CLASS A ROWS 2 THROUGH 7 ARE ASSERTED, NOT VALIDATED. The guard says those
    six frames still emit a real call. It says nothing about whether 5d's
    reading of what they push and what their callees read is right, and no
    Class A row except ae558 has been observed faulting.
  - IT IS ov007 ONLY, exactly as 5d's sweep was. The pooled-load-then-branch
    idiom is a mwccarm idiom and no other overlay was scanned by that lane or
    by this one. The veneer derivation would extend to another overlay by
    adding a spec; nobody has measured what it would find.
  - A DERIVED FRAME WITH NO src/ TU WOULD NOT GET THE RETIREMENT CHECK. All 22
    veneers have a matched TU on this tree, so the count is zero, and where it
    is not zero the guard names those frames on its own green line. What it
    costs when it happens is a loud failure instead of a clean retirement, not
    a false green, because a displaced frame whose form is wrong still fails.
  - THE COVERAGE FLOOR IS THREE MAPS, measured, not reasoned. If the ov007
    slice legitimately leaves a target the floor has to be narrowed by hand
    with the measurement written down, which is gxband_guard's rule and its
    weakness too.
  - NOTHING WAS RUN. Scene 1 still cannot run; this lane added no runtime
    evidence of any kind and every statement above is read off a linked binary,
    a map, a build file or the ROM image.
