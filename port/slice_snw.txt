# ---- 1. THE ROW port/mg_fanout_costs.txt SECTION 3 LEFT BLANK -------------
#
# Twenty-nine of the thirty minigame ids resolve to a vtable through a load
# relocation inside their own factory.  This one does not, and the file said so
# rather than guessing:
#
#   "MgSnowballSlalom (0x179) has a SpawnInfo at 0x0213ffb8 and a factory, and
#    no load relocation inside that factory points at any of the thirty-two
#    signature tables.  Either its factory reaches its vtable through an
#    indirection the other twenty-nine do not use, or its class is one of the
#    three signature tables no id claims.  Whoever takes 0x179 derives it by
#    hand first; the row is left blank rather than guessed."
#
# BOTH HYPOTHESES WERE TESTED.  The first is right, the second is ruled out,
# and neither verdict rests on the handover run mg9 lane LKY left (section 8).
#
# ---- 2. THE FACTORY DELEGATES, AND THE DELEGATE IS THE WRITER ------------
#
# Disassembled from extracted/overlays/overlay_0006.bin at base 0x020bfec0 --
# the shipped image, never a dsd export, whose relocated words would make
# literals read as live pointers.
#
# MgSnowballSlalom_Spawn, 0x0212a520, size 0x34 = 12 instructions plus a
# ONE-word pool = 13 = 0x34/4:
#
#   0x0212a520  stmdb sp!,{lr}
#   0x0212a524  sub   sp,sp,#4
#   0x0212a528  ldr   r0,[pc,#0x20]      ; pool 0x0212a550 = 0x0000c59c
#   0x0212a52c  bl    0x02043444         ; allocate 0xc59c
#   0x0212a530  cmp   r0,#0
#   0x0212a534  addeq sp,sp,#4           ; null -> return it unchanged
#   0x0212a538  ldmeq sp!,{lr}
#   0x0212a53c  bxeq  lr
#   0x0212a540  bl    0x021295ac         ; THE CONSTRUCTOR
#   0x0212a544  add   sp,sp,#4
#   0x0212a548  ldm   sp!,{lr}
#   0x0212a54c  bx    lr
#
# THE HANDOVER CALLED THIS A TAIL CALL AND IT IS A BL.  Run mg9 lane LKY's note
# says the factory "tail-calls a writer".  The effect is what LKY described --
# the factory writes no vtable and the callee's r0 is the factory's return
# value -- but the instruction at 0x0212a540 is a bl followed by a three-
# instruction epilogue, not a b or a bx.  The distinction matters to nothing
# here and is recorded because the next reader will disassemble it.
#
# func_ov006_021295ac, 0xe0 = 45 instructions plus an ELEVEN-word pool = 56 =
# 0xe0/4.  Pool: 0x0000471c, 0x0213e448, 0x0000aba4, 0x0214000c, 0x0000acd8,
# 0x0203d47c, 0x0203d738, 0x0000b5d8, 0x02125800, 0x0000ba14, 0x0212968c.
# Two vtable stores into the object's first word, in inheritance order:
#
#   0x021295c8  str r1,[r4]     r1 loaded from 0x02129664 = 0x0213e448
#   0x021295dc  str r1,[r4]     r1 loaded from 0x0212966c = 0x0214000c
#
# with func_ov004_020b2adc (the base constructor) called FIRST at 0x021295b8
# with the object in r0, then Particle::SysTracker::Initialise at this+0x471c,
# ModelBase at this+0xaba4, and three func_020733a8 sub-object builds at
# +0xacd8, +0xb5d8 and +0xba14.
#
# So the object MgSnowballSlalom_Spawn produces carries data_ov006_0214000c,
# and the indirection section 3 hypothesised is ONE DELEGATED CONSTRUCTOR.
#
# ---- 3. THE ATTRIBUTION CLOSES ON ITSELF ---------------------------------
#
# "An offset match is a candidate; a blx on the loaded word is the finding."
# Four readings of the relocation set, and the last one is a ring:
#
#   a. MgSnowballSlalom_Spawn is the ONLY caller of func_ov006_021295ac in the
#      whole overlay -- one arm_call, from:0x0212a540.  Nothing else builds
#      this object.
#   b. func_ov006_021295ac is the only body that writes 0x0214000c into an
#      object it constructs.
#   c. 0x0214000c has exactly THREE load relocations in all of ov006:
#         from:0x0212966c  in func_ov006_021295ac+0xc0   the constructor
#         from:0x0212571c  in func_ov006_0212568c+0x90   D2
#         from:0x021257dc  in func_ov006_0212573c+0xa0   D0

#      names its own destructors and its own destructors write the vtable.
#      Both also write 0x0213e448 back on the way out -- 0x02125738 and
#      0x021257f4 -- which is the base half of the same unwind.
#
# The two destructors' literal pools hold the SAME five member offsets the
# constructor's does (0x471c, 0xaba4, 0xacd8, 0xb5d8, 0xba14), so all three are
# reading one object layout.  0x0212573c carries one extra pool word,
# 0x020a0eac, and one extra call, 0x0203c1e8 with r1 = *(0x020a0eac) -- the

# ---- 5. FIVE WIDTH CHECKS ------------------------------------------------
#
# The table is THIRTY-SIX words, 0x0214000c..0x0214009c.
#
#   1. SPAN.  The next object begins at 0x0214009c.  0x90 / 4 = 36.
#   2. TERMINAL SLOT.  Slot 35 at 0x02140098 holds 0x020ad660, the word every
#      class in this family ends on.
#   3. WHAT THE WORD PAST THE END IS.  0x0214009c reads 0x2f474d2f, which is
#      ASCII "/MG/" little-endian and the head of the NUL-terminated string
#      "/MG/d_2d_mg_bg_yukidama_ncl.bin".  Not a code address, not in any
#      module's text range, and port/tools/vtablerows.py agrees on its own:
#      "slot 36 word (CANDIDATE only, width says it is not a slot):
#      0x2f474d2f".
#   4. RELOCATION COUNT.  36 load relocations inside the span, and ZERO in the
#      0x40 bytes after it.  A 37th slot would be an unrelocated word.
#   5. RELOCATION STRIDE.  Those 36 sit at a uniform stride of 4 from
#      0x0214000c to 0x02140098 with no gap, so no word inside the span is a
#      plain constant and the count cannot be short at either end.
#
#      The stride check REFUSES AND CONFIRMS ONLY.  Run mg9 corrected it twice
#      (lanes MMT and BOX): it counts gaps, it is not self-calibrating, and it
#      cannot by itself establish a width.  It is the fifth check because it
#      would have caught an over-read, not because it derives the 36.
#
# THE WIDTH WORD IS ALSO AN IDENTITY WITNESS.  The string a 37th slot would
# have eaten is a file THIS CLASS LOADS: src/func_ov006_02129268 (slot 0,
# InitResources) calls func_020adc74(&data_ov006_0214009c).  Three more follow
# it in the same run of strings, and all four are read by that one body:
#
#   0x0214009c  "/MG/d_2d_mg_bg_yukidama_ncl.bin"   BG palette
#   0x021400bc  "/MG/d_2d_mg_yukidama_ncg.bin"      tiles

#   0x021400fc  "/MG/snowman_head.bmd"              the 3D model

# yukidama is Japanese for snowball, and message 554 says the player rolls
