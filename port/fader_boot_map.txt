1. THE CLASS, AND THE ONE THING THE HANDOVER GOT WRONG

MG2's report, port/mg_fanout_costs.txt section 10 and battery.py's old
SCENE_BLOCKED row all describe data_0209f61c as "an arm9 FaderBrightness". It
is a dWipe_c. The ROM says so, in its own RTTI, with config/arm9/relocs.txt
applied to extracted/arm9_dec.bin (flat, base 0x02004000):

    0x020926dc  __si_class_type_info   name "7dWipe_c"           base 0x0208ea00
    0x0208ea00  __si_class_type_info   name "10dFdColor_c"       base 0x0208ea24
    0x0208ea24  __si_class_type_info   name "15dFdBrightness_c"  base 0x0208e9e0
    0x0208e9e0  __class_type_info      name "8dFader_c"
    0x0208ea18  __si_class_type_info   name "9dFdWipe_c"         base 0x0208ea00

    dFader_c <- dFdBrightness_c <- dFdColor_c <- dWipe_c

which is exactly the four vptr stores func_0202fc40 makes, in base-to-derived
construction order, and which also identifies the three sibling tables the port
already hosts by number rather than by name:

    data_0208eafc = _ZTV8dFader_c            hal/scene_boot.cpp:702, ROM bytes
    data_0208eacc = _ZTV15dFdBrightness_c    hal/scene_boot.cpp:693, trap-filled
    data_0208eb2c = _ZTV10dFdColor_c         hal/scene_boot.cpp:688, trap-filled
    _ZTV9FaderWipe (config name) = _ZTV9dFdWipe_c, 0x0208ea9c

NOTHING IN THE HANDOVER'S CONCLUSIONS CHANGES. Every address MG2 gave is right,
including the one that matters most ("a host fill for data_020926f0, which is
NOT _ZTV9FaderWipe"). What changes is what a successor searches for: a lane
told "FaderBrightness" goes looking in the 0x02017xxx fader engine, and none of
the ten bodies is there.

WHY 0x24, off the compiled binary rather than off the C. src/_ZN5Scene9SetFaders
EP15FaderBrightness.cpp declares a local `struct Scene` with ten virtuals and
calls thiz->v24(); MSVC puts that at byte 0x24, which under the ROM fader slot
order is SetToStart. The first 0x27 bytes of the host function, disassembled
out of walk_window.exe:

    +0x00  push ebp / mov ebp,esp
    +0x03  mov  ecx, [0xc0999c]           data_0209f5bc, the INSTALLED fader
    +0x09  test ecx,ecx / je +0x74        the ROM's own null guard
    +0x0d  mov  eax, [ecx]                its vptr
    +0x0f  push esi                       the callee-save, NOT an argument
    +0x10  push ecx                       CDECL: receiver on the stack
    +0x11  mov  eax, [eax + 0x14]         IsAtStart, by ROM byte offset
    +0x14  call eax
    +0x19  test eax,eax / je +0x36
    +0x1d  mov  esi, [ebp + 8]            thiz, the NEW fader
    +0x20  mov  ecx, esi                  THISCALL: receiver in ECX
    +0x22  mov  eax, [esi]                its vptr
    +0x24  call dword ptr [eax + 0x24]    SetToStart
    +0x27  mov  [0xc0999c], esi

THIS PINS THREE THINGS AT ONCE. It is the fault instruction, byte for byte. It
shows the two calling conventions of section 7a in eleven instructions. And it
says what had to be true for the fault to happen at all: execution reached
+0x24, so data_0209f5bc was non-null AND its IsAtStart returned true, which
means the fault is on the NEW object and not on the installed one.

WHICH ALSO SETTLES WHICH SLOT THE AFTER RUN EXERCISES. hal/scene_boot.cpp
resets data_0209f5bc to 0 before the spawn, so dScMgBase_c slot 1's own
SetFaders is not the first: Scene::BeforeInitResources runs before it and
installs the gate-31 colour fader (a real HalFaderWipe at data_0209f5e8). By
the time slot 1 calls SetFaders the guard is true, IsAtStart answers true, and
+0x24 dispatches. The BEFORE binary died on that instruction; the AFTER binary
runs through it into +0x27 and on into InitResources. So slot 0x24 of this
seat IS dispatched, and that is the measurement rather than an inference from
the fill being present.

AND "SLOT 0x08 HAS NO CALL SITE IN THIS IMAGE" WAS A STATEMENT ABOUT THE
BINARY THAT GOT READ AS ONE ABOUT THE GAME. Section 9a swept walk_window's own
.text. That is the right sweep for an ABI audit, which is what 9a is, and the
wrong one for a reachability ruling: a ROM caller that is in no slice cannot
appear in a sweep of the host image, so the sweep could only ever return the
callers the port had already seated. What the ROM does, read out of
config/arm9/relocs.txt and the arm9 disassembly rather than out of the map:

  * _ZN7dWipe_c11AdvanceFadeEv has EXACTLY ONE reference in the whole ROM,

    is reached through the vtable or not at all.
  * The ROM's frame phase 2 is func_02019390, and it calls TWO fader advances:

        func_0202345c();
        func_02018efc();     data_0209d4ac, the INSTALLED fader
        func_02018ec0();     data_0209d4b0, the fader IN MOTION

    Both are six-line bodies that load the object, return on null, and
    dispatch its vtable byte 0x08. func_02018efc runs on the early-return path

WHAT THE DRIVER CHANGES FOR EVERY OTHER SCENE, because it is not a minigame
edit. func_02018efc advances WHATEVER is installed, so it runs on the 46
levels too, and there it reaches hal/fader_wipes.cpp's host HalFaderWipe:
_ZN8dScene_c19ResetFadersAndSoundEv (slice_w1l2, the level path) hands
&data_0209f5e8 to Scene::SetFaders, which writes it into d4ac. Two things
follow and both were measured rather than argued.

  * THE STEPPING BRACKET IS LOAD-BEARING AND THE FIRST CUT GOT IT WRONG.
    HalFaderWipe::AdvanceFade has an UNDRIVEN path that SNAPS currInterp to
    its target so an invisible fade cannot hold a transition open, gated on
    hal/fader_wipes.cpp's g_hal_fader_stepping. Called outside the bracket,
    func_02018efc made every level snap the installed fader once a frame:
    level 1's SM64DS_WINDOW_SELFTEST=120 run printed seven of the host stub's
    AdvanceFade notes. THE 46-LEVEL BATTERY WAS GREEN OVER THAT, which is the
    honest limit of what a green means here. func_02018efc IS the frame
    loop's driven advance -- it is the function port_fader_advance was written
    to stand in half of -- so the bracket wraps it now, the same level run
    prints zero notes, and the driven path with speed 0 writes nothing
    (Fader::AdvanceInterp leaves currInterp equal and returns before the
    blend registers).
  * THE GARBAGE-RECEIVER HAZARD HAS A LIVE CONSUMER NOW. HalFaderWipe::
    AdvanceFade is a real MSVC __thiscall virtual and reads its receiver from
    ECX; func_02018efc pushes the receiver as a cdecl argument. The stack is
    balanced either way, and the object is in ECX at that call as well, so it
    works -- for the same reason section 10's last unproven item gives for the
    three Scene::SetFaders and Minimap::Behavior sites, and with the same
    absence of any guard. The difference is that those three were dormant and
    this one runs on every frame of every level. Nothing enforces it; a
    recompile that schedules ECX differently would break level fades silently.
    Recorded, not fixed: the fix is the one hal/fader_wipes.cpp's own header
    already routes, ROM-SHAPED vtables for the host wipe objects.

THE COUNTS GOING DOWN IS THE SECOND HALF OF THE RESULT and it took a moment to
read as a pass rather than a regression. The fade now ENDS. _ZN7dWipe_c15SetBackwardTimeEj with
type 0 computes its per-frame acceleration over 0x2d frames; case 1 of
_ZN7dWipe_c11AdvanceFadeEv accumulates +0x1c until it reaches 0x200000, then clamps, calls
func_0202fb30 and writes state 2. func_0202fb30 clears IE bit 1, clears
DISPSTAT bit 4 and nulls the handler, so the HBlank edge closes and delivery
stops. The arithmetic reconciles exactly:

    17280 copies / (191 rows x 2 destinations + the vblank reset's 2) = 45
    11835 deliveries / 263 lines                                     = 45

45 = 0x2d, the frame count the setter derived. The gates read handler=0 ie=0
dispstat=0 at exit because the fade disarmed itself, which is what
port/irq2_map.txt section 4 predicted when it refused to hoist the per-line
gate check ("a handler may disarm itself mid-frame and the ROM's own does").

9b. THE THREE SHAPES MSVC EMITS, and the cleanup each one requires. The
distinction that matters is not cdecl-versus-thiscall, it is WHO CLEANS:

  A  THISCALL, no arguments      mov ecx,<obj> / call [vt+off]
                                 nothing pushed; callee must clean 0
  B  THISCALL, two arguments     push b / push a / mov ecx,<obj> /
                                 call [vt+off], and NO cleanup follows
                                 8 bytes pushed; callee must clean 8
  C  CDECL, struct of pointers   push <obj> / call eax /
                                 add esp,4 or pop <scratch>
                                 caller cleans its own push; callee cleans 0

agree on the cleanup and differ only on where the receiver is, which is a wrong
`this` and not a smashed frame.
