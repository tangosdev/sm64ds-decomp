THE STAGE LIFECYCLE: what hal/level_boot.cpp does that the ROM's Stage does,
which half is scaffolding and which half is genuinely the host's, and what
each lifecycle phase is actually blocked on. Run link60, lane L4.

Baseline this was measured against: 0d81b845c, walk_window 4950 / 11243 linked
(44.0%), battery ALL GREEN, gate GREEN, skips [scene 4 SM64DS_SCENE_SLOT9=0].
arm9 3098 matched TUs, 1664 linked, 1434 unlinked. No exe sha256 is quoted:
the link embeds build-location state, so a hash from one worktree is not a
number another worktree reproduces (the attestation is the gate manifest's
git_sha plus git_dirty).

Every "unresolved" list below was PRODUCED BY A LINK, not read off an earlier
note. The method is the same each time: wire the TU into walk_window in a
throwaway CMakeLists edit, build, read link.exe's own error text, revert, and
the exact slice is written beside the count so the probe is re-runnable. Three
of the counts in port/arm9_frontier.txt and port/slice_w8a.txt have moved since
they were written and one of them was wrong in a way that matters; both are
corrected below with the measurement attached.

AND AN UNRESOLVED-EXTERNALS COUNT IS A FLOOR, NOT THE ANSWER, which cost this
file four numbers on review. A matched TU that is compiled-but-dropped, or that
resolves through an /alternatename face, never appears in link.exe's output and
still has to link before the slot runs. Every count below now states which
reading it is. All four corrections ran in the same direction: the first draft
erred optimistic in slots 3, 6, 9 and 0.


0. THE ONE-LINE ANSWER
----------------------

The Stage's whole lifecycle is behind ONE gate, and it is not the vtable.

  * The vtable is not the problem. hal/stage_bridges.cpp already hosts
    _ZTV5Stage and trap-fills it, and thirteen of its eighteen slots have a
    body that closes against today's link with nothing added.
  * The dispatch is not the problem either. The port already runs all five of
    the ROM's processing passes over the ROM's own list structures
    (hal/actor_registry.cpp, the four Process host copies in port/unmatched/).
  * An actor reaches the behaviour and render lists ONLY by surviving the init
    Process. func_02043880 (phase 1, matched, linked) moves a node onto
    data_020a4b78 and data_020a4b98 when the actor's +0x10 is set, and +0x10 is
    set by the init pass succeeding. So slots 6/7/8 and 9/10/11 are downstream
    of slots 0/1/2.
  * Slot 0 is Stage::InitResources, and it does not close: TWENTY-EIGHT
    unresolved externals compiled on its own, TWENTY-ONE with the gate-36
    closure and three host bodies in front of it (both bases and both slices
    are in section 4), of which the six that matter are a second writer for a
    global hal/fader_wipes.cpp owns.

So "seat the Stage vtable" and "route the boot through the ROM's lifecycle"
are not two jobs that can be done in either order. The init phase is the whole
lane, and everything after it is downstream of one function.

WHAT THE LANE THEN DID ABOUT IT. Commit two (885cd16c2) WROTE FOURTEEN SLOTS,
of which ELEVEN carry a ROM body and three -- 0, 6 and 9 -- took host
occupants. Review added slot 12, so the seat now writes fifteen and twelve of
them are the ROM's. Read those two numbers as separate from the "thirteen of
eighteen close" line above: that one counts which BODIES close, this one counts
which SLOTS the fill writes, and they were conflated in commit two's own
message.

The seat also routed port_stage_a_boot through func_020433b8, so the boot is
DISPATCHED by the ROM's init Process through slot 0 rather than called by name,
the Stage arrives on the behaviour and render lists at its SpawnInfo's
priorities 3 and 6, and the pause-bit stand-in in hal/stage_bridges.cpp retires
in favour of Scene::BeforeBehavior. Slot 0's occupant is still the hosted boot
body; slot 3 is TRAPPED, not hosted, which commit two's message also got wrong
while the code comment beside it had it right.

The linkage delta of commit two is ZERO, honestly, because every body the seat
reaches was already in the image through some other caller. What the seat
changes is that the four blocked bodies now have a live dispatch waiting
instead of a table nothing reads -- which is the difference between seating
them later being an honest edge and being a manufactured one. It also armed a
live path to a slot it had left trapped, which is section 9.

2. THE SEAM, FUNCTION BY FUNCTION
----------------------------------

port_stage_a_boot (hal/level_boot.cpp:2154-2332) against
Stage::InitResources (src/_ZN5Stage13InitResourcesEv.cpp, 0x0202cc0c, marked
NONMATCHING TERMINAL-FLOOR: four words diverge, a register-rename-only delta).

Reading the two side by side, the boot is a SUBSET with three substitutions.
It is not a reimplementation: every line of it either calls the same matched
body the ROM calls, or stands in for one, or supplies an input the ROM gets
from a mode the port never entered.

2d-i. THE HOSTED HALVES OF Stage::Behavior, AND WHAT THEY DO NOT CARRY

  Stage::Behavior is in no slice, so the port hosts individual STATEMENTS of it
  where a subsystem needs one: hal/message_pump.cpp owns UpdateMessage, and
  since run rel0215 hal/star_flow.cpp's port_vs_countdown_tick owns the VS
  countdown. Both are called from tests/walk_window.cpp's frame loop. One debt
  line covers both, and it is a fidelity gap rather than a live defect today:

    * TWO EARLY RETURNS ARE MISSING FROM THE VS ARM. Stage::Behavior's VS
      branch returns before the countdown on data_0209fc9c != 0 (the pause
      state, after func_02032f54 and a data_0209fcc8 >= 7 arm) and on
      data_0209fc68 == 6 (match end). port_vs_countdown_tick reproduces
      neither. The port hosts neither piece of state, so both read zero and the
      difference cannot be observed right now -- but the day either goes live,
      the port ticks the countdown where the ROM would suppress it.

    * THE PAIRING IS HALF-IMPLEMENTED. On the ROM these two hosted statements
      are the two sides of ONE test: data_0209f2d8 != 1 calls UpdateMessage,
      == 1 runs the VS block. port_vs_countdown_tick self-guards on the mode;
      port_message_pump does not. So in a match the port runs both arms where
      the DS runs exactly one. Harmless while the message box is idle in an
      arena, and wrong the moment it is not.

  Retiring either half means giving Stage::Behavior a slice and a real caller,
  at which point both of these go away with it rather than being patched here.

  (level_boot.cpp:2915) is the ROM's twelve Model::LoadFile over data_020756f0,
