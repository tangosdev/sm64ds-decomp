# BATCH 2 listed four classes whose destructor name nothing owns today and
# whose only ROM referrer is their own class vtable. Two of the four are
# REFUSED here rather than seated, and the reasons are in the lane's report:
#
#   _ZN13daObjMaruta_cD1Ev   ov080 0x02127014   (b) no port slot.
#       _ZTV13daObjMaruta_c is a RAW PER-SYMBOL DATA MOUNT (port/ov080_syms.txt
#       line 56, the ov085 --pack shape): its slot-16 word is a DS code address
#       and --pack rebases only pointers whose target lands inside the emission,
#       so the word stays a DS address and the table is never dispatchable. The
#       base class gets no host array either -- port/CMakeLists.txt's ov030
#       rename block states the rule outright ("derived vtables are host arrays,
#       never mounted storage") and every daObjMaruta_c DESCENDANT (RollingLogTtm
#       0x02115a48, daObjHmMaruta_c) carries its own host array whose slot 16 is
#       that descendant's own destructor. Nothing in the port can honestly
#       reference ??1daObjMaruta_c@@QAE@XZ.
#       (The TU itself is fine: probe-compiled with walk_window's own flags it
#       defines ??1daObjMaruta_c@@QAE@XZ and ??_GdaObjMaruta_c@@QAEPAXI@Z and its
#       only undefined externals -- ?Destructor1@dBgActor_c@@UAEXXZ and
#       ?Destructor0@dBgActor_c@@UAEXXZ -- are both in walk_window.map already.
#       It is the EDGE that is missing, not the body.)
#
#   _ZN16daObjFallBlock_cD1Ev  ov098 0x02139fc8  (b) no port slot, same shape.
#       _ZTV16daObjFallBlock_c is mounted per symbol at port/ov098_syms.txt line
#       25, in a file whose own header says "the vtables are left out because
#       they are host arrays the registry fills" -- this one is not left out, it
#       is in the packed data span as bytes. Its four overridden members
#       (Behavior/Render/OnHitByMegaChar/Kill) are dispatched from OTHER
#       overlays' host arrays (hal/actor_classes_ov022_w16.cpp,
#       hal/actor_classes_ov045.cpp), each of which seats its OWN class's
#       destructor in slot 16. Same probe result as Maruta.
#
#   BOTH REFUSALS ABOVE ARE SUPERSEDED (run linkfull, lane VARIANT5). Their
#   premise was the mount, and the mount was the anomaly: both tables are host
#   arrays now (hal/actor_classes_ov080.cpp, hal/actor_classes_ov098.cpp, ROM
#   contents slot for slot), both tokens are off their per-symbol lists, and
#   slots 16/17 of each hold the class's own D1/D0 -- the ROM's words at
#   0x02128378/0x0212837c and 0x0213c5fc/0x0213c600. The four bodies are the
#   `#ifdef _MSC_VER` arms of their own src files, each spelling the ROM body
#   step for step (MSVC never emits an inline destructor under the flat name),
#   on port/slice_w31_variant5.txt. The INLINE-DTOR-COMDAT ruling below still
#   holds for daDsnBase_c; it never applied to these two, whose arms define a
#   flat name no COMDAT carries.
#
#   _ZN11daDsnBase_cD1Ev     ov091 0x02132d6c   (b) MEASURED AND REFUSED.
#       A THIRD ARTEFACT SHAPE, alongside census.md's DTOR_VARIANT and
#       CTOR_VARIANT rulings: call it INLINE-DTOR-COMDAT. daDsnBase_c.h defines
#       ~daDsnBase_c() {} in the class body on purpose, so every TU that compiles
#       a DERIVED destructor emits ??1daDsnBase_c@@QAE@XZ as its own inline
#       COMDAT. On the base build walk_window.map already carried that symbol,
#       out of _ZN6ThwompD1Ev.cpp.obj, and the one reference to it is
#       hal/actorport_dtor_bridge.cpp:1166,
#       /alternatename:@actorport_d16t_daDsnBase_c@8=??1daDsnBase_c@@QAE@XZ,
#       which is the ROM slot-16 spelling of _ZTV11daDsnBase_c. So the ROM text
#       ALREADY RUNS; what the row is missing is only an object of its own name.
