1. THE ENTRY GATE, AND WHAT IT ACTUALLY EXERCISED
--------------------------------------------------

The ov007 lane closed by saying its own mount tested only the EXCLUSIVE half of
the residency model -- every answer it produced was coresident FALSE -- and that
the PERMISSIVE half, "coresident TRUE between two mounted overlays that
genuinely contest an address, where the model has to drop a binding it would
otherwise have made", would first be exercised by ov004 plus ov006. This lane is
that mount. The prediction is half right and the half that is wrong matters, so
it is the first thing here.

WHAT DID GET EXERCISED. coresident(ov004, ov006) = True is the only True the
model produces between two scene-slot occupants, and it is now load-bearing:
55 pointers bind across the pair BECAUSE of it, and would not bind without it.
The model's answers, printed from Residency over the 96 mounted footprints:

    scene slot        ov002, ov003, ov004, ov005, ov006, ov007
    passengers        ov004 rides ov006
    sticky            ov075
    level territory   from 0x021111a0 on the ov002 scene

    coresident(ov004, ov006) = True     <- the pair, by rule 2's passenger arm
    coresident(ov004, ov002) = False    coresident(ov006, ov002) = False
    coresident(ov004, ov003) = False    coresident(ov006, ov003) = False
    coresident(ov004, ov005) = False    coresident(ov006, ov005) = False
    coresident(ov004, ov007) = False    coresident(ov006, ov007) = False

    mounted overlays co-resident with ov004:  ov001, ov006
    mounted overlays co-resident with ov006:  ov001, ov004

WHAT THIS PAIR DOES NOT EXERCISE, STATED CORRECTLY. An earlier version of this
section argued that the drop direction might be UNREACHABLE on today's rules.
That is wrong, and the review caught it. It misread window_count:

    def window_count(src, v):
        return sum(1 for ov, (s, e) in windows.items()
                   if s <= v < e and res.coresident(src, int(ov[2:])))

Each window has to be co-resident with the SOURCE. It does not have to be
co-resident with the other windows, and usually is not. Two mutually EXCLUSIVE
overlays both counted against one source is the ordinary case, not an impossible
one, and it is exactly what the 105 contested rows in this build already are:
they come from 17 source overlays, and the largest window_count among them is
47 -- an ov091 want at 0x02111244, which every level overlay's window covers.
The level slot performs the drop 105 times a build.

WHAT SURVIVES of that argument is one narrower sentence, and it is true: no two
mounted overlays are ever both OVERLAPPING and CO-RESIDENT, because rule 1 tests
overlap first and returns False. That is why ov001, ov004 and ov006 can never
contest each other -- the three windows are disjoint, abutting twice --

    ov001   0x020aa420 .. 0x020ad660
    ov004   0x020ad660 .. 0x020bfec0
    ov006   0x020bfec0 .. 0x021430a0

and it is why this pair contributes no contested row of its own and moved no
pre-existing one. But that is a fact about THIS pair's addresses, not a property
of the model, and it does not generalise.

THE DROP DIRECTION IS REACHABLE. It is reached 105 times today, and it is
reachable by this lane's own rows: mounting ov000 alone would do it. ov000's
footprint is 0x020aa420..0x020bf4e0, it shares ov001's base, and it is neither a
scene occupant nor sticky nor level territory, so coresident() falls through to
True for everything -- ov006 included. Its window then covers most of ov004's.
Measured, with nothing else changed:

    rebased rows        284 -> 264      20 LOST
    contested           105 -> 749

All 20 lost rows are ov006 -> ov004 rows and all 20 are among this lane's own
55. So these bindings are not unconditional: they hold because ov000 is not
mounted, and the day it is, twenty of them are correctly withdrawn.

The honest summary the next mount lane should inherit: this lane exercised
coresident TRUE in the direction that WRITES bindings, and did not exercise the
direction that withholds them -- not because that direction is unreachable, but
because this pair's windows happen not to overlap any window co-resident with
them.

THE PASSENGER REFUSAL STAYED QUIET, which is the third thing this gate was to
check. ov004's footprint ends at 0x020bfec0 and ov006's base IS 0x020bfec0;
_overlaps() is strict, so 0x020bfec0 < 0x020bfec0 is false, the pair does not
overlap, and Residency.__init__'s refusal did not fire. It is the first time
that check has run against a mounted pair rather than a modelled one.

5. FINDINGS
-----------

F1  dsd's .ctor SYMBOL NAMES ARE NOT C IDENTIFIERS, and the rule the ov007 lane
    established walks straight into them. FIXED IN THIS LANE, proven neutral.

    "Mount every data-kind and bss-kind symbol dsd names" is the rule that makes
    a packed run hole-free, and it is right. It had never met a .ctor section:
    ov007's is zero length and ov003's the same, and every other mount list is
    hand-picked. ov004 has four .ctor words and ov006 thirty-one, and dsd names
    each one after the sinit it points at with a leading dot --
    `.p__sinit_ov004_020b948c`. The config holds 308 names that are not C
    identifiers: 305 of them are .ctor words spelled that way, one per .ctor
    word in every overlay that has constructors, and the other 3 are itcm
    kind:label(arm) names (.L_01ff8df8, .L_01ffa588, .L_01ffadf8), which are
    labels rather than storage and no mount list would ask for one.

    Emitted verbatim the declaration is `u8 .p__sinit_ov004_020b948c[4]`, which
    is not C. That fails loudly, but it fails minutes later as a parse error in
    a generated file with nothing pointing back at the symbol list, so ovdata
    now refuses the name where the list is, with the remedy in the message.

    Byte-neutral and provably so: no token in any of the 46 ovNNN_syms.txt files
    fails the test, and every file under build/port/host-src regenerates
    identical before and after.

    LEAVING THE .ctor TABLE OUT IS ALSO RIGHT ON ITS OWN TERMS, not just
    convenient. Those words hold DS addresses of .init code no data mount hosts.
    Hosting them would give a constructor walk thirty-one addresses that resolve
    to nothing; the zeroed pack padding that stands in for them reads as a table
    that terminates immediately, which is exactly the "identified but not wired
    to run" this lane was asked for.

F5  28 SYNTHETIC GAP BLOCKS IN PACKED MOUNTS SIT OUTSIDE .dsstate AND A SAVE
    STATE DOES NOT CAPTURE THEM. NOT FIXED HERE. ROUTED, WITH F4.

    Found by trying F4's object-keyed rule. ovdata routes a plain (non-pack)
    mount's arrays into .dsstate with `#pragma data_seg(".dsstate$mmm")`, and a
    packed mount's named symbols with an explicit __declspec(allocate) per
    symbol. Its SYNTHETIC gap blocks -- the `port_ovNNN_gap_ADDRESS` arrays it
    creates for un-symbolized statics that emitted pointers land in -- are
    emitted as ordinary file-scope arrays after both, and the pack branch never
    opens the data_seg. So in a packed mount they land in the default data
    segment. The emitter's own comment notices half of this and stops:
    "(the synthetic gap arrays above are data and had to land in .dsstate too,
    which they did while it was open.) Packed mounts never opened it."

    Measured on this build: 28 such blocks, 5368 bytes, across ELEVEN packed
    mounts (ov001, ov009, ov016, ov020, ov021, ov022, ov044, ov064, ov070,
    ov071 and ov095). They are not padding -- they hold real ROM bytes, the
    in-mount and cross passes rebase pointers ONTO them, and the game's walks
    step through them, so they are mutable DS state by the same argument that
    puts every other mounted byte in .dsstate. A restore leaves them stale. That
    is the 0.2.0 ANIM_PTRS class exactly, which is the bug dsstate_guard was
    written for, and F4 is why the guard could not see it.

    THE LIVE CASE IS DEMONSTRATED, not argued. The review found one and the F5
    lane inherits it as its first test vector: data_ov009_02112238 goes 0xffff
    to 0x0000 while Bob-omb Battlefield runs, and a save then a load misses the
    rollback, because the word is not in the captured span. The static half
    checks out here -- config/arm9/overlays/ov009/symbols.txt names
    data_ov009_02112238 kind:data(any) at 0x02112238, port/ov009_syms.txt omits
    it, so it falls inside port_ov009_gap_0211222c (244 bytes from 0x0211222c,
    the word at +12), and that block sits at RVA 0x62f7e0 against a captured
    span of [0xafa000, 0xbde120). Outside, and written during play.

    NEITHER ov004 NOR ov006 EMITS ONE, so this lane adds nothing to it: 28
    before and 28 after. It is entirely pre-existing.

    NOT FIXED HERE because the fix moves 5368 bytes of eleven shipped mounts into
    .dsstate, changes their emitted C, and changes the save state's captured
    span and layout. That is a behaviour change to working mounts and to the
    save/restore format, and it needs its own lane and its own soak, not a rider
    on a mount lane. The two together are one small tooling lane: route packed
    synthetic gaps into .dsstate, then key the guard on the mount object so it
    would have caught it.

    The two gaps this lane adds are the largest members of that set, 2420 and
    16700 bytes, and they are also its safest: what they cover is not skipped
    data but a whole .init CODE section plus its .ctor table, and a data walk
    does not cross a code section. The 25 faithful gaps are the exception, not
    the rule, and a future header should say which kind it has.
