THE REMAINING HOSTED-DATA TRUNCATIONS, DERIVED AND FIXED
Run link60, lane GAP5. Base cons port-mount-noseat-cluster 3a5733c03, gate
GREEN 5831/11250 (51.8%), battery ALL GREEN, skips [].

The castle moat water bug (notes/port-selftest-bmp-gate.md on main, fix landed
at cons 3a5733c03) was one instance of a class, not a one-off. A real array
whose only host is a synthetic gap block gets its extent from the next entry in
dsd's symbols.txt, `ambiguous` guesses included. When a guess lands inside the
array's span the hosted copy is short, and the read past the end lands on
whatever the linker parked next -- which in the water's case was a row of
rebased HOST POINTERS, so an image base decided pixels.

port/tools/battery.py names five more of these. This document derives all five
from ROM bytes, corrects one of them, and adds a sixth the sweep turned up.

Every extent here is read from extracted/overlays/overlay_XXXX.bin at the base
in config/arm9/overlays/ovNNN/delinks.txt. Not from dsd exports (proven stale,
and ov021's is the compressed image), not from raw vtable words.

1. HOW A CANDIDATE IS FOUND, AND WHY THE LIST IS SHORT
--------------------------------------------------------

port/tools/gapaudit.py enumerates the synthetic gap blocks (48 of them at this
base, 9420 bytes over 12 mounts, all inside the captured .dsstate span). It
does not itself decide which are short. The screen that does is:

    for each gap block, compare its emitted size against the distance to the
    next NON-AMBIGUOUS dsd symbol after its start.

A block shorter than that distance was cut by an ambiguous guess or by ovdata's
+0x18 discovered-target floor. Six of the 48 came back:

  mount  gap block      hosted   to next real sym   ambiguous cuts between
  ov009  0x021133d4         96               1320   20
  ov009  0x02113214         24                448    4
  ov016  0x021148d4         24                 52    2
  ov009  0x02112c9c         24                 48    2
  ov021  0x02114818         24                 48    1
  ov016  0x02113bec         28                 32    1

THIS SCREEN PRODUCES CANDIDATES, NOT EXTENTS. The distance to the next
non-ambiguous symbol is an upper bound: an array is allowed to end before it.
Two of the six are false positives and the derivation is what caught them --

  ov016 0x021148d4 and ov021 0x02114818 are both the Itanium
  __si_class_type_info record {typeinfo vtable + 8, name, base}, 12 bytes. The
  +0x18 floor already OVER-covers them at 24. They read as candidates only
  because the SpawnInfo symbol that follows each one is itself marked
  ambiguous, so the screen's upper bound skips past it to the next real symbol.

The two carried fixes the screen cannot see are the ones that are not gap
blocks: ov021 0x021148dc is an already-mounted named symbol sized by its
next-symbol delta, and ov070 0x02122968 sits INSIDE a gap block rather than at
its start.

AND THE SCREEN IS NOT THE MEASURE. It only looks at where a gap block STARTS,
so it is blind to an interior member, and it says nothing about what a fix
COSTS. Both blind spots bit this lane, in the same way, and the correction is
the same tool:

    THE MEASURE IS AN INTERVAL DIFF OF THE HOSTED ROM ADDRESSES, PER MOUNT.

Take the set of DS addresses each mount's sidecar (build/port/host-src/*.c.map,
"provides" rows, pack pads excluded because they are zero filler) actually
backs with ROM bytes, before and after. Report LOST and GAINED intervals. Merge
only when LOST is empty.

HOW TO RE-RUN IT, because no tool in this tree does it yet and a reviewer needs
the number rather than the paragraph. Generate a BASE sidecar set from the base
tree's syms files, and diff it against the built tip's own sidecars:

    for ov in ov009 ov016 ov021 ov070; do
      python port/tools/ovdata.py $ov /tmp/base/${ov}_syms.c \
             --from-list <base-tree>/port/${ov}_syms.txt --pack
    done
    cp build/port/host-src/*.c.map /tmp/allbase/      # untouched mounts
    cp /tmp/base/*.c.map           /tmp/allbase/      # changed ones, base
    # then per mount: set(range(a, a+size)) over the "provides" rows whose
    # name is not pkNNN_gap_*, base minus tip = LOST, tip minus base = GAINED

Copying the tip's sidecars for the untouched mounts is not cosmetic: diffing
against an ABSENT base file reports the whole mount as gained, which on this
tree turns a real "+2140, LOST 0" into a meaningless "+440855".

WHY A BYTE SUM CANNOT SUBSTITUTE, stated plainly because this lane got it
wrong and shipped the wrong number in an earlier draft of section 10. Naming a
symbol RE-LAYS the discovered-target gap runs around it, and a run that used to
stretch across its neighbour then stops short. If the newly named symbol is
bigger than the span the run gave up, the byte total goes UP while a real ROM
interval silently stops being hosted. The first version of this lane's ov009
change measured +1872 bytes of coverage and was simultaneously dropping
[0x02112f58, 0x0211301c) -- 196 bytes, most of the tag-0x01 array -- leaving
its rebased pointer 28 bytes of runway before the walk crossed into
port_ov001_gap_020ab620 and its four rebased host pointers. That is this file's
own failure class, reintroduced by this file's own fix, invisible to the byte
sum, invisible to mapdiff (which tracks names, and no name was lost), and
invisible to the candidate screen (0x02112f3c is interior to a gap block).

The interval diff caught it, and then caught five more rounds of it: closing
one member moves the gap's end back onto the next ambiguous guess upstream and
drops the next span. THE RULE THAT FALLS OUT IS "NAME THE WHOLE RUN OR NAME
NONE OF IT". The ov009 descriptor's arrays are two contiguous runs and the
final change names every member of both; ov070's curve needed two upstream
neighbours before its own gap ended on a named symbol. Sections 2, 4 and 6 give
the arithmetic.


2. ov009 0x02113214 -- 28 records of SIXTEEN bytes, not six
-------------------------------------------------------------

THE STRUCTURE. The level descriptor at ov009 0x02112b60 carries two tables of
8-byte records, {u8 tag; u8 count; u16 zero; void *data}:

  0x02112b6c = 6            0x02112b74 = 9
  0x02112b70 -> 0x02112c9c  0x02112b78 -> 0x02112dcc

Four records of those two tables point into one contiguous run, and each
array's stride is different:

  record      tag   count   points at     stride   size
  0x02112ca4  0x05     29   0x0211301c         8   0x0e8
  0x02112cbc  0x40     17   0x02113104        16   0x110
  0x02112cac  0x20     28   0x02113214        16   0x1c0
  0x02112dcc  0x02    220   0x021133d4         6   0x528

  0x0211301c + 0x0e8 + 0x110 + 0x1c0 + 0x528 = 0x021138fc

0x021138fc is data_ov009_021138fc, non-ambiguous, and its contents are the
{function, 0} pairs __sinit_ov009_02112458 copies into Bird's behaviour table:

  0x021138fc  0211145c 00000000 02111234 00000000

Four consecutive exact landings with three different strides. No single stride
in that chain is a free parameter.

WHY 6 IS WRONG FOR TAG 0x20. 28 * 6 = 0xa8 ends at 0x021132bc, which is not a
symbol, not a record boundary and 0x118 short of the array that follows. The
16-byte stride is directly visible instead:

  0x02113394  fed400ed 08980315 00000000 310d0000
  0x021133a4  012c00ed 08980315 00000000 320e0000
  0x021133b4  177000ed 06a4018d c0000000 330f0000
  0x021133c4  e82c00ed 0c80061f 80000000 34100000

A repeated type id in the first halfword (0x00ed), a coordinate triple, an
orientation halfword, and two counters that step once per record (0x0d31,
0x0e32, 0x0f33, 0x1034). The last record starts at 0x021133c4 and ends at
0x021133d4. The tag-0x40 array at 0x02113104 has the identical record shape and
in places identical records: 0x02113134 and 0x02113234 are the same sixteen
bytes, and so are 0x02113144 and 0x02113244. (0x02113124 and 0x02113224 are NOT
-- they differ at byte 14, 0xff against 0x01. An earlier draft named that pair.)

THE ORIENTATION HALFWORD IS NOT A CLEAN QUADRANT, which an earlier draft
claimed ("only ever takes 0x0000/0x4000/0x8000/0xc000"). Counted over the 59
records of the three 16-byte arrays: 33 carry zero, 26 carry something, and of
those 26 only EIGHTEEN are 0x4000/0x8000/0xc000. The other eight are 0x2000,
0xa000 and 0xaaab in the tag-0x01 array, 0x09f4, 0x2333, 0x2aaa and 0xeaab in
tag 0x40, and 0xe000 in tag 0x20. Nothing in the extent derivation rests on
this field; it is described here only because a banner described it wrongly.

Only the tag-0x02 and tag-0x03 arrays are Vector3<s16>. The tag-0x02 points
read as world coordinates from the first to the last, [-200, 783, 3100] through
[-5200, 254, 4000].

WHAT WAS HOSTED. 24 bytes, the +0x18 floor, with FOUR ambiguous boundaries
inside the span (counted, not estimated). The first is 0x02113228, twenty bytes
in, so even the floor was doing the covering.

CONSUMER, AND ITS REACH. Both arrays are reached by a rebased HOST pointer, so
the walk really does start on hosted storage and run off the end -- the exact
water-track shape. From the generated ov009_syms.c at the base commit:

    *(unsigned int *)(port_ov009_gap_02112c9c + 20) = (unsigned int)(port_ov009_gap_02113214 + 0);
    *(unsigned int *)(port_ov009_gap_02112dcc +  4) = (unsigned int)(port_ov009_gap_021133d4 + 0);
    *(unsigned int *)(port_ov009_gap_02112b60 + 336) = (unsigned int)(port_ov009_gap_02113214 + 0);
    *(unsigned int *)(port_ov009_gap_02112b60 + 624) = (unsigned int)(port_ov009_gap_021133d4 + 0);

Each array is reached from two places. The count that drives the walk is the
record's own count byte, which is 28 and 220 against 1 and 16 hosted records.

4. ov009 0x02112c9c -- the six-record table, DERIVED NEW
----------------------------------------------------------

Not in the carried commits. Same class, and it is the index for both arrays
above.

EXTENT. 6 records * 8 = 0x30, ending on data_ov009_02112ccc. That end is not an
inference: 0x02112ccc is the target of the ninth record of the OTHER table, at
0x02112e0c, {tag 0x2a, count 4}. The count 6 is the word at 0x02112b6c, the
slot immediately before the table pointer at 0x02112b70, and the pairing is
confirmed by the second table, whose count word 0x02112b74 = 9 matches nine
records ending exactly on data_ov009_02112e14.

WHAT WAS HOSTED. dsd guessed an ambiguous boundary at 0x02112ca8, twelve bytes
in; the +0x18 floor rounded that to 24. Three of six records.

CONSUMER. Visible without any disassembly, by comparing the two tables in the
generated source at the base commit: three pointers rebased into
port_ov009_gap_02112c9c (+4, +12, +20) against all nine into
port_ov009_gap_02112dcc, which is the same structure sized correctly by its
next-symbol delta. Records 3..5 were being read out of the next block.

SIDE EFFECT, MEASURED, AND IT CUT BOTH WAYS. Naming 0x02113214 (section 2) ends
the discovered-target run that used to stop at 0x021130cc, so the gap before it
is re-laid as port_ov009_gap_0211301c[504] = 0xe8 + 0x110, covering the tag-0x05
array AND the tag-0x40 array at 0x02113104 exactly. Both were short: tag-0x05
was hosted 176 bytes of 232 off the tail of port_ov009_gap_02112b60[1388], and
0x02113104 was not hosted at all. That is the good half.

The bad half is that the SAME re-lay shortened port_ov009_gap_02112b60 from
1388 to 1016 and dropped [0x02112f58, 0x0211301c), and closing that dropped the
next span upstream, five times over, down to the CLPS run. Section 1 tells that
story because the lesson is about method, not about this table. The lines
listed in section 0 close all of it; the interval diff is the proof.

Nothing in this change names 0x02113104. The contested window keeps its status
as an open question; it simply stops being a hole, because a run that used to
end in the middle of it now ends on a real symbol. After the change all six
record pointers rebase onto hosted storage:

    *(unsigned int *)(data_ov009_02112c9c + 36) = (unsigned int)(port_ov009_gap_0211301c + 232);

232 is 0xe8, so that is 0x02113104.


5. ov016 0x02113bec -- the CLPS block
---------------------------------------

Carried extent 0x20, verified, but its banner's supporting anecdote was wrong.

WHAT A CLPS BLOCK IS, MEASURED RATHER THAN ASSUMED. "CLPS", u16 entrySize, u16
count, the entries, then a run of 0xffffffff padding out to a 32-byte multiple.
Counted over every extracted image: 245 CLPS blocks, all 245 with entrySize 8,
and every count-1 (131 of them), count-2 (64) and count-3 (4) block measures
exactly 32 bytes.

The padding-to-32 rule matters. An earlier pass of this lane assumed a fixed
"+16 trailing ffffffff" and that formula flags 65 blocks as truncated; it is
wrong, because a count-2 block carries only two trailing words, not four. Only
163 of the 245 blocks are followed by 16 bytes of 0xff. The 32-byte multiple is
the rule that holds.

THE BLOCK. 0x02113bec is byte-identical to 0x02113bac:

  0x02113bec  53504c43 00010008 01000fc5 000000ff
  0x02113bfc  ffffffff ffffffff ffffffff ffffffff

count 1, so 0x20, running to data_ov016_02113c0c. dsd guessed an ambiguous
boundary at 0x02113c08, 0x1c in, clipping the last of the four trailing
ffffffff words. Its twin at 0x02113bac is already sized 0x20 by dsd's own
next-symbol delta, which is the local corroboration.

THE BANNER CORRECTION. It said ov009 has three consecutive count-1 blocks at
0x20 spacing. ov009 has FOUR: 0x02112bf8, 0x02112c18, 0x02112c38, 0x02112c58,
each 32 bytes with 16 of trailing ffffffff and differing only in its single
entry word, running 0x02112bf8 to 0x02112c78.


6. ov070 0x02122968 -- the curve cut on its apex
--------------------------------------------------

Carried extent 0x194, verified, and this is the prettiest of the six.

The array is 101 Fix12 words, 0x02122968 to 0x02122afc. 0x02122afc is the end
of ov070's .rodata by the delinks section table and the start of
__sinit_ov070_02122afc, a real function, so the end needs no arithmetic at all.

The curve is symmetric about its maximum 0x2800 (2.5 in Fix12) at 0x02122a6c,
and dsd guessed an ambiguous boundary at exactly 0x02122a6c -- the one word
where the byte pattern reverses direction:

  0x02122a64  0x000027d0     0x02122a74  0x000027d0
  0x02122a68  0x000027f4     0x02122a70  0x000027f4
  0x02122a6c  0x00002800  <- apex, and the cut

Word index 65 of 101. Words 66..100 (35 of them) mirror words 30..64 (35 of
them) value for value, which is what the carried banner claims and it is
correct. The hosted copy was the rising half only.

THERE IS NO COVERAGE TRADE. e4f25f862 recorded one and an earlier draft of this
document repeated it: naming data_ov070_02122968 takes it out of the
discovered-target set, port_ov070_gap_02122594 shrinks 0x4d8 -> 0x304, and ROM
[0x02122898, 0x02122968) -- 208 bytes -- stops being hosted. Both called that
acceptable because nothing reaches the dropped span.

THAT IS THE WRONG STANDARD, and it is the standard that let this lane
reintroduce its own failure class in ov009. A hosted interval that stops being
hosted is the defect, whoever reads it, because "nothing reaches it" is a claim
about today's call graph and the truncation outlives it.

The hole is closed instead, with two upstream lines. The dropped span sits
inside a run of 171 constant 0x1000 words spanning [0x021226bc, 0x02122968),
and that run carries two real non-ambiguous symbols that are both reloc
targets -- the .rodata pointers of the records at 0x021234c4 and 0x021234dc:

  data_ov070_021227d8:0x190   0x021227d8 + 0x190 = 0x02122968, the curve
  data_ov070_021226bc:0x11c   0x021226bc + 0x11c = 0x021227d8

Every one of those 271 words is 0x1000, verified against the raw image. With
both lines ov070's gap ends on a named symbol, the cascade stops, and ov070's
interval diff is LOST 0 / GAINED 144 -- the 144 being the falling half of the
curve, which is the whole point.

8. CONSUMER REACH, RANKED
---------------------------

Not every one of these can reach a frame, and saying which can is the
difference between a fix that needed a rendering A/B and one that did not.

  the ov009 descriptor run                   HIGH, render-reachable.

      Reached as the third word of the resource triple at 0x02114b8c,

  ov021 0x021148dc                            LOW, not rendered.
      RTTI name lookup only. It matters because every read returned "16da"

runs. The pad is battery.py's own interior recipe, and it moved the span by 72
bytes each time, so the perturbation was applied and had an effect on the
layout. It simply did not have one on the frame.

WHAT THIS DOES AND DOES NOT LICENCE.

  * P1 == P2 means the PRE-FIX build already had no layout sensitivity at these
    counts. So this lane CANNOT claim to have removed an observed sensitivity.
    The fixes rest on the extent derivations and the consumer evidence above,
    not on a frame delta.
  * P1 == P3b means the package changes no pixels, at a .dsstate span 1936
    bytes smaller than base. No BMP baseline needs updating for this merge.
  * P3b == P4b means the package introduces no new sensitivity.
  * None of these six rows says the truncations were harmless. It says the
    level-1 selftest at seven counts cannot see them, which is a statement
    about the probe.

THE STRUCTURAL REASON THE PRE-FIX PROBE IS QUIET, as far as it can be
established. ov009 is hosted TWICE. hal/level_boot.cpp's row for level 1
resolves LVL_Overlay 0x02112bdc through port_ov009_at into port_ov009_image[],
the WHOLE-image mount, and the descriptor at 0x02112b60 with its two record
tables and its path arrays lives inside that image at full length -- it was
never truncated there. The per-symbol mount these lines size is the other half,
the one actor code reaches BY NAME, and no source in src/ or port/hal names
0x02112b60, 0x02112c9c, 0x02113214 or 0x021133d4. The water track was in the
same per-symbol mount and DID reach the frame, because CastleWater's actor code
names data_ov009_02112bc4 and follows its +12 pointer into the track; these
three have no equivalent named root.

That is an explanation, not a proof that the per-symbol copies are dead. It is
not claimed here that nothing reads them.

ov070 has no whole-image mount at all (it is not in PORT_LEVEL_OVERLAYS and
there is no port_ov070_image), so its per-symbol copy of the curve is the only
copy in the build, and that fix is unambiguously live.

The bound the pre-fix state DID have, and which these fixes remove, is the one
battery.py's rule names: while a truncated block's overrun can land on rebased
host pointers, a layout change can reach the frame through it. It can here --
port_ov009_gap_021133d4's 96-byte block is followed in the map by
port_ov001_gap_020ab620, which takes four rebased host pointers, and reading
204 points past the end crosses into it. The probe says that path is not
exercised on level 1 in 300 frames. It does not say it is unreachable.


10. THE .dsstate SPAN, DECOMPOSED
-----------------------------------

For the player-loop lane, because old save states stop loading when the span
changes and that is desired behaviour rather than a bug.

  base 3a5733c03  .dsstate [0xbb0000, 0xc9ab30)  961328 bytes  11666 symbols
  tip             .dsstate [0xbb0000, 0xc9a3a0)  959392 bytes  11681 symbols

THE BASE DOES NOT MOVE. The span SHRINKS by 1936 bytes, which reads backwards
for a change whose whole point is hosting more ROM, so here is where it goes.

COVERAGE, as a SET of unique DS addresses per mount, off the ovdata sidecars
(build/port/host-src/*.c.map). This is the interval-diff measure of section 1,
totalled; the LOST column is zero everywhere and that is the merge condition:

  mount     unique ROM bytes hosted      lost
  ov009     2756 -> 4732   (+1976)          0
  ov016      904 ->  908      (+4)          0
  ov021      512 ->  528     (+16)          0
  ov070     3132 -> 3276    (+144)          0
  TOTAL     7304 -> 9444   (+2140)          0

AN EARLIER DRAFT PUT +1872 HERE and said "ov070 is the only mount that loses
real coverage, 208 bytes". Both halves were wrong. The number came from summing
the generated array declarations, which double-counts rows that overlap (a
named symbol also covered by a gap block) -- the same sum over these sidecars
gives +1956, and the 184-byte difference from the true +2140 is exactly that
overlap. And no mount loses coverage now: ov070's 208-byte hole is closed by
data_ov070_021227d8 and data_ov070_021226bc (section 6), and the ov009 holes
that draft never noticed are closed by the run naming (sections 2 and 4).

The SPAN still shrinks while coverage grows, and that is the pack pads: naming
a symbol lets --pack lay it against its neighbour instead of padding around a
hole. 2140 bytes more real ROM inside a section 1936 bytes smaller means the
zero filler fell by roughly four kilobytes. The pads are not in the sidecars,
so that figure is a subtraction rather than a measurement, and it is offered as
orientation only -- the load-bearing numbers here are the span, which the
linker prints, and the coverage set, which the interval diff computes.

Old .dsstate save states will refuse. That is the documented desired behaviour.


11. ONE FLAKE, RECORDED RATHER THAN RE-RUN AWAY
-------------------------------------------------

The gate run on the final package came back RED:

    selftest level 40: FAIL rc=4294967295

rc 4294967295 is -1. It has not reproduced since, and here is the whole
measurement rather than the sentence "I re-ran it and it passed", which is the
sentence that hides a real intermittent:

  * level 40 standalone, tip build, same env the battery uses
    (SM64DS_LEVEL=40, SM64DS_FAULTS_FATAL=1, SM64DS_WINDOW_SELFTEST=300):
    24 runs, 0 failures, all reaching frame 299 and pos=(0, 1228800, 0).
  * level 40 standalone, PURE BASE build at 3a5733c03 in a second tree:
    20 runs, 0 failures.
  * the full battery re-run on the same binary: ALL GREEN, "selftest level 40:
    ok".
  * no crash.txt, no fault report, and no playlog entry for the failing run,
    while the surrounding manual runs did leave playlog entries.

port/ov007_seat.txt records the same signature on a different level: "the
middle one failed with selftest level 7: FAIL rc=4294967295 (rc -1, a killed
child, not a fault -- no fault report and no playlog entry), on a machine that
was building in another window at the time." Same rc, same absence of artifacts.

WHAT THAT DOES NOT ESTABLISH. 0 failures in 20 base runs is not proof the base
is immune -- it failed to catch the event either, and one occurrence in ~45
runs is entirely consistent with a rate that 20 samples would miss on both
sides. So this is NOT a demonstration that the flake is unrelated to this
package. It is a demonstration that the package does not make level 40 fail
reproducibly, plus a signature match to a documented environmental kill. A
reviewer who wants the stronger claim needs a run count that 20 does not buy.

Level 40 is Bowser in the Sky and its census is BOWSER, BOWSER_TAIL,
BOWSER_FIRE, SPIKE_BOMB, BOWSER_SKY_PLATFORM, PLAYER, CAMERA, HUD, MINIMAP.
None of those classes lives in ov009, ov016, ov021 or ov070, which is the
argument from the other direction and is also not a proof.


12. WHAT WAS DELIBERATELY NOT TOUCHED
---------------------------------------

Named here so a reader does not read their absence as an oversight:

  * ov009 0x02113104, the contested window. No symbol line added. It is now
    covered incidentally by port_ov009_gap_0211301c (section 4), which is a
    consequence of sizing its neighbour, not a decision about it.
  * ov002's plain-mount named sizing, 383 targets, unaudited and with no
    --pack protection.
  * The four spurious kind:load relocs inside data_ov009_021133d4. Suppressing
    entries in shared dsd config is the repo owner's call, not a lane's.
  * The 65-row CLPS census this lane's first pass produced. It rests on a
    trailing-ffffffff formula that section 5 shows is wrong. Re-run against the
    pad-to-32 rule before anyone treats it as a worklist. Note that four ov009
    rows of that census ARE now fixed, not because the census was trusted but
    because the interval diff walked into them from the other end.

WHAT A FOLLOW-UP LANE SHOULD DO WITH THE INTERVAL DIFF. It is the measure this
lane needed and did not have, and nothing in the tree runs it. The eleven other
mounts were checked here only incidentally, by diffing base against tip; a
mount whose syms file nobody is editing has no before-column to diff against
and so is not covered at all. Making it a standing check means giving each
mount a recorded hosted-address set the way tools/tiers.py records tiers, so a
run that drops an interval is caught by CI rather than by a reviewer reading a
byte total. That is a tool, not a banner, and it is out of this lane's scope.
