THE PPU LAYER-BLENDING UNIT: ALPHA (BLDCNT mode 1) IN BOTH SOFTWARE RASTERISERS
Run link60 Stage 5, lane BLND1. Worktree C:/tmp/blnd1, branch s5-ppu-blend, off
cons 74f8a1aa5. Coordinator merges; this lane never merges or pushes.

WHAT WAS ADDED
--------------
The DS 2D colour-special-effects unit's ALPHA path (BLDCNT mode 1 + BLDALPHA),
including the always-on semi-transparent-OBJ alpha, in the port's two LIVE
software compositors:

  engine B (bottom screen)  port/ntr/ppu_sub.cpp
  engine A (top screen)     port/hal/message_compositor.cpp

Both already resolved pixels by priority; the change makes each resolve the TOP
pixel AND the one directly BELOW it, and when the top is a 1st target and the
below a 2nd target it outputs

  out = clamp31( top*eva/16 + below*evb/16 )     (BLDALPHA: eva bits0-4, evb bits8-12)

per channel, in 5-bit exactly as the hardware does. bgr555 expansion
(v<<3 | v>>2) is losslessly reversible by >>3, so the framebuffer's 8-bit
channels round-trip to the DS's 5-bit blend and back with no error.

An OBJ in mode 1 (semi-transparent) is ALWAYS a 1st target and ALWAYS
alpha-blends regardless of BLDCNT's first-target bits -- this is what makes
dScMgCurling_c's tint render, because its BLDCNT puts NO first-target BG bits up
(engine A 0x0d40, engine B 0x0440) and the effect fires only through the mode-1
shadow sprite. With no 2nd target beneath it a semi-transparent OBJ draws opaque,
as on hardware.

Window colour-effect gating: bit 5 of the window masks enables/disables the
effect per region; the blend is gated on (window_mask & 0x20) in both files.

BLDCNT layout (from the ROM's own G2x::SetBlendAlpha, src/_ZN3G2x13SetBlendAlpha
EPVttttt.cpp: *reg = ((a|0x40)|(b<<8)) | ((c|(d<<8))<<16), a=1st, b=2nd, c=eva,
d=evb, the 0x40 forcing mode bits 6-7 to 01):
  bits 0-5   1st-target select (BG0,BG1,BG2,BG3,OBJ,BD)
  bits 6-7   mode: 0 off, 1 alpha, 2 brightness-up, 3 brightness-down
  bits 8-13  2nd-target select

ESCAPE HATCH: SM64DS_BLEND_OFF=1 restores the old opaque path in both files
(read once via getenv, static-cached). Same binary, same .dsstate base, so a
before/after is the only comparison notes/port-selftest-bmp-gate.md permits, and
any regression bisects against the pre-blend image.

THE FADER DOUBLE-APPLY RULING (mission item 4)
----------------------------------------------
BRIGHTNESS (BLDCNT mode 2/3 + BLDY) is NOT applied by this unit. It is owned by
the existing fade path, and applying it here too would double every fade.

Derivation, from the code:
  * hal/fader_wipes.cpp HalFaderWipe::AdvanceFade writes BLDCNT mode 2 (white /
    brighten) or 3 (black / darken) + BLDY on BOTH engines via
    G2x::SetBlendBrightness at 0x40000{50,54} and 0x40010{50,54}, first-target
    0x3f. It NEVER writes BLDALPHA (0x52) and NEVER mode 1.
  * port_fader_blend_state() reads the RAW engine-A BLDCNT/BLDY (0x4000050/54)
    and returns evy+toWhite; walk_window's fade composite then dims the whole
    top framebuffer. So ANY engine-A mode-2/3 write is already applied globally.
  * The sub screen's fade is applied downstream too: ppu_compose_stacked's evy
    (engine A's) on the bottom half, and the corner panel inside walk_window's
    fade composite. ppu_scanout_sub separately applies MASTER_BRIGHT (0x6C), a
    different register the fader does not touch.
So the mode field partitions ownership cleanly: the game writes mode 1 for alpha
effects and mode 2/3 only for fades. blend_apply() returns the top pixel
unchanged for any mode != 1 (and for a semi-OBJ with no 2nd target), so a fade
frame is a provable no-op here.

PROOF (measured): scene 1 (SCENE_TITLE) runs an active BLDY brightness fade --
SM64DS_PPU_AUDIT over 60 frames read engine A BLDCNT 0x00bf (mode 2) / 0x00ff
(mode 3) with BLDY ramping 0x0f,0x0e,0x0d,0x0c,0x0b,0x0a and BLDALPHA 0x0000, on
both engines. Captured with SM64DS_SCENE_BMP at mid-fade frames 3, 5, 8 and 12,
blend ON vs SM64DS_BLEND_OFF=1:

  scene1 @frame 3    on-vs-off diff = 0 bytes
  scene1 @frame 5    on-vs-off diff = 0 bytes
  scene1 @frame 8    on-vs-off diff = 0 bytes
  scene1 @frame 12   on-vs-off diff = 0 bytes

Byte-identical while a fade is visibly progressing = the blend unit does not
touch the fade. (A second inertness check: level 1 boot frames 0..25, dumped
with SM64DS_DUMP_FROM/TO, vary hugely frame-to-frame as the 3D scene loads yet
are byte-identical ON vs OFF on all 26 frames.)

OBJ-VS-OBJ PRIORITY: THE TWO CURLING LAYERING BUGS (run link60, lane BLND2)
================================================================================

The owner playtested the shipped blend (0.2.8) in curling (scene 374,
dScMgCurling_c) and found two layering faults, both on the BOTTOM screen:
  1. the light-blue shadow tint drew OVER the bumper (the cursor/aim bar), which
     should render in front of the tint, untinted;
  2. the snow changed texture where it crossed a shell.

BOTH ARE ONE DEFECT, AND IT IS ON ENGINE B (ntr/ppu_sub.cpp). Measured on the
shot frame with SM64DS_PPU_AUDIT (scene 374, the shot driven by the in-exe
SM64DS_CLICK_TEST scripted stylus "256,724>256,584@100-119" in a focused
SM64DS_SCENE_WINDOW=1 run):

  engine A (top screen): mode-1 OBJ count 0 on all 160 samples. NOTHING blends
    on engine A in curling, so hal/message_compositor.cpp is not involved and
    was not touched.
  engine B (bottom screen): BLDCNT_B 0x0440 (mode 1 alpha, first-target NONE,
    2nd target BG2), BLDALPHA_B 0x1002 (eva 2/16, evb 16/16), and 5 mode-1
    semi-transparent sprites/frame. Only BG2 (priority 2) is enabled; every
    other playfield element is an OBJ. The blue tint is the semi shadow sprite
    alpha-blending over BG2.

  OAM (engine B, measured):
    shells   normal (mode 0) priority 1   OAM index 0,2,4,6,8
    shadows  SEMI   (mode 1) priority 2   OAM index 1,3,5,7,9   (the blue tint)
    cursor/  normal (mode 0) priority 0   OAM index 10,11        (the "bumper")
      bumper bar
    snow     normal (mode 0) priority 0   OAM index 13..60

THE RULE THE PORT HAD WRONG. raster_obj wrote g_obj[py][px] UNCONDITIONALLY as
it walked OAM 127->0, so the lowest OAM index always won -- pure index order,
"regardless of priority" as the old header note here even said. The DS does NOT
do that. OBJ-vs-OBJ is resolved by PRIORITY first, the lowest priority NUMBER
winning, and OAM index only breaks a tie. This is melonDS's DrawSpritePixel
verbatim (GPU2D_Soft.cpp): walking OAM 0->127 it overwrites iff the new pixel is
opaque AND (the slot is empty OR new prio < old prio). GBATEK's OBJ notes say the
same: a sprite's priority field orders it, index is the tiebreak.

  Bug 1: the shadow (prio 2, OAM 1) and the shell body (prio 1, OAM 0) both have
         a LOWER OAM index than the cursor bar (prio 0, OAM 10-11), so the old
         index-order write drew them over the bumper -- the semi shadow then
         alpha-blended over BG2 there, punching a blue notch through the bumper's
         gold outline. Priority order makes the prio-0 bumper win: it draws
         opaque, in front, and the tint only appears where the semi shadow is
         genuinely the top-relevant OBJ (which is what the DS does).
  Bug 2: the shell (prio 1, OAM 0) has a lower OAM index than the snow
         (prio 0, OAM 13+), so the old write drew the shell over the snow;
         the snow took the shell's texture wherever it crossed one. Priority
         order makes the prio-0 snow win -- it stays snow over a shell.

THE FIX (ntr/ppu_sub.cpp, raster_obj, ~6 lines). Before writing g_obj, skip if a
better-priority sprite already owns the pixel:

    if (g_obj[py][px].hit && prio > g_obj[py][px].prio) continue;

For the 127->0 walk this is exactly melonDS's "empty || new <= old": `<=` keeps
the lowest index on a tie (a lower-index sprite is processed later and overwrites
an equal-priority one), and a strictly-better priority wins whatever the index.
The resolver and blend_apply already read g_obj.prio/.semi, so the sprite that
wins by priority now drives the blend. NOT gated by SM64DS_BLEND_OFF: this is OBJ
resolution, not the alpha effect, so it applies to the OFF and ON paths alike and
the OFF-vs-on comparison stays contained to the curling blend region.

2. THE DIVERGENCE
-----------------

hal/message_compositor.cpp's raster_obj walked OAM 127 -> 0 and wrote
g_a[py][px] UNCONDITIONALLY for every opaque texel, so the lowest OAM index won
whatever the priorities were. Its own comment recorded the gap
("raster_obj still draws sprites over every BG regardless of priority, which is
a separate gap and not this lane's") and so did
port/ov004_ov007_2d_map.txt section 7 h and i.

The DS resolves OBJ-vs-OBJ by PRIORITY first -- attribute 2 bits 10-11, lowest
number in front -- and uses the OAM index only to break a tie. One OBJ pixel
exists per screen pixel, so a sprite that loses contributes nothing: not a
colour, not a semi-transparent flag. Both shell games put the SNOW at priority 0
and the HIGHEST OAM indices, the shells at priority 1 and the reflections at
priority 2 on the LOWEST indices, so index order inverted the whole stack.

THE SECOND HALF OF THE DEFECT IS THE ONE THE OWNER'S WORDS NAME. When the
reflection won a pixel it also BLENDED against whatever was in g_a at that
moment, and that was the sprite it had just covered. The test
"bl.second & (1u << owner)" with owner = kOwnerObj reads BLDCNT bit 4, which
0x0d does not set, so the blend did not fire and the reflection's own texel was
written OPAQUE over the snow. That is "it changes the color of the things
passing it" literally: the snow's white became the reflection's outline colour.


3. THE FIX (hal/message_compositor.cpp, raster_obj, one test)
-------------------------------------------------------------

    if (!objprio_off && g_a[py][px].hit
        && g_a[py][px].owner == kOwnerObj
        && prio > g_a[py][px].prio)
        continue;

ntr/ppu_sub.cpp's line for the 127 -> 0 walk, with ONE addition: the owner test.
g_a is a shared buffer that already holds background pixels with their own
priorities, and a sprite must not lose to a background here. OBJ-vs-BG is a
different hardware rule (a sprite beats a background at EQUAL priority and loses
only to a strictly better number), it is still not implemented in this file, and
folding it into this test by dropping the owner check would move every scene in
the game instead of the ordering this fixes. It stays in the gap list.

SM64DS_OBJPRIO_A_OFF=1 restores the unconditional write on the same binary.

ONE DIVERGENCE REMAINS AND IS NAMED IN THE CODE: a semi sprite that WINS this
test over an already-written sprite pixel still blends against that loser's
colour rather than against the 2nd-target layer below the whole OBJ layer, which
this file does not keep.

TWO SHAPES REACH IT, NOT ONE. This paragraph used to name only the first, and
run mg8's reviewer was right that the scope was too narrow:

  * a semi OBJ whose priority is at least as good as a NORMAL OBJ it overlaps;
  * TWO SEMI-TRANSPARENT OBJs AT EQUAL PRIORITY overlapping each other. The
    lower-index one wins the tie, finds an OBJ pixel already written
    underneath, and since BLDCNT_A names no OBJ second target it writes
    opaque. The shell games' reflections are all priority 2, so the first
    shape never fires here -- but they are semi-transparent and they do
    overlap, which is exactly the second shape.

NEITHER IS A REGRESSION. The old unconditional path did the same thing in both
cases, so this fix does not make either one worse or more frequent; the wording
above was narrow, the behaviour was not. Closing it means resolving OBJ into its
own buffer the way ntr/ppu_sub.cpp does.

The .dsstate section lands at the same base (0x83B000, size 0xEA3C9) before and
after this change, so notes/port-selftest-bmp-gate.md permits the cross-binary
byte compares as well as the one-binary A/B.

TWO NUMBERS DESCRIBE THIS SECTION AND THEY DIFFER BY ONE. Run mg8's reviewer
read the span as 0xEA3C8 and filed the digit above as an off-by-one; the merge
checked it and the digit above is RIGHT. Both numbers are correct measurements
of different things, so the next reader gets them both rather than re-deriving:

  0xEA3C9  the PE section's VIRTUAL SIZE, which is what dumpbin /headers prints
           for .dsstate and what the parenthetical above quotes alongside the
           section's virtual address;
  0xEA3C8  &dsstate_hi - &dsstate_lo, the CAPTURED PAYLOAD SPAN, which is what
           tools/dsstate_guard.py prints as "[lo, hi)" and what lk6_savestate
           copies.

The difference is the fence itself. hal/dsstate_seg.cpp declares both sentinels
as `char` -- one byte each -- with dsstate_lo in .dsstate$aaa and dsstate_hi in
.dsstate$zzz, so dsstate_hi is the section's LAST BYTE and sits one byte inside
the section's end. This build's map:

    0004:00000000  _dsstate_lo  00c3e000
    0004:000ea3c8  _dsstate_hi  00d283c8      section virtual size 0xEA3C9

Quote whichever you mean and say which; do not "fix" one into the other.

AND THE BASE ABOVE IS THIS LANE'S BUILD, NOT THE MERGED TREE'S. On the mg8
merge tip .dsstate is at RVA 0x83E000, moved 0x3000 by the OTHER two lanes'
code, and the SIZE is unchanged at 0xEA3C9. That does not weaken the sentence:
its load-bearing claim is that the base and span are the SAME before and after

================================================================================
OBJ-VS-BG: THE HALF SGX LEFT OPEN, AND WHAT IT COSTS
(run mg10, lane RGX)
================================================================================

SGX above fixed sprite-against-sprite on engine A and said, in the code and in
this file and in port/ov004_ov007_2d_map.txt section 7 j, that sprite-against-
BACKGROUND was a different rule it was deliberately not taking. This is that
rule.


1. THE RULE, CITED RATHER THAN INFERRED
---------------------------------------

GBATEK, OAM attribute 2, names the field the sprite is ordered by: bits 10-11
are the "Priority relative to BG (0-3; 0=Highest)". The same page settles the
tie in the sprite's favour -- when a sprite's priority equals a background
layer's, the sprite "becomes higher priority and is displayed on top of that BG
layer". GBATEK's BGxCNT page gives the backgrounds' own field the same shape
("BG Priority (0-3, 0=Highest)") and breaks BG-against-BG ties by index: at
equal priority BG0 is in front and BG3 behind.

So a sprite loses to a background ONLY when the background's priority NUMBER is
strictly smaller. The test is `<`, not `<=`, and getting that backwards would
hide every sprite that shares a priority with a background it is meant to sit on
top of.

THE THREE BG-AGAINST-BG HALVES WERE ALREADY RIGHT and are not touched: the BG
loop in hal/message_compositor.cpp walks prio 3 -> 0 and, within a priority,
BG3 -> BG0, so the last background to write a cell is the frontmost one. That is
why comparing the sprite against ONE cell answers the whole layer -- the cell
holds the background the hardware would have shown.

THE 3D LAYER IS THE SAME RULE AND WAS ALREADY IMPLEMENTED. With DISPCNT bit 3
set BG0 IS the 3D engine's output, so "OBJ against the 3D layer" is "OBJ against
BG0" and the tie still goes to the sprite. read_bg disables BG0 exactly then, so
no hit-buffer cell is ever owned by it and the new test cannot see it; the
comparison happens at the final blit instead, in layer_behind_3d, whose OBJ arm
is `prio > p3d`. Strictly worse loses, equal wins. Nothing about the 3D layer
moves in this lane, and this paragraph exists because a reader who finds the new
test and not that one would conclude the 3D case is missing.


2. THE CHANGE (hal/message_compositor.cpp, raster_obj, one test)
----------------------------------------------------------------

    if (!objbg_off && g_a[py][px].hit
        && g_a[py][px].owner != kOwnerObj
        && g_a[py][px].prio < prio)
        continue;

BESIDE SGX's test, NOT INSIDE IT. The two are different rules with different
ties -- sprite-against-sprite keeps the last writer on a tie, sprite-against-
background gives the tie to the sprite -- and they get separate kill switches so
a lane bisecting a changed frame can switch off one without the other:
SM64DS_OBJBG_OFF=1 here, SM64DS_OBJPRIO_A_OFF=1 there.

WHAT IT ALSO FIXES, WITHOUT BEING ABOUT BLENDING. The semi-transparent OBJ path
blends against whatever g_a holds, and before this test that could be a
background IN FRONT of the sprite -- a blend against a layer the hardware would
never have put underneath it. Those pixels are skipped outright now.

SM64DS_OBJBG_PROBE=x,y is the per-pixel transcript this lane's evidence is taken
with. Section 4 of the mg8 write-up above took the same reading by hand-patching
raster_obj for one run; keeping the probe means the next lane needs no patch. It
prints, for one DS pixel: what the BG loop left there, one line per OAM entry
that reaches it with what each of the two OBJ tests decided, and the 2D result.


3. THE TOGGLE IS HONEST, PROVEN THE SGX WAY
-------------------------------------------

.dsstate lands at the SAME base AND the same span before and after this change,
[0xc5c000, 0xd463d0), 959440 bytes, so notes/port-selftest-bmp-gate.md permits
the cross-binary compare as well as the one-binary A/B.

Tip binary with SM64DS_OBJBG_OFF=1, against a base build made in the same
worktree from clean c941e1855: all 23 hosted scenes and the level-1 selftest
BYTE-IDENTICAL, 24 rows of 24, zero differing. The switch restores the old
compositor exactly.

Engine A on the IDLE scene runs DISPCNT 0x00001d00 (bit 3 clear, BG0/BG2/BG3/OBJ

SO THE SPRITES ARE NOT WHAT BROKE. BG0's curtain was burying both artwork layers

6. WHAT THIS DOES NOT CLOSE
---------------------------

A 1st-target BG blending over the OBJ layer. The BG loop runs entirely before
raster_obj, so g_a never holds an OBJ pixel while a background is being
composited, and BLDCNT naming OBJ as a 2nd target under a BG 1st target cannot
fire. Pre-existing, unchanged by this lane, and it needs the same fix the
remaining semi-OBJ divergence needs: resolving OBJ into its own buffer the way
ntr/ppu_sub.cpp does.

SCENE 370's BOMB MARCH: THE COMPOSITOR IS NOT WHY IT DOES NOT DRAW
(run mg10, lane RGX)
================================================================================

hal/scene_mg_bomroom.cpp section 9 records, from run mg8, that the seeded
bin-full repro reaches the carry with the counter advancing while "the central
play field is BLACK and no bombs are drawn in it", and that lane SGX's engine-A
OBJ priority fix was the plausible cure and was not the cure. This lane put the
OBJ-vs-BG rule in as well, re-ran the same repro, and it is still not the cure.
What follows is where it actually is, so the next lane does not spend another
run on the raster.

THE ARMS FIRST. SM64DS_SOS_FILL=40 + SM64DS_SOS_TRACE=1, top capture, ON vs
SM64DS_OBJBG_OFF=1: f380 1708 px, f450 4908 px, f560 1720 px -- and the black
field is IDENTICAL in both arms. The rule does not touch it. The trace says the
march is running: t374 top=3 sub=2, all forty bombs at state 6 substate 4.

1. THE BOMBS ARE OBJ, ON BOTH ENGINES. src/func_ov004_020afdd0.cpp is the
   framework plotter -- OAM::Render at y + 0xc0 + G for the top engine and
   OAM::RenderSub at y for the bottom, the RenderOamBothScreens shape.

2. THEY ARE NOT IN ENGINE A's OAM IN THAT REPRO, AND THE SEED IS WHY.
   src/func_ov006_020d7524.c is the bomb renderer, reached from Render slot 9,
   and it opens `if (self->e[i].b699 == 0) continue;` -- byte +0x4699. The ROM
   sets that byte in func_ov006_020d8324, the spawn-delay state, which counts
   +0x4690 down and then writes +0x4699 = 1, +0x4694 = 1, +0x4697 = 1.

   sos_binfill writes +0x698, +0x697, +0x69b, +0x69c, +0x69d, +0x690, +0x692,
   +0x696, +0x670, +0x688, +0x68c, +0x660 and +0x664 -- every field
   func_ov006_020d8408 writes, which is exactly what its header promises -- and
   then calls the ROM's drop handler, which parks the bomb at +0x697 == 5. The
   delay state never runs, so +0x4699 is never set, so no seeded bomb is ever
   submitted. The seed jumps a bomb from "just spawned" straight to "parked in a
   bin" and skips the state that turns its drawing on.

   MEASURED, by a temporary edit made, read and reverted: adding +0x699 = 1 and
   +0x694 = 1 to the seed takes engine A's OBJ ownership at f380 from 2956 px to
   13475 px. The bombs draw. Nothing in the compositor changed.

   THE ONE-LINE HANDBACK, for whoever owns hal/scene_mg_bomroom.cpp: in
   sos_binfill, beside the existing +0x698/+0x697 writes, add
       *(unsigned char *)(b + 0x699) = 1;
       *(unsigned char *)(b + 0x694) = 1;
   which is what func_ov006_020d8324 writes when the delay it seeds expires.
   NOT taken here: that file is not this lane's.

3. THE BLACK FIELD IS BG2 SCROLLING OFF, AND THE ROM DRIVES IT.
   src/func_ov006_020d5b10.c state 1 does `+0x62dc += 0x3000` per frame and
   `SetBg2Offset(0, +0x62dc >> 12)`, up to 0xc0 = 192, then clamps. BG2CNT 0x9411
   is a 32x64 map -- 256x512 px -- whose content ENDS at map row 191. Read off
   the strip probe across the whole ramp:

     rows  24..191   5120/8192 opaque      (flat, the field)
     rows 189..220    480/8192 opaque      (the last of it leaving)
     rows 192..223      0/8192 opaque      (empty map)

   so at vofs 192 BG2 owns 0 px and BG3 -- priority 2, 8192/8192 opaque, 74.5%
   near-black there -- is what shows. Probed at DS(150,100):

     f380  BG loop left BG2 prio 1 colour cecece
     f560  BG loop left BG3 prio 2 colour 000000

   The compositor draws what the registers and VRAM say, on both frames.

4. AND THE ROM ITSELF STOPS DRAWING THE MARCHING BOMBS. At the clamp,
   func_ov006_020d5b10 calls func_ov006_020d8904, which writes +0x699 = 0 on
   every bomb in state 6. With the seed corrected, engine A's OBJ ownership runs
   13275..14290 px through f442 and falls to 2956 px by f506, centred on that
   clamp.

STILL OPEN, AND IT IS A CARTRIDGE-DATA QUESTION RATHER THAN A RASTER ONE:
whether BG3's near-black centre is what a real DS shows once the field slides
off. That is scene 366's shape -- compare BG3's tiles and palette against the
ROM's own files, the way run mg5 lane WREND settled the Luigi curtain -- and it
is not answerable from this side of the compositor.
