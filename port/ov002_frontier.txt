=====================================================================

Run linkw wave C, lane cat-ov002, worktree branch cat-ov002 off 459f21a07.
Every number below was read out of this worktree's own build:

    baseline   4888 / 11243 linked, battery ALL GREEN, exe 702f3357...
    after      4892 / 11243 linked, battery ALL GREEN, exe c13bbec7...

WHAT LINKED, AND WHY THOSE FOUR
-------------------------------
Gate 204 seated slot 17 -- the deleting destructor -- on four classes the port
already fills: Coin, HealingHeart, the Cap and PushBlock. Three of them were on
bw_trap17 and PushBlock had the member chain typed out by hand in a host thunk.
The bodies were matched, flat C, unmarked and fully closed; what they lacked was
a reference edge, and the ROM's own vtable word is the honest place for one.
See slice_gate204.txt for the derivation.

That gate supersedes port/slice_w1l1.txt section (2), which declines slot-17
seats -- Coin's by name -- on the grounds that the trap is a diagnostic and
seating it buys a double free. The distinction w1l1 does not draw is that
bw_trap17 declines SOFT into the quarantine net while the Player's ps_trap
aborts HARD, and that the binary-wide slot-17 dispatch count is measurably
zero. The going-forward rule, with the measurement and its positive control,
is written out at the bottom of slice_gate204.txt. Cite that one, not both.

HOW THE REMAINING 401 SPLIT
---------------------------
Method: a TU's ROM address comes from config/arm9/overlays/ov002/symbols.txt;
every ov002 relocation whose `to:` is that address and whose `from:` lands
inside a data object is a table word; a table is HOSTED when a port/hal or
port/unmatched file declares it as an array or names it as data_ov002_*; a
pointer-to-member object is one whose cxx_aliases spelling carries the `@@3P8`
member-function mangling.

THE BUCKETS ARE ORDERED AND EACH TU IS COUNTED ONCE, so the counts are only
reproducible next to the order. It is, first match wins:

     1  host copy defining the Itanium name
     2  host copy defining the MSVC-mangled name
     3  inferred-stub marker
     4  MSVC-method form (the source defines Class::Method, not a C body)
     5  word in a hosted vtable
     6  word in a pointer-to-member record
     7  word in a vtable the port does not host
     8  nothing above -- a plain callee

A TU can qualify for several. _ZN4CoinD1Ev is both an MSVC-method form and a
hosted vtable word, and lands in 4 because 4 is the binding constraint: no
slice line reaches a body MSVC will not compile against the host seams. Read a
bucket as "the first thing that has to change", not as "the only thing true of
it".

  167  vtable slot on an UNSEATED class
   97  plain callee -- no vtable word names it; it links when its caller does
   48  MSVC-method form (a real C++ method or destructor, not a C body)
   29  HOST-COPY, Itanium name -- already in linkage.py's replacement queue
   28  INFERRED-STUB -- the ratchet holds it out
   14  mwcc PMF record -- needs a states seat
   10  hosted vtable slot, blocked on one placeholder binding
    7  HOST-COPY, MSVC name -- INVISIBLE to linkage.py's queue
    1  hosted vtable slot, seatable (Player D0; deliberately trapped, below)

THE THREE FINDINGS WORTH CARRYING FORWARD
-----------------------------------------

1. THE ov002 VTABLE-TAIL FRONTIER IS INFERRED-STUB BODIES, NOT PORT WIRING.

   Two seats in hal/actor_classes.cpp record their own tail slots as ready
   follow-ups: SIGN_POST's header says slots 21/22/27/31 are "matched in src and
   in no slice", and BLACK_BRICK_BLOCK's says slot 23 "stays on ac_trap23 only
   because its real body is not sliced yet -- seating it is a follow-up".

   Every one of those six bodies -- func_ov002_020bb27c, 020bb23c, 020bb374,
   020bb3b8, 020b3788, 020b36dc -- carries the `recovered from vtable slot
   identity` marker, so seating any of them fails port/tools/
   inferred_stub_guard.py. So does every other unlinked ov002 body the ROM's own
   words put in a hosted table's tail. The follow-up those comments describe is
   not a slice line; it is decompiling six guessed bodies.

   A SECOND CORRECTION TO THE SAME COMMENT. BLACK_BRICK_BLOCK's header rules
   slot 22 blocked because its body reaches slot 31 through `fn(c)`, a cdecl
   call, while the seated slot 31 is __fastcall -- and rules slot 23 unblocked
   because its DISPATCHER is now thiscall. Slot 23's BODY has the same defect as
   slot 22's: src/func_ov002_020b3788.cpp declares
   `struct Vt { int dummy[0x7c/4]; void (*fn)(void*); }` and calls
   `(*(struct Vt**)c)->fn(c)`, which MSVC emits as a cdecl call through a
   function pointer onto the __fastcall bbb_kill at slot 31. Seating slot 23 as
   the comment suggests would introduce exactly the bug the comment attributes
   to slot 22. Slots 24 (020b36dc) and 27 (020b36b4) use a C++ virtual call and
   would be convention-clean -- they are held out only by the marker.

2. linkage.py's REPLACEMENT QUEUE CANNOT SEE HOST COPIES THAT DEFINE ONLY THE
   MSVC-MANGLED NAME.

   The queue matches a map symbol against the set of matched TU stems, and a
   stem is an Itanium name. A host copy that compiles a real C++ method defines
   `?Behavior@Player@@UAEHXZ`, which is not any TU's stem, so the pair is never
   examined. Ten ov002 matched TUs are shadowed that way today:

     _ZN3HUD13InitResourcesEv          HUD_InitResources.cpp
     _ZN6Player11ChangeStateERNS_5StateE   reverse_bridges.cpp
     _ZN6Player12St_Jump_MainEv        Player_St_Jump_Main.cpp
     _ZN6Player12St_Swim_MainEv        method_faces.cpp -> Player_SwimMain.cpp
     _ZN6Player16CleanupResourcesEv    Player_CleanupResources.cpp
     _ZN6Player16St_WallJump_MainEv    Player_St_WallJump_Main.cpp
     _ZN6Player17St_NoControl_InitEv   Player_St_NoControl_Init.cpp
     _ZN6Player8BehaviorEv             Player_Behavior.cpp
     _ZN8PathLift12BaseBehaviorEv      PathLift_StateDispatch.cpp
     _ZN9OneUpLogo13InitResourcesEv    OneUpLogo_InitResources.cpp

   Each host file's header documents a real host-ABI reason (the mwcc
   pointer-to-member dispatch over DS code words, the TextureSequence::Prepare
   argsweep seam, the GetHealth receiver seam), so these are exceptions rather
   than work.

   THREE OF THE TEN ARE ALREADY IN THE QUEUE, and the queue is not as blind as
   a first read of this list suggests. ChangeState, St_Swim_Main and
   CleanupResources each have a companion host object that ALSO defines the
   Itanium spelling -- Player_ChangeState.cpp, Player_SwimMain.cpp and
   method_faces.cpp respectively, all three visible in walk_window.map -- so
   the queue sees them by name and, each being PORT_HOST_ABI tagged, files them
   under EXCEPTIONS. That is the queue working.

   SEVEN are absent from all three columns, and seven is the actionable number
   for a demangling fix. It is the same seven this file's own bucket table
   counts under "HOST-COPY, MSVC name".

   PORT_HOST_ABI TAGS ARE NOT THE MISSING PIECE, and an earlier draft of this
   file said they were. The tag is not rare in these files: method_faces.cpp
   carries seven, PathLift_StateDispatch.cpp carries two, and one of those two
   sits directly above BaseBehavior. It is inert there only because MSVC
   inlined the forwarder and /OPT:REF dropped the external, which is the
   folded-away-face case method_faces.cpp's own header warns about at length.
   So the gap is the queue's name matching, not missing documentation: tagging
   the other seven changes nothing while a tag is only consulted for a symbol
   the queue already asked about. The fix is to make the queue demangle, or to
   have each host copy also carry the Itanium spelling the way the three above
   do.

3. func_ov002_020bd664's POINTER-TO-MEMBER TABLE IS LIVE AND UNSEATED.
   UNPROVEN AT RUNTIME -- stated as a shape read off the source and the map,
   not as an observed fault.

   src/func_ov002_020bd664.cpp is linked (slice_gate10) and reached from
   src/func_0200e5ac.c, which is also linked. It builds a 14-entry array of
   mwcc pointers-to-member out of data_ov002_0210a054 .. 0x0210a534 and calls
   `(self->*table[p[6]])(p + 7, a2, a3)`. Those fourteen objects are mounted
   ov002 data whose first word is a DS code address, and MSVC's
   single-inheritance member pointer is that one word, so the call goes to a DS
   address inside the mapped overlay image. That is the same shape as the
   walljump crash port/unmatched/Player_St_WallJump_Main.cpp was written
   against; no port_*_states_seat covers this table.

   The fourteen bodies those records name are all in the unlinked set
   (func_ov002_020bccfc, 020bcd18, 020bcd38, 020bd20c, 020bd250, 020bd354,
   020bd3a0, 020bd438, 020bd45c, 020bd480, 020bd4ac, 020bd4c8, 020bd4e0,
   020bd600), so a seat over this table both closes a latent wild call and
   links fourteen TUs. It was not taken here: it needs the SignPost/Coin
   states-seat treatment with per-record byte checks, and it sits next to the
   level object loader, which is another lane's file this wave.

WHAT IS ONE BINDING AWAY
------------------------
Five classes have a trapped slot 17, a matched flat-C D0 body, and every callee
already linked. The only blocker is that the body spells its own vtable as the
bare placeholder `VT`, which cxx_aliases binds ONCE, to data_ov002_021081e4.
Each needs one per-source COMPILE_DEFINITIONS line, which belongs to the actors
lane this wave. `HEAP` needs nothing -- it is already bound to data_020a0eac,
which is what all five want.

    src/_ZN10BrickBlockD0Ev.c            VT=_ZTV10BrickBlock
    src/_ZN11VirtualDoorD0Ev.c           VT=_ZTV11VirtualDoor
    src/_ZN18PoppingLavaBubblesD0Ev.c    VT=_ZTV18PoppingLavaBubbles
    src/_ZN19AmbientSoundEffectsD0Ev.c   VT=_ZTV19AmbientSoundEffects
    src/_ZN8MugenBgmD0Ev.c               VT=_ZTV8MugenBgm

Two more want a host object rather than a -D: src/_ZN10StarSwitchD0Ev.c and
src/_ZN11CannonHatchD0Ev.c both store _ZTV10dBgActor_c, the shared base table,
which nothing in the port defines. Their own class tables are already aliased
(daObjSwitch_c, daObjCannonShutter_c); dBgActor_c is a real second table and
wants a mount, not an alias onto one of theirs.

WHAT IS DELIBERATELY LEFT ALONE
-------------------------------
_ZN6PlayerD0Ev is the one hosted slot with a clean body and no binding problem,
and it stays unlinked on purpose. hal/level_boot.cpp seats slot 17 of
data_ov002_0210a83c on ps_trap and says why: the ROM's teardown never dispatches
the deleting form, so a call arriving there means something reached the Player
through `delete`, "which is a bug worth an abort rather than a double free".

This is the same reasoning gate 204 supersedes for the three soft traps, and it
survives here for the reason the new rule turns on: ps_trap calls std::abort(),
so it is a live misuse detector rather than a bounded decline into the
quarantine net. Losing it costs the first-failure stop; losing a bw_trap17
costs a diagnostic for a call site the sweep proves does not exist. Lane l5
made this call before and it stands. +1 on the headline is not worth the trade;
anyone who wants it should reverse the rule deliberately rather than notice the
inconsistency and close it the easy way.

THE PLAYER STATE MACHINE, ANSWERED FOR THE COORDINATOR
------------------------------------------------------
Five St_ bodies are in the ov002 unlinked remainder. None is a switch case that
was never wired and none is a state no selftest enters:

  St_Jump_Main, St_WallJump_Main, St_NoControl_Init
      hal/player_states.inc HAS the case and it calls the MSVC method; the
      method is defined by the host copy in port/unmatched, so the matched TU
      would be a duplicate definition. Blocker: the per-character PMF rows hold
      DS code words and the matched source calls them as plain function
      pointers.
  St_Swim_Main
      same, one level further out: method_faces.cpp defines the MSVC method as
      a face onto the Itanium name and port/unmatched/Player_SwimMain.cpp
      defines that, PORT_HOST_ABI tagged for the GetHealth receiver seam.
  _ZN6Player18St_LevelEnter_MainEv
      on slice_gate10.txt and /OPT:REF-stripped. The port does not route
      through this name at all: player_states.inc case 0x020c6f3c calls
      func_ov002_020c6f3c, because the community Player symbol at that address
      is the one the port distrusts. A naming question, coordinator-routed, not
      a wiring gap.

The remaining 167-in-unseated-classes half is also, in part, a naming problem
rather than a port one. InvisiblePole, InvisibleSecret, Seaweed, WaterfallMist
and PoppingLavaBubbles all carry config names that belong to a DIFFERENT ROM
class than the actor the port seats -- hal/actor_classes_bob_world.cpp derives
the shift by address at its head. So e.g. the seven _ZN13InvisiblePole* TUs are
not the class the port fills as INVISIBLE_POLE, and they will link when the
class they really belong to is mounted, not before.


================================================================================
VS MULTIPLAYER: WHAT ov002 STILL OWES (run mg16, lane MP3)
================================================================================

MP3 linked the ROM's multiplayer conductor and got two Player actors into one
world, driven by two processes, physically colliding. Two things it went looking
for in ov002 and did NOT find are recorded here rather than only in a lane's
status file, because this is where the next person will look.

1. THE VS STAR-STEAL LOGIC IS NOT LOCATED. In DS VS mode a player who is hit
   drops a star and the attacker can take it. Searched for and not found: no
   ov002 symbol matches a steal/drop/transfer shape, and the only VS star
   symbols in the tree are RENDER-side (the HUD's star count). The PvP hit
   consumer func_ov002_020d869c was read end to end -- it refuses any collision
   whose partner is not actor id 0xbf (Player) -- and it does not move a star.
   THIS IS AN OPEN QUESTION, NOT A MEASURED NEGATIVE: the search was by symbol
   name and by reading the hit path, not by tracing the star count backwards
   from its writer, which is what would settle it. Anyone picking up VS scoring
   should start there.

2. THE PER-PLAYER Ctrl SPLIT SYMBOLS CAP THE GAME AT TWO PLAYERS, and the cap
   is in the PORT, not in ov002. On the DS data_0209f4a0/a2/a4/a6/ac are
   interior addresses of the Ctrl block (data_0209f498 + 8/0xa/0xc/0xe/0x14,
   stride 0x18), which is why Player::Behavior reads its stick angle as
   `&data_0209f4a6 + data_020a0e40 * 0x18`. hal/auto_bss.cpp hosts them as five
   separate int[8] arrays, so that walk only lands correctly for slot 0 (offset
   zero) and slot 1 (+0x18, still inside 32 bytes). Slot 2 would write at +0x30,
   off the end. tests/walk_window.cpp REFUSES above two players loudly rather
   than corrupting a neighbour.
   THE FIX is to host the five as interior addresses of data_0209f498 the way
   hal/camera_bridges.cpp hosts the comms records. It is a band migration with a
   real regression surface: those symbols sit INTERIOR to .dsstate$mmm, so
   growing or moving them shifts every hosted global above them and retires
   every BMP baseline in the tree.

3. THE VS MODE FLAG IS DELIBERATELY OFF. data_0209f2d8 == 1 is not "two players
   are present", it is DS VS MODE, and eleven attack-cylinder wrappers in ov002
   branch on it (VS ground-pound radius 0x82000 against single-player's
   0x32000), as do func_ov002_020dd908's shockwave, Stage, StarMarker, the HUD
   and the fader. MP3 moved the player COUNT and left the mode alone, so two
   players run on mode-0 code that was already proven. Turning the flag on is a
   lane of its own and it wants ov075 (the VS menu) mounted first, because
   src/PrepareVsMode.c is what the ROM sets it from.
