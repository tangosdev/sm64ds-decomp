DEBUG MENU LEVEL-SELECT NAMES  (lane DBGNAME, run link60)
=========================================================

WHAT THIS COVERS
  The port's debug menu (port/tests/walk_window.cpp) has a "level select" row
  (MENU_LEVEL) that used to read as bare numbers -- row / level id / entrance /
  overlay -- with no readable level name. This lane gives each ROM level id a
  short player-facing name so the row reads e.g.

      level select  row  2/54   6 Bob-omb Battlefield  ent 13 ov014 MOUNTED

  The numeric level id stays as the prefix on purpose: this is a debug menu and
  the id is what a bug report quotes. The minigame row (MENU_MINIGAME) was
  already named from the ROM's typeinfo and is untouched.

WHERE THE NAMES COME FROM  (not invented)
  Primary authority: port_level_table[] in port/hal/level_boot.cpp. That table
  has 46 level ids, each DERIVED FROM THE ROM'S OWN OVERLAY DATA and documented
  per landing wave in that file:
      data_020758c8[id]  -> overlay id
      data_02092208[id]  -> the LVL_Overlay record
      SUBLEVEL_LEVEL_TABLE[id] -> course
      LVL_Overlay +0x08..0x0e  -> the four asset handles (bmd/kcl/icg/icl)
  Its leading name is the retail course name. The short forms in LEVEL_NAME[]
  are that name trimmed to fit the row.

  Cross-check: the ROM carries its OWN debug stage-name string pool inside ov003
  at 0x020b1060 ("BombHei Map", "Snow Mt", "Cave", "Habatake", "Suisou",
  "Horisoko", "Kaizoku Irie", "Battan King Map", "Teresa House", ...). These are
  the internal romanised names and match the parenthetical internal name on
  every id in port_level_table[], which is what pins each short name to the
  right id. (The pool is a string pool referenced by a pointer table that is
  not in ov003's static image, so it is used here as a cross-check on the id
  mapping, not as the display text -- the display text is the retail name.)

  A NOTE ON THE OWNER'S EXAMPLE: the task sheet's illustration "10 Bob-omb
  Battlefield" is not correct against the ROM. Level id 6 is Bob-omb
  Battlefield (bombhei_map, ov014); level id 10 is Cool Cool Mountain
  (snow_mt, ov018). The table below follows the ROM, not the example.

CONFIDENCE
  HIGH   = id + overlay + course proven from ROM data in port_level_table[];
           short label is the retail name trimmed.
  HIGH*  = same proof of id/overlay identity; the short label distinguishes a
           SUBLEVEL / second area and that wording is this lane's curation.
  MED    = real stage the ROM names, but NOT mounted in the port and so not
           independently re-derived here (only id 31).
  (none) = the port has no name; the row falls back to "(level N)". These are
           the ids port_level_table[] proves are NOT stages.

CORRECTION (VS wiring lane, run vs1)
  The "29, 42, 43, 51 -- there is no course behind them" reading above is
  WRONG for all four of those ids, and the evidence that corrects it is the
  ROM's own VS map list: data_ov075_0211c6ec, four signed bytes
  {0x33, 0x2b, 0x1d, 0x2a} = levels 51, 43, 29, 42, indexed by the lobby's
  map pick and handed straight to LoadLevelNoReturn by func_ov075_02116c8c
  (the matched VS start). They are the FOUR VS BATTLE MAPS. The name-handle
  observation stands -- their handles sit past the course-name space BECAUSE
  a VS map has no course name and no star select -- but the conclusion drawn
  from it does not. All four now have port_level_table[] rows (ov059, ov051,
  ov037, ov050) named "VS map 1..4" by list position; the derivation is
  port/slice_vs.txt section 4. Level 41 (test_map_b, null asset handles)
  keeps the old verdict.
