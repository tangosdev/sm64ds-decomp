# Scene boot, slice 1: dScStarSel_c, the STAR SELECT (scene id 4).
#
# ov003 is the smallest of the four occupants of the shared scene slot at DS
# 0x020ad660 (the others are ov002, the in-level engine the port has always
# run; ov004, the minigame framework; and ov007, the title and file select).
# It is 36 functions in 0x4240 bytes and carries three scene classes:
#
#     dScTitle_c     scene id 2   the debug level select
#     dScStarSel_c   scene id 4   the star select      <- this slice
#     dScGameOver_c  scene id 8   the game-over screen
#
# ONLY THE STAR SELECT IS HERE. The other two are derived, mapped and blocked;
# the block is named at the bottom of this file and it is not the mount.
#
# WHY THESE TUs LINK. The reference chain is the ROM's own and nothing here is
# a link root. The arm9 ACTOR_SPAWN_TABLE (0x02090864) relocates slot 4 to
# StarSelect_SpawnInfo (0x020b16b4); hal/scene_boot.cpp seats that record in
# data_020a4bb8[4] with its factory word repointed at the host factory, the
# same three statements hal/actor_registry.cpp makes for every other class. The
# class vtable is a host array the same file fills with the ROM's own slot
# contents, which is what names the seven bodies. Everything else here is
# reached from one of those eight entry points. Nothing in this slice is
# /include:'d and no alias points at it.
#
# WHAT DISPATCHES INTO IT AT RUN TIME. Scene::SetSceneToSpawn(id, param) parks
# the id in data_02092664; Scene::SpawnIfNecessary calls func_02013edc, which
# tail-calls func_02042fe4 -> func_02043098(id, 0, param, 1), and that is the
# spawn spine: it calls (*data_020a4bb8[id])(). Every function on that chain is
# a matched arm9 TU and all but Scene::SpawnIfNecessary were already linked.
# hal/scene_boot.cpp's port_scene_run drives the frame, reached from
# walk_window with SM64DS_SCENE=4.

# real body with declared arguments -- so it stays and is dispatched directly.

# ---- THE FOUR NONMATCHING TUs, named ---------------------------------------
# func_ov003_020ae358  near-miss from the DB (div=153)
# func_ov003_020ae6f4  dScStarSel_c::Render (div=51)
# func_ov003_020af038  dScStarSel_c::Behavior (div=112)
# func_ov003_020af8a0  dScStarSel_c::InitResources
# All four carry the decomp's own NONMATCHING header. They count as
# decompiled, not matched. port/tools/linkage.py counts them the way it counts
# any other TU in a slice -- a config function whose src TU is in the link set
# -- so a reader comparing this lane's linkage delta against the CONVERTED
# tier should subtract these four.
#
# ---- WHY dScTitle_c (id 2) AND dScGameOver_c (id 8) ARE NOT HERE -----------
# Both are fully derived: SpawnInfo 0x020b1380 / 0x020b1750, vtables
# data_ov003_020b1650 / data_ov003_020b179c, all eighteen slots read and
# recorded in port/ov003_syms.txt, factories func_ov003_020adc10 /
# func_ov003_020b1118, and every body has a src TU. Two things block seating
# them and neither is the mount or the chain:
#
#   1. ELEVEN of their fourteen slot bodies carry the marker
#      "recovered from vtable slot identity", so port/tools/inferred_stub_guard
#      refuses them until each is disassembled from the ROM and ruled, the way
#      the three star-select ones in port/tools/inferred_stub_adjudicated.txt
#      were. Mechanical, and eleven times the work this lane did for three.
#      (dScTitle_c: 020ada9c 020ada80 020ad814 020ad7a4 020ad7a0 020ad69c.
#       dScGameOver_c: 020b0b3c 020b0b34 020b0814 020b0810 020b05bc.)
#
#   2. THREE of the dtor TUs spell their vptr writes as PER-TU PLACEHOLDERS,
#      not as symbols: src/func_ov003_020ad660.c writes _ZTV10dScTitle_c /
#      _ZTV8dScene_c / _ZTV7dBase_c, src/func_ov003_020b0580.c writes
#      _ZTV13dScGameOver_c / the same two, and src/func_ov003_020b05bc.c writes
#      VT0 / VT1 / VT2 and deallocates against G0. None of those six names
#      exists in config; they are the decomp's own local stand-ins, and the ROM
#      words at those three sites are 0x020b1650 / 0x02092680 / 0x0208e4b8 (and
#      0x020a0eac for G0) -- read out of the image, the same values the
#      star-select pair spells correctly. Seating them needs the port's per-TU
#      placeholder treatment, which is its own gate.
#
# The scene id and the chain are identical for all three, so whoever takes them
# adds rows to port_scene_classes and to this slice, and changes nothing else.
