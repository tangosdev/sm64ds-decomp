THE 2D HARDWARE GAPS, MEASURED: WHICH ONES A LIVE SCENE ACTUALLY TOUCHES
Run link60 Stage 3, lane W2D. Base c7b44af04, gate GREEN 5533/11243 (49.2%).

port/ov004_ov007_2d_map.txt section 7 lists six clusters of DS 2D hardware the
ntr layer does not model, and says which of them "are candidates" for the title
screen and the minigame option screen. That list was written from what two
overlays' SOURCE pokes. This is the same question answered from runs.

The short version: NONE of the six clusters is live in any scene that runs
today. What the measurement did turn up is a different thing entirely -- a wrong
bit contract in the code that was supposed to be skipping one of them.


1. HOW IT WAS MEASURED, AND WHAT THE METHOD CANNOT SEE
-------------------------------------------------------

Two instruments, because one question is about values and the other is about
waiting.

  port/ntr/ppu_audit.cpp     samples both engines' whole 2D register file, the
                             OAM object-mode census and the touch hardware
                             surface at every scan-out. Env-gated on
                             SM64DS_PPU_AUDIT=<path>; inert otherwise.
  port/tools/ppu_reg_readers.py
                             sweeps src/ for every reader of those registers and
                             checks each hit against walk_window.map, so a
                             reader that is not linked is not counted.

WHY SAMPLING AND NOT INTERCEPTION. ntr/io.cpp maps real memory at the DS
addresses, so a 2D register store is an ordinary store to an ordinary page. It
does not pass through io_read/io_write unless the storing function happens to be
hostgen'd, and for the 2D surface that is the exception, not the rule. The proxy
table at the bottom of every run's output proves it. Level 1's whole proxied 2D
traffic over 900 frames is three rows, and all three are the same register:

    rd 04000060 w2 = 00000000  x1
    wr 04000060 w2 = 00000008  x900
    rd 04000060 w2 = 00000008  x899

That is 1800 accesses, but to DISP3DCNT and nothing else -- not one BGxCNT, not
one window or blend register, not one palette or OAM word. Scene 4's table is
empty outright. So the proxy sees essentially none of the 2D surface, there is
no seam to intercept at, and this is the same fact that forced L1's GXSTAT fix
to normalise the LATCH rather than a returned value.

WHAT SAMPLING SEES. The register state at scan-out, which is the state that
decides the image: the 2D unit reads these registers as it draws, and the port
has no scanline timing, so a value written and overwritten before scan-out
cannot reach the screen in either the port or the hardware.

WHAT IT CANNOT SEE. A mid-frame value that is gone by scan-out. And it cannot
tell "never written" from "written zero" -- but zero is the OFF state for every
register in the gap set (BLDCNT mode 0 is no effect, MASTER_BRIGHT factor 0 is
no change, MOSAIC 0 is 1:1, and the window enables live in DISPCNT bits 13-15,
which are sampled), so zero reads as "not in use" throughout. That is sound for
the question asked and is NOT sound for any question about writes.

THE SEAM. ppu_audit_sample is called from ntr::ppu_scanout_sub, which is the one
scan-out the live harness runs every frame, and it samples BOTH engines from
there. Engine A's live 2D path is hal/message_compositor.cpp, not ntr/ppu.cpp --
ppu_scanout is in no live path at all, because it fills the whole framebuffer
and would erase the 3D frame. Hooking the sub scan-out reaches engine A's
registers without touching a file this lane does not own.

READING OF THE TWO DISPCNTs.

  Bits 13, 14 and 15 are CLEAR: no window of any kind is armed. So the identity
  values sitting in BG2PA/BG3PA are inert -- in mode 0 those backgrounds are

  in the star select is sprites only.

  off during a level walk; the top screen is pure 3D. The stale BG2CNT/BG3CNT
  values are leftovers behind a disabled display.

  level 1 engine B = 0x40011803. BG mode 3 (BG3 extended affine), BG3 + OBJ on,

  ppu_sub.cpp models all of it -- the moving BG3PA/BG3X/BG3Y values in the table

4. SCENE 1 PRODUCES NO 2D MEASUREMENT, AND THAT IS THE MEASUREMENT
-------------------------------------------------------------------

SM64DS_SCENE=1 dies at c0000005 inside dScDSMT_c::InitResources, before the
frame loop starts. The audit file is never created: ppu_audit flushes on its
FIRST sample precisely so that "the seam never ran" (no file) is distinguishable
from "it ran and everything was zero" (a file full of zeros), and there is no
file.

So the title screen exercises zero 2D scan-out today and cannot demand any gap
on this list. Its blocker is port/ov007_seat.txt section 5's unmatched ROM body
func_ov007_020c9688, which is a decomp, not a port change and not a PPU gap.

This matters for prioritisation, because ov007 IS the overlay the gap list was
worried about, and the static sweep in section 5 finds it writing BLDALPHA and
MOSAIC. Those writers are real and they are unreachable. Implementing colour
special effects against them today would be building for a scene that cannot
run, and could not be tested by running it.

The window unit's linked writers are all modelled: ppu_sub.cpp and
message_compositor.cpp both implement WIN0/WIN1/WININ/WINOUT, which the gap list
did not know -- section 7a said "neither models the window registers", which had
not been true for either engine for some time. That paragraph is corrected in
place now, rather than only contradicted from here.

BLDCNT has sixteen linked writers on engine A and every sampled frame reads 0.
That is consistent rather than contradictory: hal/fader_wipes.cpp READS
BLDCNT/BLDY itself and drives the fade through master brightness, so the fade
path consumes those registers outside the PPU, and the scenes measured here
simply were not fading at any sampled frame.

TWO ROWS THAT LOOK LIKE THE GXSTAT SHAPE AND ARE NOT, both checked:

  VCOUNT. One linked reader, func_02013f4c, and it ends with a two-loop VBlank
  wait (`while (VCOUNT >= 0xc0) ; while (VCOUNT < 0xc0) ;`) that a dead-zero
  latch would hang in forever. It is not a dead latch: ntr/rt.cpp's
  run_scanlines() sweeps VCOUNT 0..262 every frame, and the function is reached
  only through func_02013f28's `for(;;)` -- the dev crash screen, cut content,
  not on any normal path. No action, and rt.cpp is not this lane's file.

  DISPSTAT. Two linked readers, and both touch only bits 3 and 4 (the VBlank and
  HBlank IRQ enables), which are software-owned and correct as a latch. The
  hardware-owned bits 0-2 are a dead-zero latch with no linked reader.

THE ONE UNMODELLED REGISTER THAT IS NOT ZERO. DISPCAPCNT reads 0x80000000 on
every frame of scene 4, and display capture is not modelled at all, so the
headline sentence needs this exception stated rather than buried in the table.
It is still not a live gap, for two reasons, both checked rather than assumed.
Engine A is in display mode 1 (graphics) throughout, not mode 2 or 3, so nothing
displays captured VRAM. And bit 31 is the one bit that could have produced the
GXSTAT failure shape -- hardware CLEARS it when the capture completes, so a game
polling it against a latch would spin forever -- but both linked touchers are
pure writes with no read-back:

    Scene::ResetHardwareRegisters   *(u32*)0x4000064 = 0x80000000;
    func_ov007_020bd4e8             *(u32*)0x4000064 = 0x80370010;

The first is a scene-init reset value, which is why scene 4 carries it, and the
second is in ov007 and unreachable. No action taken.

A CAVEAT ON THE OAM CENSUS NUMBERS. The census counts an entry as enabled when
attribute 0 bit 9 is clear, which is the hardware's own disable bit, and that
comes to all 128 entries on every frame (300 x 128 = 38400 in the mode-0 row).
It must not be read as "38400 sprites drew". What those 128 entries actually
are differs BY ENGINE AND BY RUN, measured directly rather than assumed:

                     all-zero   y == 192   other y (real sprites)
  scene 4 engine A       0         101              27
  scene 4 engine B     128           0               0
  level 1 engine A       0         128               0
  level 1 engine B       0         101              27

So there are two separate reasons the count is 128 and neither is "128 sprites".
Where the game has run OAM::Reset it parks unused entries OFF SCREEN rather than
setting bit 9 (attribute 0 low byte 0xc0, y = 192), and bit 9 stays clear on a
parked entry. Where it has not, the entries are boot zeros, and a zeroed
attribute 0 also has bit 9 clear.

AN EARLIER REVISION OF THIS PARAGRAPH GAVE ONLY THE FIRST REASON, for both
engines. That is engine A's story. Engine B in a scene run is the second case:
128 all-zero entries, no OAM::Reset having touched them, which is a real defect
in the scene bring-up rather than anything about 2D hardware, and is routed as
its own lane. The table above is the correction.

The mode-1/2/3 result does not move under either reason, because a parked entry
and a zeroed entry both still carry object-mode bits and every one reads 0.


7. THE DEFECT: OBJ WINDOW IS MODE 2, AND THE PORT WAS SKIPPING MODE 3
-----------------------------------------------------------------------

OAM attribute 0 bits 10-11 are the object mode. GBATEK: 0 Normal,
1 Semi-Transparent, 2 OBJ WINDOW, 3 Prohibited (the DS reuses 3 for bitmap
OBJs). The field position is pinned independently by the decomp's own code
rather than by docs alone: src/_ZN3OAM6RenderEbP7OamAttriiii5Fix12IiEi.c
composes the word as `(mode << 10) | (mosaic << 12)`.

All three of the port's OAM rasterisers had

    if (((a0 >> 10) & 3) == 3) continue;     // OBJ window: skip

which is the wrong mode in both directions. Mode 3 was thrown away, and mode 2 --
a sprite that on hardware is INVISIBLE and contributes only a mask -- was drawn
as an ordinary opaque sprite, painting the mask's silhouette onto the screen in
its own palette colours.

THE SAME MISLABEL WAS IN TWO OTHER FILES, and both are corrected in place rather
than only contradicted from here, because a reader who never opens this document
would otherwise still hit the trap. port/ov004_ov007_2d_map.txt section 7a said
"skip OAM mode 3 (OBJ window)", and port/scene_boot_map.txt section 7a rested
its star-select conclusion on "none of its THIRTY OAM::Render call sites passes
objMode 3" -- a test that cannot rule out the OBJ window, because the OBJ window
is not mode 3. That conclusion happens to be right and is re-derived in place
from the run instead: zero mode-2 objects in 300 frames, and DISPCNT bits 13-15
clear on every one of them, so no window of any kind is armed.

NOT LIVE, STILL FIXED. Zero mode-1, mode-2 and mode-3 objects appear on either
engine in any of the 1200 sampled frames, so nothing on screen changes today.
It is a contract error of exactly the class L1's GXSTAT was -- correct by
accident, wrong on the day something uses it -- and it costs four lines to state
correctly.

WHAT CHANGED, per file:

  ntr/ppu_sub.cpp   The OBJ window is now MODELLED. Mode-2 sprites write a mask
                    (g_objwin) instead of colour; DISPCNT bit 15 arms it;
                    WINOUT's upper six bits say what shows inside it; precedence
                    is WIN0, then WIN1, then the OBJ window, then WINOUT. This
                    file composites in one pass, so the mask exists before the
                    BGs are sampled.
  ntr/ppu.cpp       Skips mode 2 and mode 3 with the right names. This file has
                    no window unit, so it cannot carry the mask; not drawing the
                    sprite is still the closer of the two answers, because on
                    hardware it does not appear in the image either.
  hal/message_compositor.cpp
                    Same minimal fix. The mask is NOT modelled here and cannot
                    be without restructuring: this compositor runs its BG loop
                    BEFORE raster_obj, so an OBJ-window region would not exist
                    yet when the BGs are masked. Recorded rather than bodged.
                    OWNERSHIP DEVIATION, self-flagged: this is a hal file and no
                    sibling lane owns it, but it carried the identical one-line
                    defect and leaving it half-corrected would be worse.

PROOF: port/tests/smoke_objwin.cpp. It programs engine B's registers, VRAM, OAM
and palettes by hand -- no game code, no ROM data, links ntr alone -- and checks
four things:

  A control      a mode-0 sprite draws, whole, at the right place. Without this
                 the "no sprite colour" check below would pass vacuously.
  B obj window   a mode-2 sprite paints NOTHING, and its silhouette is instead
                 the region where WINOUT's upper half lets the BG through.
  C bitmap obj   a mode-3 sprite neither draws nor masks.
  D enable bit   with DISPCNT bit 15 clear the mask does not leak through.

Passing output:

    A control      green=256 (first 40,60)  red=48896
    B obj window   green=0  red=256 (first 40,60)  blue=48896
    C bitmap obj   green=0  red=0  blue=49152
    D winobj off   green=0  red=49152
    smoke_objwin: ok

AND IT WAS CONFIRMED TO CATCH THE OLD BEHAVIOUR, not merely to pass. With the
`== 3` test and `is_win = false` reinstated in ppu_sub.cpp and nothing else
changed, the same binary reports 5 failures, including case D showing green=256
-- the window sprite being painted on screen, which is the bug stated as a
pixel count.


8. TOUCH: THE REGISTER SURFACE HAS NO LINKED READER
-----------------------------------------------------

Gap (f) says ov004's TouchIcon_c and ov007's touch_panel "both read the touch
panel", and that walk_window has a touch bridge but "no touch-panel register
model". The second half is true and turns out not to matter.

The game does not read the panel hardware on any linked path. It reads
TouchInfo[4] at DS 0x020a0de8 -- {u8 touched, u8 held, u8 x, u8 y} per
controller -- which hal/auto_bss.cpp hosts as one contiguous 16-byte block and
hal/sub_screen.cpp's poll_touch() already fills from the mouse every frame, with
SM64DS_TOUCH_PROBE for a scripted stylus on top. That bridge is the seam, and it
exists.

The hardware path behind it is ARM7 work: the TSC is read over SPI and posted to
shared WRAM, and the arm9 side of that is func_0205f300, which reads 0x027fffaa
and 0x027fffac. IT IS NOT LINKED -- zero hits in walk_window.map -- and the
audit confirms both words, plus SPICNT and SPIDATA, read 0 on all 1200 frames.

So the honest model is the empty one, and it is already what the port has: no
ARM7, no SPI transaction, no panel registers, and the stylus state delivered
directly into the record the game actually reads. NOTHING WAS CHANGED HERE. The
seam a later lane would want is not a register model at all; it is that
poll_touch publishes only slot 0 and only from the mouse.

ONE HONEST LOOSE END IN THE SAME FAMILY, QUEUED AND NOT RIDDEN.

The pad is TWO dead latches, not one, and the reader combines them. Its single
linked reader, func_02013f4c, opens with

    raw = ((*(u16 *)0x4000130 | *(u16 *)0x27fffa8) ^ 0x2fff) & 0x2fff;

so KEYINPUT (0x04000130, the ten ARM9-visible keys) is ORed with the ARM7-posted
word at 0x027fffa8 (X, Y and the hinge, which the ARM9 cannot read directly)
before the whole thing is inverted. Both are zero in the port, on every frame of
both runs. The DS keypad is ACTIVE LOW, so zero is not a neutral reading: it
means EVERY button held, on both halves. A dead latch here reads as the worst
possible answer rather than an absent one.

It is recorded rather than fixed, for two reasons.

  UNTESTABLE ON ANY NORMAL PATH. func_02013f4c is reached only through
  func_02013f28's `for(;;)`, which is the dev crash screen -- cut content that
  nothing in a level or scene run calls. A model written here could not be
  exercised by any run this lane or the battery can make, so it would ship
  unverified, which is the failure mode this whole audit exists to avoid.

  IT IS NOT ONE LINE. Two registers with different layouts have to be driven
  from a host input source with the polarity inverted, and the port already
  delivers input a different way entirely: through the Ctrl block at
  data_0209f498, which is what Stage::CheckInput reads. Wiring the latches
  without deciding which of the two is the source of truth would give the game
  two disagreeing input paths.


9. GXSTAT BITS 8-14, THE RIDE-ALONG
-------------------------------------

L1's review amendment 2 bounded bits 0..14 as read-only-but-unmodelled and asked
the next lane in the file to close them. Closed for bits 8-14.

L1's stated reason for leaving them was "the host has no matrix-stack model to
normalise them FROM". That was wrong about the host. ntr/gx.cpp has kept both
stacks and both stack pointers all along -- g.pos_sp over pos_stack[32] and
g.proj_sp over proj_stack[2], maintained by the MTX_PUSH and MTX_POP handlers --
so the stack level is not a guess. A new read-only accessor
gx_matrix_stack_levels() reports it and io.cpp's gxstat_normalize folds it in.
Busy (bit 14) is pinned to 0 on the same argument GXSTAT_IDLE already rests on:
ntr executes a display list synchronously, so the game can never observe a push
or pop in flight. GXSTAT_HW grows 0x0FFF0000 -> 0x0FFF7F00.

Field positions from the game, not from docs alone:

    func_02055464: if (GXSTAT & 0x4000) return -1; *out = (GXSTAT & 0x2000) >> 13;
    func_02055490: if (GXSTAT & 0x4000) return -1; *out = (GXSTAT & 0x1f00) >> 8;

AND THIS CORRECTS WHAT L1's NOTE SAID THE SPIN WAS WAITING ON. It read
func_02055624's `while (func_02055490(&a)) ;` as "spin until the stack level
reads 0". It is not: both helpers return -1 only when BUSY and 0 otherwise, so
the loops spin until NOT BUSY and then use a and b as the levels. That moves the
risk in the fix's favour. With busy pinned to 0 the loops still fall through
immediately, exactly as they did against the dead latch, so there is no new
hang. What changes is the half after the spin: func_02055624 pops the stacks by
a and b, which against a dead-zero latch popped NOTHING and left the stack
unwound.

func_02055624 IS LINKED, AND THE LINE ABOVE USED TO SAY IT WAS NOT. That was
L1's "0 references in walk_window.map", measured against a 4950-symbol build and
carried into a 5533-symbol one without re-deriving it. My own build's map has it
at 0001:0003d520, with func_020557b4 and their caller func_ov007_020bcf90.

The true statement is narrower and more useful: the chain is UNREACHABLE, not
unlinked. func_02055624's linked callers are func_020557b4 and
func_ov007_020bcf90; func_020557b4's only linked caller is the same
func_ov007_020bcf90; and that one sits on scene 1's Render path, behind the
InitResources fault in section 4. The other caller of func_020557b4,
func_0200f4b4, is genuinely absent from the map. So the day this matters is THE
DAY SCENE 1 RUNS, not the day something links: the two pops stop being no-ops
against zeros and become real pops against gx.cpp's live sp counters, which is
the whole reason for the change.

AND ONE BOUND ON WHAT THE FIX IS. gxstat_normalize runs only on accesses that
come through io.cpp's proxy, and almost nothing on this surface does. Bits 8-14
are therefore a SNAPSHOT taken at the last hostgen'd touch of GXSTAT, not a live
mirror of the stacks. That is strictly better than a latch that never tracked
anything and strictly less than modelling the register. Making it live means
writing through from gx.cpp at push and pop time, which is that file's lane.

Bits 0-7 (the box-test result) stay a latch. The host runs no box test, so there
is nothing truthful to report, and no linked reader asks.


10. WHAT THIS LANE DID NOT DO

  * No OBJ-window mask on engine A. Structural, stated in section 7.

11. THE SEVENTH CLUSTER, WHICH WAS NOT ON THE LIST: OBJ EXTENDED PALETTES
--------------------------------------------------------------------------
Run link60 Stage 4, lane SUB2, base 34d3a3130, gate GREEN 5810/11249 (51.6%),
battery ALL GREEN. The battery's two standing exceptions are SCENE_BLOCKED rows
and not SCENE_SKIPS ones: scene 1 and scene 374 cannot run at all and are
required to fail with their recorded blocker. A skip is a scene that passes
with a class switched off, and neither of these is that.

Section 6 could not have found this one, because the instrument could not see
it. The register file says a scene's DISPCNT bit 31 is clear and the mode census
says all its objects are mode 0, and both were TRUE of scene 4 while its
character portrait decoded through the wrong palette every frame. What was
missing is that neither table said what a sprite decodes FROM.

TWO ROWS ADDED TO ntr/ppu_audit.cpp, and they are what settled it.

  OAM enabled-entry attributes, distinct (attr0, attr1, attr2) triples, with
  the colour-mode bit, the palette field, the character name and the size
  decoded out. Distinct triples rather than entries: a HUD redraws the same
  sprite every frame, so 38400 entry-samples come to about twenty rows.

  OBJ decode inputs, nonzero bytes: OBJ VRAM, the standard OBJ palette and --
  new -- the OBJ EXTENDED palette store, whose base 0x068a0000 is taken from
  src/_ZN3GXS14LoadOBJExtPlttEPKvjj.cpp's own arithmetic rather than a doc.
  Engine A gets no extended-palette row: this tree has no GX::LoadOBJExtPltt TU
  to derive a base from, and a guessed base is the invented mapping the audit
  exists to avoid.

Tile 512 x 32 bytes is 0x4000, and 0x4000 is exactly where dScStarSel_c::
InitResources decompresses the selected character's portrait. The ROM's own

    handle 0x244   data/2D_cad/d_2d_player_select_mario_8bit_ncg.bin
    handle 0x245   data/2D_cad/d_2d_player_select_mario_8bit_ncl.bin   512 B

so the four 256-colour sprites are the portrait, the 512-byte _ncl is the
256-colour palette the scene pushes through GXS::Begin/Load/EndLoadOBJExtPltt,
and the nine 16-colour sprites beside it are on the standard palette and were
never affected. An extended palette applies to 256-colour sprites only, which is
why exactly one element of that screen was wrong and the rest were right.

FOUR SPRITES, ONE IMAGE: WHY THE STRIDES LOOK WRONG AND ARE NOT. The four
portrait entries are declared 64x64 and sit 16 screen pixels apart, at (88,56),
(104,56), (88,72) and (104,72), with tile numbers 16 pixels apart too. Read
quickly that says "16x16 sprites mislabelled", and it is worth writing down why
it does not.

Work the 2D model through. OBJ VRAM in 2D mapping is a matrix 32 slots wide,
32 bytes a slot; a 256-colour 8x8 cell is two slots, so a matrix row is 16 cells
across and 8 source pixels tall.

    tile 516 - 512 = 4 slots  = 2 cells        = 16 source px right
    tile 576 - 512 = 64 slots = 2 matrix rows  = 16 source px down

SOURCE STRIDE EQUALS SCREEN STRIDE on both axes. So wherever two of these
sprites overlap, both sample the SAME source pixel, and the four composite into
one coherent image rather than four fighting copies. The declared size is not
contradicted by anything: the sprites are 64x64 windows onto one picture, laid
down at a 16-pixel step, and their union is the 80x80 the portrait occupies.

AND THE COHERENCE IS EVIDENCE FOR THE 2D MODEL, not a loose end. Run the same
arithmetic under 1D, where a sprite's cells are consecutive: the horizontal pair
still agrees (4 slots is 2 cells is 16 px along the row of a 64-wide sprite),
but the vertical pair does not -- 64 slots is 32 cells, which for a 64-wide
sprite is four rows, 32 source pixels, against a 16-pixel screen step. A 1D
reader would draw the lower pair half an image out of register with the upper.
The frame does not do that. So the ROM's cleared bit 4, ppu_sub.cpp's 2D slot
arithmetic and the OAM data all agree, and the "16x16 stride" reading is
RESOLVED rather than open.

WHY BIT 31 WAS CLEAR WAS NOT A 2D GAP AT ALL. It was a hosted-global aliasing
break: the SetBankFor* family reaches members of one struct at 0x020a6088 out to
+0x18, and +0x18 IS the DS symbol data_020a60a0 that GXS::BeginLoadOBJExtPltt
reads back. The port hosted them as separate objects, so Begin read zero, End
restored bank 0, and SetBankForSubOBJExtPltt(0) cleared the bit the scene had
just set. hal/cxx_aliases.cpp carries the fix and the derivation.

HOW BIG THE HOSTING MISS WAS, in the config's own figures rather than the
port's. EIGHTEEN src TUs name data_020a6088. The symbol's span in
config/arm9/symbols.txt is TWO bytes -- data_020a608a starts at +2 -- while the
struct view reaches +0x18 and func_02053d9c clears the block as
data_020a6088[0..12], 26 bytes a call. The old host object was `int[2]`, eight
bytes, which was already the base map's placement gap rather than the symbol's
span. Review read the base map and named where the overrun landed: all of
data_020a8114 plus two bytes of data_0208e6ec, with the +0x18 store on
data_0208e6ec. Those names belong to one link and are not a constant; the
durable statement is that a 26-byte write into a two-byte symbol lands on
whatever the linker put next.

THE BG PATH WAS BROKEN THE SAME WAY AND IS FIXED BY THE SAME BAND, which this
lane did not claim the first time. GX::SetBankForSubBGExtPltt records at +0x16
and func_02054118 -- GXS::BeginLoadBGExtPltt's callee, func_020540f0's exact
sibling -- clears DISPCNT_B bit 30 and reads that word back as data_020a609e.
Same split, same zero, same bank-0 restore.

port/tools/gxband_guard.py is the post-link pass the bullet above asked for.
It reads the expected offsets out of config/arm9/symbols.txt at run time and
the produced ones out of every walk_window.map the build writes, and it fails
the build when they disagree. It runs in build-port.cmd's post-link slot, the
one alternatename_guard --map already occupied, and its fixture battery runs
before configure with the other selftests.

WHY A NEW TOOL RATHER THAN AN EXTENSION. alternatename_guard owns that slot but
its whole domain is the fate of an /alternatename directive -- its baseline
file, its scoping rules and its selftest are that one question, and two
unrelated failure classes behind one exit code is how a selftest stops covering
its subject. dsstate_guard is the closer relative (it reads the map, it
polices hosted DS globals) but it asks a binary membership question with no
config input, wired POST_BUILD on walk_window alone, which is the one-target
coverage this change exists to remove. What is reused rather than re-invented
is the map-reading discipline already paid for here: faultmap's row shape and
Rva+Base convention, and closure.map_defined's refusals for a missing,
zero-byte, row-less or trailer-less map.

TWO BANDS, NOT ONE. The undersized-hosted-global family produced three catches
this run, and the two that are contiguity questions are declared together:

    gxbank   0x020a6088..0x020a60a4   13 config members, end IS a config row
    dtcm     0x023c0000..0x023c4000    1 config member, end is the ARM9 TCM
                                       extent and says so in prose

Only the GX band's numbers come entirely from a symbols.txt. The DTCM's 16 KB
is a hardware extent -- config/arm9/dtcm/delinks.txt describes 0x20 bytes of
initialized .data and nothing more -- so the declaration carries a provenance
string and the guard prints that instead of claiming the config said it. The
third catch of the run, the fader seat's, is a single hosted global sized by
its config next-symbol delta and is NOT a band; sweeping every hosted global
against that rule is a different and much larger tool, and plenty of hosted
globals are deliberately smaller than their gap.

WHAT IT ASSERTS, five arms, each with a fixture break only it catches:
presence of every member; every consecutive delta against the config delta;
no foreign symbol strictly inside the span; the span fitting inside its image
section; and -- because the map's section table lists one row per contribution,
so the grouped-section remedy publishes each member's length -- every member's
SIZE where the map states one. Twelve of the GX band's thirteen deltas are
measured between symbol pairs. The thirteenth is data_020a60a0's four-byte
tail, which no member follows: exclusion and containment assert it
structurally, and on this tree's layout the size arm measures it outright
(.dsstate$gxbank12's row says four bytes). 36 selftest arms, all green.

A SIXTH THING IT ASSERTS, ADDED ON REVIEW: the coverage floor. Each band
declares the set of maps that hosted it when it was measured, and a band that
quietly leaves one of them fails the build. Every other arm reads that
regression as green, because a map with no definition of the head is correctly
skipped, so without the floor a shrink from three hosting targets to two is a
smaller green rather than a failure. Proved both ways on real maps: the three
declared targets satisfy it today, and a sweep of a directory holding only
walk_window's two maps fails naming smoke_player.

THE BREAK-PROOF, two mutations, both built and both restored.

M1, SUB2's own recipe: align(8) on data_020a609c. walk_window and

M2, the one the runtime check cannot see: data_020a60a0 hosted at 2 bytes

    walk_window.exe SM64DS_SCENE=4 SM64DS_SCENE_FRAMES=30 SM64DS_FAULTS_FATAL=1

       not one diagnostic line from the layout check

M3 AND THE POSITIVE CONTROL ARE THE REVIEW'S MEASUREMENTS, NOT THIS LANE'S, and
they went past the case this lane made.

M3 put align(8) on data_020a6098 instead, which sits at +16. walk_window's band

THE POSITIVE CONTROL closed the question M2 could not close by itself. M2's
evidence is a silence, and a silence is only evidence if the thing that should
have spoken can speak on that path at all. The review ran the M1 binary the

UNPROVEN, AND THE BOUNDARIES

  * The guard does not size a member that shares a contribution row. Only a
    member with a row of its own reaches the size arm; data_023c0000 is one
    that does not, so its 16 KB is proved by what follows it, not read off the
    map.
  * A symbol at exactly a member's address is excused as an alias. Every real
    build has such rows (a fired /alternatename, MSVC's decorated spelling),
    the linker does not overlap storage, and what that costs is telling an
    alias from a zero-length decoy.
  * Nothing here says the port_gxbank_layout_check call should go. It is
    cheaper than this guard at what it does cover and it is the only thing
    that speaks during a run; the case for retiring it was not made and was
    not attempted.
  * M1 and M2 were both built and both restored, and the tree was returned to
    HEAD's bytes; no measurement in this section was taken off a mutated
    tree that is still on disk.
  * The DTCM band was proved GREEN on three maps and its failure arm was
    proved on fixtures, not on a real short-hosted build. Re-sizing
    data_023c0000 for real would have been a second full rebuild for an arm
    the GX band already exercised end to end.
  * The ORIGINAL split -- the head hosted alone in another file with the
    twelve members somewhere else, which is the state SUB2 found -- is a
    selftest fixture here and was not reproduced in a real build. Doing that
    means reverting the band fix, and M1 and M2 already broke a real link two
    different ways.
  * M3 AND THE POSITIVE CONTROL ARE THE REVIEW'S RUNS. This lane re-derived
    M3's arithmetic off its own two maps and did not rebuild it, and did not
    re-run the positive control at all. Both are recorded as the review's
    measurements and should be read that way.
  * The coverage floor is a declared set, so it is only as good as the
    measurement that filled it. It catches a band leaving a target it used to
    be in; it cannot know that a NEW target should have hosted one. Widening
    it is a measurement anyone can take, narrowing it needs the reason in the
    commit, and neither is enforced by anything but review.

12c. WHAT WAS ADDED TO THE INSTRUMENT, AND WHY THE 2D TABLE COULD NOT SEE IT

Sections 1-11 sample 2D registers only, and on the top screen that is half the
picture. An empty frame reads identically whether the 3D layer submitted
nothing or the 2D layers were never enabled, so the table alone cannot separate
a viewport fault from an enable fault -- which is exactly the ambiguity this
lane was sent to resolve.

  ntr/ppu_audit.cpp grows an ENGINE A 3D LAYER section: the latched VIEWPORT
  rectangle and the POLYGON count, sampled at the same instant as the 2D
  registers so the two are comparable. The viewport is read through a new
  ntr::gx_debug_viewport, beside the existing gx_debug_matrices, and is in HOST

  hal/message_compositor.cpp's own debug dump no longer needs a dialogue box to

12e. A CORRECTION TO 12b AND 12d, CAUGHT BY SHARPENING MY OWN INSTRUMENT

The viewport row this lane added originally reported the rectangle alone, and
12b's first form read "VIEWPORT x 0, y 0, w 512, h 384 on all 300 samples" as
though the game had programmed it. It had not. gx_reset runs once a frame and
"g = State{}" restores the viewport to a FULL-SCREEN default, so a sample that
reads full-screen is consistent with two different worlds: the game issued a
full-screen viewport, or the game issued none and the default stood. The row
could not tell them apart, and the sentence it produced picked the flattering
one.

VIEWPORT_SETS is the fix -- a count of VIEWPORT commands executed since the
last reset, incremented in the command 0x60 handler and reset with the rest of
the state. On scene 374 it reads 0 on all 300 samples. The game issues no
viewport command on this path at all.

The ruling is unchanged and is in fact stronger: a transform that is never
exercised cannot be the one that broke the frame. What changed is that the
evidence now says "not used" instead of "used and correct", which are different
findings that happened to point the same way.

WHY THIS IS RECORDED RATHER THAN QUIETLY EDITED. The wrong form is in commit
05e5fa0ea's message, where it cannot be edited, and an instrument that returns a
value nobody can attribute is the exact failure this file's section 1 warns
about under "what the method cannot see". The next reader of the viewport row
needs to know the row grew a companion and why, so the header the dump prints
now says READ VIEWPORT_SETS FIRST.

The ROM's own full-screen viewport (Initialise3dGraphics writes 0xbfff0000 to
0x4000580, which decodes to x1 0, y1 0, x2 255, y2 191) is still the ROM's
intent for the 3D layer generally. It is just not evidence taken from this run,
and 12b no longer presents it as such.

12f. THE 12e CLASS RECURRED INSIDE 12e's OWN COMMIT, in the probe this time

Review finding (a), and it is worth its own entry because it is the SECOND
instrument in this lane to report a value it could not attribute, after 12e
fixed the first one in the same set of commits.

The mask-versus-register probe chose its verdict word on "mask == live". Zero
equals zero, so on any run where the game had not set a layer enable the probe
printed "published" -- including on every level run of the NO_PUBLISH arm,
where the copy it was reporting is switched OFF. It asserted a publish that had
demonstrably not happened, in the exact arm built to prove it had not.

Fixed by taking the claim off the comparison and putting it on the mechanism.
The publish path reports itself through the same static latch the write reads,
and the comparison is only allowed to speak where it has content:

    publish disabled        say so, and say the register's contents came from
                            somewhere else
    mask 0 and live 0       nothing to publish; the equality proves nothing
    mask == live, nonzero   published
    mask != live            NOT PUBLISHED

NO CONCLUSION IN 12d MOVES. The level result rests on BMP identity across the
two arms, which is a measurement of frames and never consulted this line; the
scene-374 result is the mask != live arm, which was always the honest branch.
What was at risk was the next reader, who would have taken "published" off a
level run as evidence about the publish.

THE GENERAL SHAPE, since this is now twice in one lane. Both defects are an
instrument whose output has fewer states than the world it reports on: a
viewport rectangle that could not distinguish programmed from defaulted, and an
equality that could not distinguish agreed from both-empty. Neither was wrong
about a number. Both were wrong about what the number licensed. The check that
catches this class is to ask, of every field an instrument prints, which
different worlds produce this same output.

13c. THE BACKGROUND: THE READER IS RIGHT AND THE BYTES ARE WRONG

Curling's BG2 is the easiest background in the game to check, because its
tilemap is the IDENTITY: file 0x30 is 1024 entries, every tile id used exactly
once, cell n holding tile n with its own palette bank. The tilemap and the
palette are loaded RAW, no compression and no relocation, so the bytes in VRAM
can be compared against the cartridge's own files byte for byte.

    engine A BG palette  0x05000060 +0x1a0   == file 0x2f            EXACT
    engine A char data   0x06020000          768 tiles populated, and 768 is
                                             exactly the visible screen
    engine A tilemap     0x06009000 +0x800   != file 0x30
                                             the 1248 bytes of file 0xc7,
                                             COMPRESSED AND UNDECODED, followed
                                             by 800 bytes of heap tail
    engine B tilemap     0x06204000 +0x800   == file 0x34            EXACT
    engine B BG palette  0x05000460 +0x1a0   == file 0x33            EXACT

File 0x30's bytes are nowhere in engine A's whole 512K BG VRAM window, and
every branch of G2::GetBG2ScrPtr except the mode-7 one lands inside that
window, so this is not a destination the reader and the writer disagree about.

WHY: THE PORT'S LoadFile CACHE OUTLIVES THE ROM'S OWN FREE. The ROM's LoadFile
(0x0201816c, then func_0201818c) allocates a FRESH buffer per call and the
caller owns it; dScMgCurling_c::InitResources frees each one with Deallocate
the moment it has copied it. hal/level_boot.cpp's host LoadFile keeps a
per-handle table and returns the cached pointer, which the ROM's free has
already invalidated. The trace, one run, in order:

    [loadfile] 0x2f -> 30031B60 slot 32 FRESH     palette,  copied, freed
    [loadfile] 0x30 -> 30031B60 slot 33 FRESH     tilemap,  copied, freed
    [loadfile] 0xc7 -> 30031B60 slot 34 FRESH     OBJ tiles land in that block
    [loadfile] 0xc8 -> 30032060 slot 35 FRESH
    [loadfile] 0x33 -> 30032180 slot 36 FRESH
    [loadfile] 0x34 -> 30032180 slot 37 FRESH
    [loadfile] 0x30 -> 30031B60 slot 33 CACHED    <-- the defect

The last line is func_ov006_020e3250, which InitResources calls at its end. It
uploads 0x800 bytes of one of three rink tilemaps (0x30, 0x2d, 0x31) to the BG2
screen base, and WHICH ONE IS NOT A COIN TOSS ON THIS PATH. Review derived it
and the code agrees: InitResources calls func_ov006_020e3378 immediately
before, whose whole body is `*(int *)(self + 0x4e9c) = 255`, and 255 is exactly
the value func_ov006_020e3250's first branch tests for. That branch sets the
field to 0 and returns without touching the generator, and 0 selects handle
0x30. The RNG re-roll below it belongs to the OTHER caller,
_ZN14dScMgCurling_c13OnYoshiTryEatEi, the in-play reset that runs func_ov006_020e3388 and
func_ov006_020e3250 without the 255 store. So the first load of the scene picks
rink 0 on every boot. It asks for handle 0x30 a SECOND time, the host cache
hands back the block the ROM freed four loads earlier, and that block now holds
file 0xc7. So the port uploads an LZ-compressed sprite
sheet into a screen-entry table: 1024 cells of arbitrary tile id and arbitrary
palette bank, full screen. That is the chunk pattern, and it is the whole of
the 95%.

Engine B escapes for one reason only: nothing reuses 30032180 after its
tilemap copy.

NOT FIXED HERE, AND THE REASON IS NOT SHYNESS. This is not a decode defect, the
compositor renders exactly the bytes VRAM holds, and the fix is not in the ntr
layer: it is the lifetime contract between an invented host cache and the ROM's
own allocator, in hal/level_boot.cpp, on the path every level's KCL and object
files take.

WHAT THIS LANE DID AND DID NOT DO TO THAT FILE, said plainly because the two are
easy to run together: it DID touch hal/level_boot.cpp, eight lines added and one
replaced, and 13a lists what they are. They are the env-gated trace above and
nothing else, inert with SM64DS_LOADFILE_TRACE unset. What is refused is the
LIFETIME FIX, not the file.

WHY THE CACHE CANNOT SIMPLY DIE, corrected from review's census after this
lane's first answer was wrong on the facts. The wrong answer said dropping the
cache would make the per-level release free buffers the ROM already freed;
port_level_reset_host frees nothing, and its own comment says so, because it
DROPS the table rather than releasing it and releasing would be the double free.
The real dependents are two, and both index the table BY HANDLE:
port_level_capture_kcl resolves the outgoing level's KCL slot out of it and
copies the SharedFilePtr aside for a late free after ResetMeshColliders, and
port_loadfile_pin_persistent marks the message bank's slot so the per-level drop
leaves it loaded. A cache that stops answering by handle takes both of those
with it. Invalidating on free instead needs a hook on Memory::Deallocate that
nothing has today. Either way it is a lane with its own battery. Recorded with a
one-command reproducer instead:

    SM64DS_SCENE=374 SM64DS_SCENE_FRAMES=2 SM64DS_LOADFILE_TRACE=1

13d. THE SPRITES: THE 1D/2D GAP IS REAL, LIVE, AND SMALL HERE

DISPCNT_A bit 4 is CLEAR, which is 2D tile mapping, and both engine-A readers
hard-coded 1D. The bit is clear because Scene::ResetHardwareRegisters ANDs
0xffcfffef into both engines' DISPCNT, bit 4 and the boundary field in one
mask, and nothing on a scene path sets it again: GX::SetGraphicsMode's own mask
is 0xfff0fff0, which preserves bit 4, and its third argument only ever reaches
bit 3 (every call site passes 0 or 1). ov006 does the same clear for engine B
by hand at func_ov006_020e73c4.

WHICH FILE. Section 11's DISPCNT note recorded this gap against ntr/ppu.cpp,
and that was accurate about ntr/ppu.cpp and named the wrong file for the
consequence: ppu_scanout_obj's only caller in the tree is tests/smoke_oam.cpp.
Engine A's LIVE path is hal/message_compositor.cpp, which carried the identical
hard-coded arithmetic. Both are fixed, in ntr/ppu_sub.cpp's shape:

    slot = map1d ? (trow * (w/8) + tcol) * (c256 ? 2 : 1)
                 : (trow * 32 + (c256 ? tcol*2 : tcol))
    cell = objvram + tile * boundary + slot * 32

The 1D branch is arithmetically identical to what was there (the old c256 form
was tno * 64, which is slot = tno * 2 in 32-byte units), so a 1D run is
byte-unchanged by construction. tests/smoke_oam.cpp writes DISPCNT = 1 << 4 and
lays its tiles out consecutively; its expectations are 1D expectations, and
honouring the bit is what keeps them true. Flipping the default would have
broken them.

MEASURED EFFECT, same scene, equal .dsstate base 0xbae000, OBJ layer alone:

    before   OBJ owns 2,053 px, x 0..255 y 0..185
    after    OBJ owns 2,369 px, x 7..255 y 0..185
    2,276 host pixels differ between the two OBJ-only captures

Only four of the 52 sprites placed in the first sample can move: the 8x8
sprites are one cell and their slot is 0 under either mapping, so the two
32x16 and the two 8x16 sprites are the whole footprint. This fix does not
make the top screen right, and nothing in this section claims it does. It
closes a gap that is wrong on every scene engine A composites for.

13e. THE OTHER TWO SUSPECTS, CLOSED ON MEASUREMENTS

  THE TILE-BOUNDARY FIELD IN 2D. Still applied in both mappings by all three
  readers, still hardware's 1D-only field, and scene 374 measures bits 20-21 at
  ZERO on all 300 samples, cleared by the same 0xffcfffef. Boundary 32 is what
  2D wants, so the gap stays inert and stays UNFIXED: this run contains no
  measurement that would tell a correct fix from a wrong one, and the audit row
  says so rather than a commit saying it silently.

  ENGINE-A OBJ EXTENDED PALETTES. Not applicable on this screen, and now that
