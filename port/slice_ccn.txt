# THE WIDTH IS 36 AND IT WAS CHECKED THREE WAYS, port/mg_fanout_costs.txt
# section 11's checks, because twelve widths in that file's section 3 table
# were phantoms:
#   1. SPAN. config/arm9/overlays/ov006/symbols.txt puts the next symbol
#      (data_ov006_0213bfe0) exactly 0x90 bytes past the vtable, so 36 words is
#      an upper bound and a 37th slot cannot exist inside the table.
#   2. TERMINAL SLOT. Slot 35 holds 0x020ad660, the word every dScMgBase_c-
#      derived table holds there.
#   3. WHAT THE WORD PAST IT IS. Index 36 reads 0x01fc00fc, which is an address
#      in no module -- it is the first word of data_ov006_0213bfe0.
#
# SIX OVERRIDES, FIVE MARKERS, which the fan-out table predicts and a fresh
# diff against dScMgBase_c's own table (data_ov004_020bc0c0) confirms: slots
# 0, 6, 9, 16, 17 and 18 differ and no other slot does. All five marker bodies
# were disassembled out of the shipped overlay image and ruled REAL_DECOMP
# before anything was seated; port/tools/inferred_stub_adjudicated.txt carries
# the per-body evidence.
#
# THE HIERARCHY IS TWO DEEP. Slot 16 (D2, func_ov006_020dbe40) and slot 17
# (D0, func_ov006_020dbe64) both store data_ov006_0213bf50 into [this] and then
# call func_ov004_020b29c0 directly, with no intermediate table between. So the
# seat fills ONE derived table, the way curling's does, and not the two 0x169
# needed.
#
# HOW THIS LIST WAS DERIVED. A relocation closure from TWO roots, the SpawnInfo
# record and the class's own overlay constructor __sinit_ov006_0213014c, which
# is the correction port/mg_fanout_costs.txt section 1 makes to a SpawnInfo-only
# walk. Measured on this class, with module residency enforced (ov002, ov003,
# ov006 and ov007 share an address window, so an address alone does not name a
# symbol -- a first version of the walk that resolved by address alone reported
# the whole window four times over):
#
#     SpawnInfo root only      ov006  27 fn   ov004  95 fn   arm9 587 fn
#     + its own .init root     ov006  64 fn   ov004 162 fn   arm9 598 fn
#
# THE arm9 AND ov004 FRAMEWORK HALVES ARE NOT REPEATED HERE. port/slice_mg1.txt
# already lists 152 ov004 TUs, the 35 overlay constructors and the arm9 waves
# the framework needed, and CMake appends both lists to the same targets and
# dedupes identical absolute paths. Only the delta is below.
#
# ONE ov006 BODY IN THE CLOSURE HAS NO SOURCE AT ALL and is therefore not here.
# It has no delink block in config/arm9/overlays/ov006/delinks.txt and no src
# file in either extension, checked rather than assumed:
#     func_ov006_020dbe9c  0xe0   the sixth callee of slot 9, Render
#
# THE SECOND FLOOR IS CLOSED. func_ov006_020dd0e0 (0x1ec, slot 0 of state table
# data_ov006_021417b0) was the state this class dispatched every frame and could
# not reach, which is why the minigame took a stylus tap and did nothing with
# it. Lane TOUCH of run mg5 matched it; the delink block and src/func_ov006_-
# 020dd0e0.c came across in the commit before this one and match.py re-verified
# MATCH on 2004/b56 in THIS tree before the line below was added. Its four
# callees were already in the build: func_ov006_020dcb1c and _020dd4b0 in this
# list, src/func_020127a4.c in the second wave below, and
# src/_ZN5Sound12PlayBank2_2DEj.cpp in slice_mg1.txt. So the class now has ONE
# hard floor, on the render path, and it is a decomp gap and not a port one.
#
# SEVEN TUs ARE HOST-COPIED AND ARE COMMENTED OUT BELOW. They are the mwcc
# POINTER-TO-MEMBER dispatchers and the port cannot compile any of them: mwcc's
# member pointer is eight bytes where MSVC's is four, so the tables stride
# wrong and the call sequence is a different shape. Their bodies are in
# port/unmatched/MgCoin_StateDispatch.cpp, each verbatim but for the table
# declaration and the call.
#
# ONLY FOUR OF THE SEVEN WOULD EVER BE NAMED BY A LINK, and this lane swept for
# `::*` across the whole closure rather than trusting an LNK1120, which is the
# rule port/mg_fanout_costs.txt section 4 states. THREE ARE SILENT: two declare
# their Entry table inside extern "C" (func_ov006_020dc298, _020dc754) and one
# declares it as `extern "C" Entry data_ov006_02141840[]` (func_ov006_020ddd6c),
# so all three mangle as the plain C name the ov006 mount already defines and
# the linker is satisfied while the stride is wrong. The sweep found exactly
# fifteen `::*` TUs in the closure: these seven and the eight ov004 ones
# MG1/MG2 already host-copied.
#
# NONE OF THE SEVEN PUTS A MEMBER POINTER IN AN OBJECT FIELD, which is the
# worse ov004 defect class (a four-byte field where the ROM has eight moves
# every field after it). All seven dispatch through a table, so their struct
# layouts are correct and only the stride and the call sequence are wrong.
