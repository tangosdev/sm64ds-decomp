# LANE EXCEPT (run link100, wave 5), batch 2: THE SLOT-5 FAMILY.
#
# Seventeen matched Render TUs across sixteen actor classes, every one of them
# a documented host-ABI exception whose stated reason is a vtable numbering
# THAT NO LONGER EXISTS.
#
# THE READING. Each of these headers says, in these words or a paraphrase of
# them:
#
#     hal/cxxname_bridge.cpp fills _ZTV9ModelAnim in MSVC order (dtor 0,
#     DoSetFile 1, UpdateVerts 2, Virtual10 3, Render 4, Virtual18 5), because
#     MSVC spends ONE slot on the destructor where Itanium spends two, so ROM
#     slot 5 (Render) lands on the host array's Virtual18.
#
# Lane SLOT5F respelled the ROM's D1/D0 pair as two plain virtuals under
# _MSC_VER in include/ModelBase.h and its five siblings, and the fills in the
# tree today are ROM-numbered:
#
#     port/hal/cxxname_bridge.cpp:519-522   _ZTV5Model[2..5]
#                                           = mv_dosetfile / mv_updateverts /
#                                             mv_virtual10 / mv_render
#                              :575-579     _ZTV9ModelAnim[2..6]
#                                           = mv_dosetfile / ma2_updateverts /
#                                             ma2_virtual10 / ma2_render /
#                                             ma2_virtual18
#
# port/hal/model_dtor_seat.cpp says the same thing in its own words ("ROM
# NUMBERING NOW"), and port/hal/actor_classes_intro.cpp says "every TU counts
# in ROM numbering now. THE TWO DUPLICATE FILLS ARE GONE."
#
# THESE ROWS WERE NOT IN LANE UNMATCH'S FOLD SWEEP, and I cannot say why from
# the evidence. That enumeration (out/UNMATCH/fold_candidates.txt) states its
# own rule -- "every port/unmatched TU whose first 4 KB names a matched src TU
# as HOST COPY OF and whose stated divergence is the MSVC destructor fold (the
# words 'slot 5', 'MSVC folds', 'one slot', 'dual fill')" -- and six of the
# files below satisfy BOTH halves of it by the letter. Counted over the first
# 4 KB of each header:
#
#     Lakitu_HostSites      "slot 5" x2   "HOST COPY OF" yes
#     PiranhaPlant_States   "slot 5" x2   "HOST COPY OF" yes
#     Spiny_HostSites       "slot 5" x1   "HOST COPY OF" yes
#     Tornado_HostSites     "slot 5" x1   "HOST COPY OF" yes
#     HeaveHo_HostSites     "slot-5" x2   "HOST COPY OF" yes
#     MrI_Render            "slot 5" x3   "HOST COPY OF" yes
#
# So the list of thirty was not the whole set its own criteria describe. The
# conclusion is not about the wording: AN ENUMERATION IS NOT A CENSUS. A row is
# closed when someone reads its reason and checks it against the tree as it is
# now, which is what out/EXCEPT/census.md does for all 414 of them.
#
# WHAT IS LEFT AFTER THE INDEX: THE CONVENTION, and it agrees. Each matched
# source dispatches through a LOCAL SIX-VIRTUAL shadow class over the embedded
# model, which MSVC compiles as a __thiscall virtual call: `this` in ecx, the
# one argument pushed, callee cleans. The host slot holds
#
#     void __fastcall mv_render(void *self, void *unused, const void *scale)
#
# -- ecx = self, edx ignored, scale pushed, callee cleans 4. Argument for
# argument and cleanup for cleanup, those two agree; the ignored edx is the
# only difference and it is read by nothing. Four of the shadows declare their
# slot-5 method returning int where Render returns void, which leaves garbage
# in eax, and all four discard the result.
#
# EVERY ROW IS VERIFIED BY ROM ADDRESS, not by name: the referrer is the
# class's own vtable slot 9 word read out of the RAW overlay image at that
# overlay's own .text base (config/arm9/overlays/ovNNN/delinks.txt line 1),
# and the destination carries a kind:function(arm,size=..) record. Seventeen
# of seventeen agreed; the generator refuses a mismatch.
#
# THE FACES. Sixteen of the seventeen matched sources are `real C++ method`
# recoveries -- they define `int Class::Render()`, whose MSVC mangling is
# ?Render@Class@@QAEHXZ -- while every fill site declares and calls the
# Itanium C NAME at C linkage, because what it used to reach was an extern "C"
# host copy. port/hal/except_faces.cpp defines that C name onto the method,
# one cdecl line each, and NOT ONE FILL SITE CHANGES. The seventeenth,
# src/_ZN7Tornado6RenderEv.cpp, defines the C name itself and needs no face.
#
# NOT IN THIS BATCH, and each for a reason:
#   Goomboss_HostSites.cpp   its second body, func_ov074_021222e0, is one half
#       of a NAME RACE with ov070's two-pointer file table at the same shared
#       -window address; retiring it needs that alias re-cut, which is a
#       different mechanism and a different lane.
#   Jrb_Renders.cpp (4 rows)  carries a SECOND stated reason -- "the shadow's
#       methods return int where Model::Render returns void, MSVC decorates
#       that differently". That reading is weak on its face (a virtual call
#       through a local shadow is an indirect call through the vptr and
#       decorates nothing) but it has not been measured, so it stays.
#   MgD3DBase_ModelAnimRender.cpp (4 rows)  ov006, four bodies in one file,
#       one of which is a different shape again. A minigame lane's row.
#   Ov085_Renders.cpp's _ZN9RabbitKey6RenderEv  its header records a MEASURED
#       convention twist on top of the slot, so it is not this reading.
#   port/hal/method_faces.cpp's Bird::Render and Flag::Render  the same
#       reading, one line each, but that file is outside this lane's list.
