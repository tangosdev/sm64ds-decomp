# Scene boot, ov007: dScDSMT_c, the TITLE SCREEN and FILE SELECT (scene id 1).
#
# ov007 is the fourth occupant of the shared scene slot at DS 0x020ad660 (the
# others are ov002, the in-level engine walk_window has always run; ov003, the
# three menu scenes the S1 spine lane seated; and ov004, the minigame
# framework). It is 548 functions in 0x57560 bytes and carries ONE scene class,
# dScDSMT_c (d_Scene_DS_Mario_Title), entered by spawning actor id 1.
#
# WHY THESE TUs LINK. The reference chain is the ROM's own and nothing here is
# a link root. The arm9 ACTOR_SPAWN_TABLE (0x02090864) relocates slot 1 to
# 0x02103264 (config/arm9/relocs.txt: from:0x02090868 kind:load to:0x02103264
# module:overlay(7), and 0x02090868 is ACTOR_SPAWN_TABLE + 4). That record is
# hosted by the ov007 mount and its +0 word is the factory func_ov007_020ccad0;
# hal/scene_boot.cpp seats it in data_020a4bb8[1] with the factory word
# repointed at the host compilation, exactly as it does for id 4. The class
# vtable is the MOUNT'S OWN data_ov007_021032e8, filled in place with host
# thunks, and it names the seven bodies. Everything else here is reached from
# one of those eight entry points, or from a code table one of them loads.
#
# HOW THE LIST WAS DERIVED. A BFS over config/arm9/overlays/ov007/relocs.txt
# from the eight entry points, following arm_call/thumb_call and expanding any
# ov007 DATA symbol a load reaches whose words are relocated into ov007 .text
# (165 such code tables). It reaches ALL 548 of ov007's functions, which is the
# measured version of the 2d map's "nearly self-contained": the title screen is
# not a slice of the overlay, it IS the overlay. 532 delink source blocks cover
# those 548 functions; 531 are listed below and the one exclusion is at the
# bottom with its reason. (527 and 526 when this was written -- the next two
# sections say where the other five came from.) FOUR of the 531 are LISTED AND
# NOT BUILT, which is a different thing from the exclusion and each has its own
# note at the bottom: run link60 lane RT1 displaced src/func_ov007_020be980.c,
# lane AE1 displaced src/func_ov007_020add3c.c, Stage 5 lane TS1 displaced
# src/func_ov007_020b6eb4.c and run mg15 lane IMPLICITR displaced
# src/func_ov007_020c2b9c.c, each to a host copy.
#
# THIS SENTENCE SAID "ONE" UNTIL RUN MG15 AND IT HAD BEEN WRONG SINCE THE
# SECOND DISPLACEMENT LANDED. Each lane wrote its own note at the bottom and
# none came back to the count at the top, so the header undercounted the cuts
# by three while every individual note was accurate. Recorded rather than
# quietly fixed: a per-lane note is not a census, and the next displacement
# updates this line as part of the cut.
#
# /OPT:REF IS THE REFEREE. No /include:, and this lane's aliases are
# name-spelling faces onto symbols that already exist. Whatever of the 531 does
# not link is a TU the title screen does not reach on the host, and
# port/ov007_seat.txt enumerates the drops rather than describing them.
#
# ---- FOUR TUs ADDED AFTER THE FACT, and what they cost ---------------------
#
# 530 delink blocks listed now, not 526. func_ov007_020beeb0, _020c49bc,
# _020c7d60 and _020cbbb0 were unmatched when this list was written and
# hal/scene_boot.cpp trapped three of the four. They landed on the decomp's main between
# 2026-08-05 and 2026-08-06, after this branch forked, and run link60's
# port-catchup lane brought them across by address. Each was re-verified here
# with tools/match.py against extracted/overlays/overlay_0007.bin at base
# 0x020ad660 rather than taken on main's word.
#
# THE LINKED COUNT MOVED BY EIGHTEEN, NOT BY THREE, and the difference is the
# interesting part. Measured by diffing the linked-stem set out of
# walk_window.map before and after, with the same build directory:
#
#   3 are the new bodies themselves (020beeb0, 020c7d60, 020cbbb0).
#   15 are ov007 TUs that were ALREADY in this list and were being discarded
#      by /OPT:REF because nothing in the binary called them. The three new
#      bodies are their callers, so they link now:
#        020bed60 020bf630 020c71c0 020c7240 020c72d0 020c7348 020c73f0
#        020c7504 020c80c8 020c9a84 020c9c24 020ca1d4 020ca308 020ca578
#        020cba78
#   0 TUs were dropped.
#
# 020c49bc is the fourth and it does NOT link: nothing references it, exactly
# as scene_boot.cpp's note said when it was the one unmatched body with no
# trap. It is listed anyway so a future caller resolves to the ROM's own code
# instead of an unresolved external.
#
# ---- A FIFTH TU, AND THE SAME LESSON WITH A LONGER TAIL --------------------
#
# 531 delink blocks listed now, not 530. src/func_ov007_020b2998.c is the
# title screen's widget setup and the writer of the scene state's +0xF4 field,
# and it was the ONE unmatched body in this overlay that scene 1 could not get
# past: hal/scene_boot.cpp trapped it, the trap returned 0, and the field stayed
# null. Run link60 lane CK1 matched it byte-identical (decomp main
# db0c4960635e, PR #1536) and lane PC2 brought it across by address the same
# day. Re-verified here rather than taken on main's word, against
# extracted/overlays/overlay_0007.bin at base 0x020ad660: match.py MATCH at
# 2004/b56 with strict relocs, linkcheck VERIFIED with 0 blind slots. The
# stale-dsd control was re-run here too, not quoted.
#
# THE LINKED COUNT MOVED BY TWELVE FOR ONE NEW BODY, and the tail is longer
# than the four-TU pass above because this body sits at the head of a chain
# nothing else in the image called. Decomposed with port/tools/mapdiff.py
# against a base map copied aside before the tip was built, 12 objects added
# and 0 removed:
#
#   1 is the new body itself (020b2998).
#   3 are its direct callees, already in this list, that /OPT:REF was
#     discarding for want of a caller: 020b2bd4, 020b7708, 020beaa0.
#   4 are one level deeper, all reached through 020b2bd4 (and 020bc6b4 also
#     through 020beaa0): 020bbf98, 020bc5fc, 020bc658, 020bc6b4.
#   4 are ARM9 TUs, not ov007 at all, and they are why a prediction made from
#     ov007's own reloc graph came in low: 020b2bd4 calls func_02044efc and
#     func_02045ef8, and each of those calls one more (func_02044f74,
#     func_02045f4c). A closure computed inside one module cannot see them.
#   0 TUs were dropped.
#
# One symbol MOVED rather than being added: _func_ov007_020b2998 was defined by
# scene_boot.cpp.obj (the trap) and is defined by func_ov007_020b2998.c.obj
# now. That is the trap removal and the body arriving, seen from the linker's
# side, and it is the shape a propagation should have.
#
# THE TWELVE ARE STILL LINK-ONLY, the same caveat the four above carry. ov007
# IS the title screen, the title screen is scene 1, and scene 1 is still the
# battery's one standing block: it now dies two call levels further on, at an
