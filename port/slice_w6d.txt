# A SLICE LINE ALONE DOES NOT LINK A TU (/OPT:REF). Every line below has its
# reference edge in hal/actor_classes_ov100pl.cpp (the two vtable fills and
# the factory) or in port/unmatched/PathLift_StateDispatch.cpp (the six state
# bodies the seat installs). Post-build every line was checked against
# walk_window.map -- no line sits here looking seated.
#
# THE CLOSURE IS RELOC-DERIVED, NOT GUESSED. Seeds: daObjPathLift_c's own six
# vtable bodies + daObjPathLift_c_classInit (ov100), and the base branch's dispatch
# entry points (ov002). Walking arm_call/load relocs out of every body to
# fixpoint gives 9 ov100 bodies + 22 ov002 bodies, and ZERO arm9 targets that
# are not already in walk_window.map -- the base branch pulls no new engine
# code at all.
#
# TWO MATCHED TUs ARE DELIBERATELY ABSENT, both host copies instead
# (port/unmatched/PathLift_StateDispatch.cpp, the gate-200 PushBlock ruling):
#   src/func_ov002_020efa54.cpp            state installer, PMF dispatch
#   src/_ZN16dPathLiftActor_c12BaseBehaviorEv.cpp   per-frame tick, PMF dispatch
# Both form an MSVC pointer-to-member over a DELIBERATELY INCOMPLETE class.
# mwcc's PMF is a uniform 8-byte {fn, delta<<1|isVirtual} pair, which is what
# makes the ROM's record 20 bytes wide (the `mov r0,#0x14` in both bodies);
# MSVC widens an incomplete-class PMF to 16 bytes and the stride, the field
# offsets and the dispatch decoding all come out wrong.
#
# THE TU THAT IS *NOT* HERE ON PURPOSE, and why (the w5-B EyerokD0 class):
#   src/minigames/d_s_mg_jump2.cpp
# That name is an ov006 export (config/arm9/overlays/ov006/symbols.txt:887,
# size 0x118) and ov006 shares the 0x020efaf0 load window with ov002, whose
# own body there is func_ov002_020efaf0 (size 0xec -- a DIFFERENT body, the
# sizes alone settle it). ov100's Init calls that address through a reloc dsd
# annotates `module:overlays(2,6)`; the overlay actually resident with ov100
# is ov002, so the body is ov002's. Slicing the named TU would hand every
# PathLift ov006's MgBounceAndPounce constructor.
