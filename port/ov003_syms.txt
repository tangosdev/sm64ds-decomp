# ov003: the three SCENE classes' whole data span.
#
# ov003 carries three scene classes -- dScTitle_c (scene id 2, the debug level
# select), dScStarSel_c (scene id 4, the star select) and dScGameOver_c (scene
# id 8). THE PORT HOSTS ONE OF THEM, the star select; the other two are
# derived to the same depth and blocked on the two things named at the bottom
# of port/slice_scene1.txt. A scene is an actor, so hosting one is the ordinary
# registry shape -- the ROM's own SpawnInfo with its factory word repointed at
# the host, plus a vtable fill -- and the mount is what puts those SpawnInfos
# and the tables the classes read by name into host memory. See
# port/slice_scene1.txt and hal/scene_boot.cpp.
#
# THE MOUNT COVERS ALL THREE ANYWAY, and that is deliberate rather than sloppy:
# the span is contiguous ROM data, the two unseated classes' SpawnInfo records
# are inert bytes while their spawn-table slots stay null, and mounting the
# whole span is what the ov079/ov080/ov081 convention asks for. Whoever seats
# the other two changes nothing here.
#
# This file used to mount ONE table (the level-select row list, gate 31). It
# is now the WHOLE data span: every data symbol MINUS the three classes' own
# vtables, which are code-pointer tables nothing rebases. Only the star
# select's is a host array today (hal/scene_boot.cpp fills it); the other two
# are simply absent, because nothing in the link set names them. ovdata.py's
# --pack mode pads the resulting address gaps automatically, reproducing the
# ROM's own relative offsets.
#
# THE THREE VTABLES LEFT OUT, every slot read off ov003's relocs with the
# words taken from extracted/overlays/overlay_0003.bin (image length 0x4240 =
# the OVT's ram_size, so the read is at addr - 0x020ad660). All three are the
# 18-slot Scene shape and agree slot for slot with _ZTV8dScene_c (arm9
# 0x02092680) everywhere they do not override:
#
#   dScTitle_c    data_ov003_020b1650: 0 Init _ZN10dScTitle_c13InitResourcesEv, 3 Cleanup
#     020ada80, 6 Behavior 020ad814, 9 Render 020ad7a4, 12 OnPendingDestroy
#     020ad7a0, 16 D2 020ad660, 17 D0 020ad69c. Slots 1/2/4/5/7/8/10/11 are
#     Scene's own halves and 13/14/15 ActorBase's, all arm9 and all linked.
#
#   dScStarSel_c  data_ov003_020b1704: 0 Init _ZN12dScStarSel_c13InitResourcesEv, 3 Cleanup
#     020af86c, 6 Behavior 020af038, 9 Render 020ae6f4, 12 OnPendingDestroy
#     020ae6f0, 16 D2 020addfc, 17 D0 020ade54.
#
#   dScGameOver_c data_ov003_020b179c: 0 Init _ZN13dScGameOver_c13InitResourcesEv, 3 Cleanup
#     020b0b34, 6 Behavior 020b0894, 9 Render 020b0814, 12 OnPendingDestroy
#     020b0810, 16 D2 020b0580, 17 D0 020b05bc.
#
# THE THREE SpawnInfo RECORDS ARE IN THE MOUNT and they are the ROM's own.
# ACTOR_SPAWN_TABLE (arm9 0x02090864) relocates slot 2 to 0x020b1380, slot 4
# to g_profile_STAR_SELECT (0x020b16b4) and slot 8 to 0x020b1750, and each
# record's +4 halfword carries its own id back (2, 4, 8) -- the registry's
# free cross-check. dsd tags all three "overlays(0,3)" because ov000's window
# covers ov003's; GetSceneOverlayID sends ids 2/4/8 to ov003 and all three
# factories are ov003 code, so ov003 is the occupant.
#
# BOTH NAMES OF THE ROW TABLE ARE HERE AND THEY ARE ONE TABLE (gate 31's
# finding, unchanged). dsd named 0x020b1180 and 0x020b1181 separately because
# dScTitle_c::Behavior addresses the same array at byte 0 (the level column)
# and byte 1 (the entrance column), so the first symbol is ONE byte long by
# the next-symbol rule. --pack is what puts them back adjacent; without it the
# level column is a lone byte and every row past the first reads whatever the
# linker put next.
#
# The first is PINNED TO ONE BYTE. ovdata's default size is
# max(4, next-symbol delta), and the four-byte floor is exactly wrong here:
# it makes the level column overlap the entrance column and --pack refuses
# the layout. One byte is what the ROM gives it, and --pack then lays the
# 0x1ab-byte second symbol immediately after, which reconstitutes the table.
