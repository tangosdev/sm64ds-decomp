# through the port's ROM-shaped table. Under MSVC the file compiles only
#     extern "C" Cls *_ZN<Cls>D0Ev(Cls *thiz)
#     { thiz->Cls::~Cls(); Cls::operator delete(thiz); return thiz; }

# arm to the same object bytes as before: match.py 2004/b56 strict MATCHING

# objects, for every file below (d0arm_bytecheck.py, both header sets).

# WHY THE ROWS WERE UNLINKED: the same reason as the pilot's. MSVC folds the
# Itanium D1/D0 pair into one ??1Cls@@QAE@XZ, which the class's D1 TU already
# defines, so the D0 TU could not be compiled as well; the flat name the
# port's ROM-shaped vtable slot 17 calls was defined by a generated face out
# of port/faces_sync.txt instead. That face and this arm make the same two
# calls: the D1 body, then the row's own deallocation (Memory::Deallocate
# with the row's heap word, or Memory::operator_delete2), proved against
# config relocs by facegen's D0 rule and checked object-side by
# d0arm_check.py. The retired D rows are in port/faces_sync.txt, so exactly
# one definition of each flat name remains.
#
# THE EDGE IS THE ONE THE PORT ALREADY HAS: the ROM's own table word 17 of
# each class relocates to its D0, and the port's slot-17 thunks call the flat
# name. No new reference and no keep-alive. Slot 17 is not the actor teardown
# path (fBase_c::AfterCleanupResources dispatches slot 16 and frees directly,
# on the cartridge as here per the pilot's own cdb measurement); these bodies
# are linked but idle in every scenario the pilot measured.
