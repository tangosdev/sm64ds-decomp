1. THE HEADLINE, AND THE CORRECTION IT RESTS ON
------------------------------------------------

ov006 is the largest single prize left (1839 matched TUs) and
port/ov006_minigame_scout.txt section 5 ranked the thirty minigame ids by
closure size so the fan-out could start with the smallest. THAT RANKING IS
BUILT ON A CLOSURE THAT MISSES EVERY MINIGAME'S STATE MACHINE, and the
correction is the most useful thing in this file.

The scout rooted each id at its SpawnInfo record. A minigame's states are mwcc
POINTER-TO-MEMBER PAIRS: eight-byte {code, adjustment} records that live in
.data and are copied at overlay-load time, by the overlay's own .init
constructor, into .bss dispatch tables. Neither end of that is reachable from
the SpawnInfo. The .bss destination carries no relocations at all -- it is
zero-initialised storage -- and the .data source is reached only from .init.
So a walk from the SpawnInfo reaches the class's vtable and the vtable's
bodies, and then stops dead before the thing the class spends its frames in.

Measured on the pathfinder's own class, both ways:

    roots                          ov006 fn   ov004 fn   arm9 fn
    SpawnInfo only (the scout's)         17         97       547
    SpawnInfo + its own .init            48        160       560

The scout costed this minigame at "19 TUs". Its real closure is 48 + 160 = 208
ov006 and ov004 functions, of which 202 have a matched src TU. The scout's
ov006 column is low by 2.8x and its ov004 column by 1.6x.

THE RANKING SURVIVES ANYWAY, AND THAT IS WORTH SAYING PLAINLY. Section 3's
per-class table re-ranks on the vtable axis and MgShuffleShell is still among
the cheapest four, so the peer screening picked a correct target from an
incorrect number. The number still has to be fixed, because the fan-out is
about to cut twenty-nine more lanes from it.

4. THE WALL, AND IT IS THE SAME ONE FOR ALL THIRTY
---------------------------------------------------

A minigame's Behavior does this, and every one of the thirty does some version
of it (src/func_ov006_020e3528.cpp, dScMgCurling_c slot 6, verbatim):

    int j = c->idx;
    (c->*data_ov006_02141950[j].pmf[0])();

That is an mwcc POINTER-TO-MEMBER call and the port cannot compile it. Three
separate reasons, and each alone is fatal:

  1. THE STRIDE IS WRONG. mwcc's member pointer is eight bytes, {code,
     adjustment}. MSVC's single-inheritance member pointer is four. The src
     spells the table `struct Entry { PMF pmf[1]; }`, so MSVC strides the array
     by 4 where the ROM strides by 8, and every index past 0 reads half of one
     record and half of the next.
  2. THE WORD IS A DS ADDRESS. The table is filled by the overlay constructor
     from .data statics holding raw ROM code addresses. Verified word for word
     for this class: all twenty-five of the source pairs
     __sinit_ov006_021304ac NAMES read {code, 0} in the image. Read them off
     that constructor, one assignment at a time, and NOT by sweeping
     0x0213c1e4..0x0213c2bc. Those are the lowest and highest pair addresses,
     but the range spans twenty-eight eight-byte slots and three of them are
     not pairs at all: 0x0213c214 is MgShuffleShell_SpawnInfo (the factory word
     and the id twice, {020e3820, 01760176}), and 0x0213c264 and 0x0213c2ac
     hold unrelated non-zero data. A sweep would find three "pairs" with
     nonzero adjustments that no constructor ever copies.
  3. THE DISPATCH IS THE FULL ARM ITANIUM SEQUENCE, virtual bit in the
     adjustment's LSB and `this` advanced by the adjustment arithmetic-shifted
     right one. The ROM emits five instructions for it. MSVC emits its own,
     incompatible, shape.

THE WALL IS NOT ONLY ov006's, AND THAT IS THE FINDING THAT CHANGES THE
SEQUENCING. It was assumed above that the pointer-to-member problem was each
minigame's own state machine. It is not: the FRAMEWORK has one too, and the
framework's is the one a boot hits first.

src/func_ov004_020b87e0.cpp is dScMgBase_c's STATE SETTER -- sixty-three lines
that build a static table of twenty member pointers out of twenty ov004
globals, assign one into the object and dispatch it. It produced TWENTY-ONE of
the first link's ninety-five unresolved externals, all from that single TU, and
the mangling says exactly why:

    unresolved external symbol "void (__thiscall C::* data_ov004_020bc97c)(void)"
      (?data_ov004_020bc97c@@3P8C@@AEXXZQ1@)

MSVC encodes the member-pointer TYPE into the symbol name, so a global the ov004
mount emits as the C symbol _data_ov004_020bc97c can never satisfy it. And that
is the mildest of the three problems: the TU's own `struct C` puts field_8 at
+8 after a leading member pointer, which is only true at eight bytes, so MSVC
lays the object out wrong before any dispatch happens.

SO EVERY MINIGAME NEEDS THIS ONE TU SOLVED, and it is paid once. It is excluded
from port/slice_mg1.txt and stands as a named trap in hal/scene_mg_faces.cpp
that reports itself and sets no state. Solving it is worth more than any single
minigame: it is one 63-line host copy plus twenty routed addresses, and it
unblocks the framework half of all thirty.

  SOLVED, run mg5 lane BASESET. The trap is DELETED from hal/scene_mg_faces.cpp
  and the TU is host-copied in port/unmatched/MgBase_StateSetter.cpp, which
  carries the derivation: the twenty globals with their code words and their
  relocation rows, the ROM disassembly of the one-time table build and the
  dispatch, and the object layout the offsets force. Every adjustment word
  reads zero and all twenty bodies are matched, delinked and already sliced.

  "ONE 63-LINE HOST COPY PLUS TWENTY ROUTED ADDRESSES" WAS LOW, and the way it
  was low is the useful part. The setter is the ONLY writer of the message
  object's +0x18, and the framework's two per-frame self-field dispatchers
  (func_ov004_020b8714 and _020b8778) return on their first line while that
  field reads -1. So while the setter was a trap, NEITHER of them ever reached
  its call, and a run could report framework dispatch calls and zero unhandled
  addresses while dispatching none of the framework's state bodies at all. The
  real seat is the whole ov004 member-pointer universe, bounded from the source
  at SIXTY installs plus the setter's own twenty, and all eighty are routed:
  fifty-six in MgBase_StateSetter.cpp and twenty-four in
  MgBase_StateDispatch.cpp. runs/mg5/out/baseset/pmf_universe.txt is the
  listing.

  IT ALSO FOUND A THIRD ARGUMENT RIDE-THROUGH, and this one crashed rather than
  read a wrong value. hal/scene_mg.cpp's vtable thunks for slots 18 and 19 were
  declared with no stack parameter while every ROM caller pushes one, so each
  dispatch leaked four bytes of stack and a later `ret` took a garbage return
  address. Both slots were scanned out of the two overlay images word by word
  (runs/mg5/out/baseset/slot18_19_scan.txt): offset 0x48 is 22 sites, offset
  0x4c is 14, and the argument count is ONE at every one of them. Four slot-18
  thunks and one slot-19 thunk gained the ride-through parameter.

THE PORT ALREADY HAS THE ANSWER AND IT IS NOT CHEAP. port/unmatched/

  the object as two ordinary ints, so there is no symbol for a link to fail on
  AND no `::*` for a source sweep to match. src/func_ov006_020c3d18.cpp sits

      int v = *(int*)(c+4);         /* the adjustment word */
      void *p = c + (v >> 1);       /* this, advanced, arithmetic shift */
      if (v & 1) {                  /* the virtual bit, in the LSB */
          int *vt = *(int**)p;
          fn = (int*)*(int*)((char*)vt + *(int*)c);
      } else {
          fn = (int*)*(int*)c;
      }
      ((void(*)(void*))fn)(p);

  which is the five-instruction shape this section opens with, one for one. The
  ROM at 0x020c3d18, read out of extracted/overlays/overlay_0006.bin at base
  0x020bfec0:

      ldr   r1,[r4,#4]
      add   r0,r4,r1,asr#1
      ands  r1,r1,#1
      ldrne r2,[r0]  /  ldrne r1,[r4]  /  ldrne r1,[r2,r1]
      ldreq r1,[r4]
      blx   r1

  So it compiles, it links, and it reads clean. ONLY A RUN CONVICTS IT, and the
  first symptom is eip equal to a raw DS address: the two words it decodes are
  the mounted ROM's, and nothing in the source ever says so.

  ROUTE IT AT THE DISPATCH SITE, NOT BY REWRITING THE STORED PAIR. The ov085 /
  ov100 shape named further up -- write host addresses over the .data pair
  before anything reads it -- is wrong for this one, and the reason is a second
  reader. src/func_ov006_020c3b80.c compares the stored pair against its idle
  sentinel data_ov006_0213aee0:

      if (r2 == g[0]) { if (c[1] == g[1] || r2 == 0) ip = 0; }

  so it asks "is this slot idle" by value. A host address never equals a DS
  address, so a seat that rewrote the pair would leave that test permanently
  false while the dispatch itself looked fine. The host copy replaces the
  DECODE, and the stored pair keeps the ROM's own words.

SO A LINK IS NOT A COMPLETE DETECTOR FOR THIS WALL, AND THE CONCLUSION IS
STRONGER FOR THE FOUR THAN FOR THE TWO. The two are hidden by a linkage
specifier and a lane that re-declared the table at C++ linkage would see them.
The four cannot be surfaced by any link ever run, because there is no symbol to
resolve; only reading the source finds them. The fan-out sweeps for `::*` in
its own slice before it believes an LNK1120.

AND THE `::*` SWEEP IS NOT A COMPLETE DETECTOR EITHER, which lane FLW's third
shape is the correction to. Both of the detectors this section prescribes --
the link and the source sweep -- return clean over a TU that decodes the pair
in ints. The pair of them is still worth running, because between them they
find twelve of the thirteen; what they cannot do is license the word "none".
A slice whose class dispatches through a sub-object gets a RUN before that
claim, and the run is the detector: eip on a DS address is the tell.

The four are also the worse defect on their own terms. MSVC's four-byte member
pointer inside the object moves every field after it, so they read the WRONG
FIELD before any dispatch happens -- src/func_ov004_020b31b4.cpp reads `state`
at 0x1c where the ROM reads [r0,#0x20] -- where the two table cases are a wrong
stride within a correctly laid out object. All four layouts were re-derived
from the ROM disassembly rather than from the src structs.

WHAT MADE THE FIX SMALL, and it was not known when this file was written: the
overlay constructors are the only writers of these tables, EVERY ONE OF THEM IS
A PLAIN .c FILE THAT SPELLS THE PAIR AS TWO INTS, and eight bytes on MSVC is
eight bytes in the ROM. src/__sinit_ov004_020b948c.c and
src/__sinit_ov006_021304ac.c both do it. So the mount's tables have been
correct at the right stride all along and only the CONSUMERS were wrong, which
turns "reproduce the mwcc member-pointer ABI" into "re-type the table and route
the code word".

THE RULEBOOK COROLLARY, AND IT KEYS ON THE SPELLING RATHER THAN ON THE USE:

    A PAIR WHOSE CONSUMER SPELLS IT AS TWO INTS IS SAFE AS AN ALIAS.
    A PAIR WHOSE CONSUMER NAMES A MEMBER-POINTER TYPE NEEDS A HOST COPY,
    WHETHER IT IS CALLED OR ONLY COPIED.

An earlier version of this line drew the boundary at copied-versus-called, and
that boundary is wrong in the dangerous direction: it would authorise an alias
onto a table a consumer only copies THROUGH A PMF-TYPED STRUCT, and such a copy
moves four bytes where the ROM moves eight and shifts every field after it in
the same object, with no call anywhere. Being a copy is not what makes a copy
safe; `struct Pair { int a; int b; }` being eight bytes on both machines is.

data_ov004_020bc904 and _020bc914 are genuine {code, 0} member pointers and are
still ordinary aliases, and they pass on the spelling: both consumers declare
`struct Pair { int a; int b; }`. The four ov004 TUs that dispatch an object
FIELD fail on the same test and need host copies, even though no global of
theirs was ever unresolved.
