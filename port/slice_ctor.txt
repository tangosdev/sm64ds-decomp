# ---- RUNG C1c: THE TWO arm9 FADER STATICS, AND WHY THE ROW IS GONE --------
#
#   src/__sinit_02074edc.c     constructs a FaderColor into data_0209f5e8 and a
#                              FaderBrightness into data_0209f5d0, and pushes a
#                              destruct node for each. Lane CTOR2 put it on
#                              this slice; lane CTOR3 rung 0 took it off again.
#
# IT MOVES ONE LIVE VPTR, and that is what broke. hal/fader_wipes.cpp
# placement-news a host HalFaderWipe over data_0209f5e8 before main; the ROM's
# initialiser runs at Entry and is therefore the last writer, so the installed
# colour fader dispatches hal/scene_boot.cpp's data_0208eb2c instead of the
# host class's table. That table is ten words of zeroed host storage until
# l2_fill_0208ea6c() runs, and l2_fill_0208ea6c() runs from scene_fill_title(),
# late in the boot. Run link100 lane WM9's loopback pair reached
# Scene::SetFaders on the VS menu -> level transition before the fill and
# called address 0 through byte +0x14 of it; both windows died c0000005.
#
# THE ROW COMES BACK when the fader vtables are live from before the ROM's own
# .ctor walk -- rung 1 of lane CTOR3, in hal/scene_boot.cpp. The two 12-byte
# destruct-node cells hal/ctor_runner.cpp hosts for this initialiser stay where
# they are; nothing else hosts them and rung 1 needs them again.
