# Lane MEM of run mg6: dScMgMemory2_c, the "Memory Master" minigame.
#
# actor id 0x16b (scene 363), spawn symbol MgMemoryMaster_Spawn (0x020f75d4),
# SpawnInfo 0x0213d288, vtable data_ov006_0213d4d4. Every one of those was
# re-read out of the ROM by this lane rather than taken from the handover: the
# doubled-id word 0x016b016b sits at file offset 0x7d3cc of
# extracted/overlays/overlay_0006.bin (base 0x020bfec0), which puts the record
# at 0x0213d288 with the factory in the word before it, and the record reads
#
#     0213d288  d4 75 0f 02   0x020f75d4   the factory
#               6b 01 6b 01   363, 363     the id, twice
#
# The class name is src/func_ov006_020f730c.c's recovered header,
# dScMgMemory2_c, and it agrees with what the destructors write: slot 17
# (src/func_ov006_020f55b8.cpp) stores data_ov006_0213d4d4 into the object's
# first word before unwinding, which is the strongest single confirmation that
# 0x0213d4d4 is the right table for this id.
#
# ---- THE HIERARCHY IS THREE DEEP, AND THE HANDOVER DID NOT SAY SO ----------
#
#     Scene -> dScMgBase_c         data_ov004_020bc0c0  36  (the framework's)
#           -> dScMgSingle3DBase_c data_ov006_0213e448  36  ovr 8, mark 6, nosrc 0
#           -> dScMgMemory2_c      data_ov006_0213d4d4  36  ovr 14, mark 12, nosrc 0
#
# port/mg_fanout_costs.txt section 3's 0x16b block lists one vtable and says
# nothing about an intermediate base, so a lane that filled one derived table
# would have left SIX of its own slots (2, 5, 7, 10, 26, 33) holding raw DS
# words. Both edges are read off code:
#
#   src/MgMemoryMaster_Spawn.c calls func_ov004_020b2adc(p), writes
#   data_ov006_0213e448 into p[0], constructs Particle::SysTracker at +0x471c,
#   then writes data_ov006_0213d4d4 over it.
#   src/func_ov006_020f55b8.cpp (slot 17, D0) unwinds in the opposite order,
#   0x0213d4d4 first and 0x0213e448 second.
#
# It is the SAME middle table dScMgFlower_c (0x186) and dScMgCup_c (0x169) sit
# under; port/slice_flw.txt and port/slice_mga361.txt derived it independently
# and this lane's read agrees with both word for word.
#
# ---- THE WIDTH IS 36 ON BOTH NEW TABLES, CHECKED THREE WAYS ---------------
#
# port/mg_fanout_costs.txt section 11's checks, because twelve widths in that
# file's own section 3 table were phantoms:
#
#   1. SPAN. config/arm9/overlays/ov006/symbols.txt puts the next symbol after
#      data_ov006_0213d4d4 at data_ov006_0213d564, exactly 0x90 = 36 words on,
#      so a 37th slot cannot exist inside the table. The middle table's next
#      symbol is data_ov006_0213e4d8, also exactly 0x90 on.
#   2. TERMINAL SLOT. Slot 35 of both tables holds 0x020ad660, the word every
#      dScMgBase_c-derived table holds there.
#   3. WHAT THE WORD PAST IT IS. Index 36 of 0x0213d4d4 reads 0x00000001 and
#      index 36 of 0x0213e448 reads 0x050a0a0f; neither is an address in any
#      module, and each is the first word of the next config symbol. Section 11
#      independently names 0x16b's as 0x00000001.
#
# ---- FOURTEEN OVERRIDES, TWELVE MARKERS, ZERO WITHOUT A SOURCE ------------
#
# port/tools/vtablerows.py --vtable 0x0213d4d4 --width 36 prints ovr 14,
# mark 12, nosrc 0, which is what section 3's row predicts. ALL TWELVE MARKERS
# WERE ALREADY RULED REAL_DECOMP against the ROM by run link60 lane MGB, with
# per-body evidence in port/tools/inferred_stub_adjudicated.txt, so this lane
# owed no adjudication and invented none. The two unmarked overrides are slot 16
# (func_ov006_020f5564) and slot 33 (func_ov006_0210a708).
#
# Six of the fourteen (slots 2, 5, 7, 10, 26, 33) are the MIDDLE base's bodies,
# which this class does not override; the eight that are its own are slots
# 0, 6, 9, 16, 17, 18, 19 and 21.
#
# ---- HOW THIS LIST WAS DERIVED --------------------------------------------
#
# A relocation closure over config/arm9{,/overlays/ovNNN}/relocs.txt and
# delinks.txt, module-resident (ov002, ov003, ov006 and ov007 share an address
# window, so a reloc's own module: field decides, never the address), rooted at
#
#   - every word of BOTH new vtables, read out of the shipped overlay image
#   - the factory at 0x020f75d4
#   - the twenty-nine state code words, read out of the image at the pair
#     addresses this class's overlay constructor names
#   - the .init range 0x021314e4..0x021318a0, which is the constructor itself
#
# and it reaches 79 ov006, 122 ov004, 658 arm9 and 6 itcm text blocks. The
# listing is runs/mg6/out/MEM/closure_16b.txt. THE arm9 HALF IS NOT REPEATED
# HERE for port/slice_mg1.txt's reason: those TUs are already compiled into the
# build and come back through /OPT:REF the moment ov004 or ov006 references
# them, so listing them would be lines that change nothing. Only the ov006 and
# ov004 delta is below, plus whatever the link asked for after it.
#
# THE STATE BODIES ARE NOT IN THAT CLOSURE AND ARE ADDED BY HAND. They are
# reached only through mounted DATA words -- the pair tables -- so no text
# relocation names them, which is the row port/mg_fanout_costs.txt section 10
# calls "they arrive with the dispatch, not with the closure". Ten of this
# lane's lines are that: 0x020f6904 and the nine model sub-object bodies
# unmatched/MgMemory2_FieldPmf.cpp routes.
#
# ---- SEVEN TUs ARE HOST-COPIED AND ARE COMMENTED OUT BELOW ----------------
#
# The mwcc POINTER-TO-MEMBER wall. Their bodies are in port/unmatched/
# MgMemory2_StateDispatch.cpp (the four table dispatchers) and port/unmatched/
# MgMemory2_FieldPmf.cpp (the three that read the pointer out of an object
# field), each verbatim but for the table or field declaration and the call.
#
# ONLY TWO OF THE SEVEN WOULD EVER BE NAMED BY A LINK, and this lane swept for
# `::*` across its whole 869-file closure rather than trusting an LNK1120, which
# is the rule port/mg_fanout_costs.txt section 4 states. The sweep
# (runs/mg6/out/MEM/pmf_sweep_16b.txt) found fourteen: these seven and the seven
# ov004 ones MG1/MG2/BASESET already host-copied.
#
#   LINK-VISIBLE
#     func_ov006_020f7234   ?data_ov006_02142440@@3PAUEntry@@A
#     func_ov006_020f5c40   ?data_ov006_02142408@@3PAP8C77@@AEXH@ZA
#   SILENT -- the table is declared inside extern "C", so it mangles as the
#   plain C name the ov006 mount already defines and the linker is satisfied
#   while the stride is wrong
#     func_ov006_020f7458   (vtable slot 6, the Behavior)
#     func_ov006_020f71c8
#   SILENT -- the member pointer is an object FIELD, so no symbol is emitted for
#   it in any linkage and no link anywhere can name it
#     func_ov006_020c19d0   the model sub-object's tick, at this+0x4f38
#     func_ov006_020c07e8   reached from it, and the one whose src STRUCT is
#                           wrong at four bytes: its pad is spelled
#                           `0xc8 - 0xb4 - 8`, so MSVC would put every field
#                           after the pointer four bytes early
#     func_ov004_020b52fc   THE FIND. Reached every frame through
#                           func_ov004_020b65e4, which vtable slot 6 calls; six
#                           lines; in NO lane's host-copy set and in no wired
#                           slice. See MgMemory2_FieldPmf.cpp section 4.
#
# ---- ONE STATE HAS A src TU AND NO DELINK BLOCK, AND IT IS NOT A FLOOR -----
#
# 0x020f6904 is slot 5 of data_ov006_02142440. The delink block before it ends
# at 0x020f6904 and the next starts at 0x020f6a00, so port/tools/stategen.py
# cannot emit a case for it -- but src/func_ov006_020f6904.c EXISTS, bannered
# NONMATCHING (div=29, logic verified vs ROM). NONMATCHING TUs are routinely
