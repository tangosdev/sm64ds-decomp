# THE ONE ov006 ROW OF THE TEN THAT STAYS, and why.
#
#   unmatched/MgSnowball_ModelRender.cpp  (src/func_ov006_02127d10.c)
#       The fold is dead here too, but it is not this file's only reason. Its
#       matched source does not dispatch through a shadow class at all: it
#       reads the vtable word by hand and calls it CDECL --
#
#           void (*fn)(void*, int*) =
#               *(void(**)(void*, int*))((char*)(*(void**)self) + 0x14);
#           fn(self, vecArr);
#
#       Byte +0x14 is ROM index 5 and _ZTV5Model[5] is Model::Render, so the
#       SLOT is right; the CONVENTION is not. hal/cxxname_bridge.cpp's mv_render
#       is `static void __fastcall mv_render(void *self, void *, const void *s)`
#       -- `this` in ecx, the way a host C++ virtual call passes it -- and a
#       cdecl call through the same word puts `self` on the stack and reads the
#       scale out of the slot that held it. That is the receiver drop the two
#       MgShared4f38 headers describe at 0x020c2924, and the repair is a
#       VIRTUAL_CALL row in port/tools/hostgen.py, which lane FOLD2 does not
#       own. Named and left. Two more MMIO stores in the same body would be
#       handled by the same hostgen pass, so the file is one table row away
#       from retiring.
#       REFERRER, for whoever takes it: from:0x02140030 kind:load to:0x02127d10
#       (data_ov006_0214000c + 4*9, the class's own slot 9).
#       RECORD: kind:function(arm,size=0x694) addr:0x02127d10,
