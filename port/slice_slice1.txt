# run link100, lane SLICE1 -- THE CONSOLIDATION GAP, BATCH 1.
#
# Every row here is a translation unit that exists in src/ on this branch, owns at
# least one symbol walk_window.exe reported unresolved in the first link after the
# main -> port sync (out/SYNC5/build_d10.log, 3327 unresolved externals), and is
# compiled by NOTHING: it is on no slice list, in no CMake block and in no hostgen
# generation list. main folded hundreds of one-function TUs into class TUs in its
# 2026-09 consolidation and the port never took the new files.
#
# HOW THE SET WAS DERIVED, and why it is not a filename scan.
#
# 1. The universe is walk_window.exe OWN unresolved block in build_d10.log, flat C
#    names only (2639 of the 3327; the other 688 are MSVC-decorated and belong to
#    the alias question, not to this one).
# 2. Each name is resolved to its ROM address out of the module symbols.txt that
#    carries it, and then to its owning TU out of THAT MODULE OWN delinks.txt.
#    Running every module ranges together lands ov031 bodies in Wiggler TUs; the
#    per-module read is the only correct one (lane SYNC5 measured that trap).
# 3. Liveness is read off the BUILD, not off the slice lists: the 8794 objects on
#    walk_window own link line in build/port/build.ninja. A TU is a candidate only
#    if it is not one of them. That is what separates this batch from the rows
#    SYNC5 quarantined and from the rows another slice already carries.
# 4. Collision prediction is per SYMBOL and definition-shaped, not a name grep: for
#    every ROM function symbol inside the candidate .text ranges, the scan asks
#    whether any object already on the link line DEFINES it (a per-function
#    leftover whose stem is that symbol, or a host copy whose text has that name
#    followed by a parameter list and an opening brace). Only TUs with ZERO
#    predicted collisions are in this batch. The nineteen that collide are held
#    for the next one with their colliding host copies named per symbol.
# 5. A candidate is dropped as well when port/host-src carries a GENERATED copy of
#    the same relative path on that link line. The per-symbol hostgen writes a
#    patched twin of the raw TU and compiles the twin, so adding the raw file
#    would be a duplicate of every body in it. 41 candidates went out that way and
#    are listed in runs/link100/out/SLICE1/other_reason.txt: their names are
#    unresolved for some reason other than nothing compiling the body.
#
# WHAT THIS BATCH DOES NOT DO. It retires nothing and it moves no host copy, by
# construction: a row is here only because nothing else defines any body in it.
# src/actors/Player.cpp is excluded by the brief, and the fourteen candidates that
# are already quarantined by compile family (C2821, C2561, C2372, C2065) stay
# quarantined; they are decomp-side asks, not slice rows.
#
# WHAT IT IS WORTH, HONESTLY. These 74 TUs own 95 of the 2639 flat unresolved
# names. Most of the rest are not a slice gap at all: they are owned by TUs the
# build ALREADY compiles, which since main langmode migration define the body as a
# real C++ member or free function, so the ROM flat name needs a flat -> decorated
# /alternatename (the tree already carries 46 of that direction) and not a row on
# any list. That measurement is in runs/link100/out/SLICE1/other_reason.txt.
#
# THE ROWS, module by module. The count after each is how many of walk_window own
# unresolved names that TU owns, and the shape is how the TU defines them:
# FLAT means the file defines the ROM C name itself (the row resolves it outright);
# MEMBER means the file defines a C++ member and the flat reference still needs an
# alias afterwards, so the row is the PREREQUISITE for that alias, not a substitute.
#
