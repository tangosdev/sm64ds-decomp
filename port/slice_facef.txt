# LANE FACEF (run link100, wave 7): THE CALLING-CONVENTION-FACE ROWS.
#
# out/EXCEPT/census.md sorted the port's 414 documented host-ABI exceptions by
# the mechanism each row's own PORT_HOST_ABI tag states. Family F -- "calling-
# convention face", 19 rows, ~10 real -- was ranked third and left for a later
# lane, together with twelve family E slot-5 rows that carried a NAMED SECOND
# REASON on top of the numbering. This file is that lane, one row at a time.
#
# THE DERIVATION IS PER ROW AND IT IS FROM THE ROM. For every row below:
#   the REFERRER is either the class's own vtable slot 9 word, read out of the
#     RAW overlay image at that overlay's .text base (config/arm9/overlays/
#     ovNNN/delinks.txt line 1) -- with the RTTI name string at vtable-4 read
#     through the typeinfo record, so the table is identified by what the ROM
#     calls it and not by a filename -- or, for a body the ROM calls directly,
#     the arm_call row in that overlay's relocs.txt;
#   the RECORD is the kind:function(arm,size=..) line at the destination in
#     that overlay's symbols.txt;
#   the DISPATCH is the ROM's own instruction at the matched TU's one call
#     site, read out of the same image.
# Verified by ADDRESS, never by filename. Every row below agreed.
#
# WHAT THE ROWS HAVE IN COMMON. All of them state, in one wording or another,
# that the host model vtables are numbered the way MSVC numbers them -- one
# destructor slot where Itanium spends two -- so a matched TU dispatching
# through a LOCAL ROM-ORDER SHADOW lands one slot short. Lane SLOT5F respelled
# the ROM's D1/D0 pair as two plain virtuals under _MSC_VER in
# include/ModelBase.h and its five siblings, and port/hal/cxxname_bridge.cpp
# fills both tables in ROM numbering today:
#
#     cxxname_bridge.cpp:520-522   _ZTV5Model[3..5]     = mv_updateverts /
#                                                         mv_virtual10 / mv_render
#                        :575-578  _ZTV9ModelAnim[2..6] = mv_dosetfile /
#                                                         ma2_updateverts /
#                                                         ma2_virtual10 /
#                                                         ma2_render / ma2_virtual18
#
# so slot 4 is Virtual10 and slot 5 is Render on both, and Virtual18 keeps its
# own slot 6 rather than being displaced. The dual fill is gone.
#
# THE SECOND REASONS, and each was checked rather than inherited:
#   THE RETURN TYPE ("the shadow's methods return int where Model::Render
#     returns void, MSVC decorates that differently", port/unmatched/
#     Jrb_Renders.cpp). Not a fact about the host. `b->m(0)` is an INDIRECT
#     call through the object's own vptr; an indirect call decorates nothing,
#     and the declared return type only decides whether EAX is read afterwards.
#     Every one of these bodies discards it. Lane EXCEPT shipped four seats of
#     exactly this shape (port/slice_except2.txt) and the battery was green.
#   MODEL SLOT 4 ("MSVC's slot 4 on Model is Render, and dispatching there
#     would draw the door's key twice and never place it", port/unmatched/
#     Door_Render.cpp). True while the fold was real; dead since SLOT5F. This
#     is the FIRST row in the tree to need Model slot 4 on the ROM numbering,
#     which is why it is in gate 1 rather than behind the slot-5 rows.
#
# TWO OF THESE MATCHED TUs CARRY THE INFERRED-STUB MARKER and both are
# admitted, not smuggled: src/func_ov100_021454c8.cpp and
# src/func_ov016_02112b28.cpp are listed in port/tools/
# inferred_stub_adjudicated.txt as REAL_DECOMP with a match.py 2004/b56
# strict-reloc MATCH recorded against the ROM (lane STUBADJ,
# runs/link100/out/STUBADJ/verify.txt). inferred_stub_guard.py admits an
# adjudicated symbol and refuses an unadjudicated one; both still owe the
# decomp-side marker correction, which is not this lane's file.
