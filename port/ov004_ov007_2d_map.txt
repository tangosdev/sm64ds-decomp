2. THE SLOT: WHY NOTHING IN A LEVEL WALK CAN REACH THEM
-------------------------------------------------------

Load addresses, from the ROM's OWN overlay table. This file first quoted
extracted/dsd/arm9_overlays/overlays.yaml and every END below was wrong; the
eight BASES were right and the slot conclusion never depended on the ends.
The yaml's code_size is not the overlay's RAM size for a compressed overlay,
which is where the error came from.

DERIVATION. The NDS header word at 0x50 is the arm9 overlay table's file
offset and 0x54 its size; the table is 32-byte entries of
(id, ram_address, ram_size, bss_size, static_init_start, static_init_end,
file_id, flags). The image occupies base .. base + ram_size and the loader
zeroes bss beyond that, so the full footprint ends at
base + ram_size + bss_size. Both columns are given because the two answer
different questions: the image end is where file-backed bytes stop, the
footprint end is what an address-containment test has to use.

    overlay   base         image end    footprint end
    ov000     0x020aa420   0x020bf4e0   0x020bf4e0
    ov001     0x020aa420   0x020ad620   0x020ad660
    ov002     0x020ad660   0x0210d9a0   0x021111a0   in-level engine
    ov003     0x020ad660   0x020b18a0   0x020b18a0   star select, level select
    ov004     0x020ad660   0x020beb60   0x020bfec0   minigame framework
    ov005     0x020bfec0   0x020c3020   0x020c3020
    ov006     0x020bfec0   0x021402e0   0x021430a0   the minigames
    ov007     0x020ad660   0x02103340   0x02104c40   title / file select

ov002, ov003, ov004 and ov007 are four occupants of ONE slot at 0x020ad660.
They are mutually exclusive by construction. walk_window runs the ov002
occupant. ov004 and ov007 are not "not linked yet", they are a different mode
of the game, and the only honest way to reach them is to enter that mode.

The corrected ends also remove a contradiction the yaml numbers created.
ov004's footprint ends at 0x020bfec0, which is EXACTLY ov005's and ov006's
base, and ov001's ends at 0x020ad660, which is exactly ov002's base. There is
no overlap anywhere, so ov004 and ov006 are cleanly co-resident, which is what
section 3 needs them to be and what the yaml-derived ends appeared to forbid.

WHICH IMAGE TO READ. extracted/overlays/overlay_NNNN.bin is the correct source
and its byte length equals the OVT's ram_size for all eight of these
(ov000 86208, ov001 12800, ov002 394048, ov003 16960, ov004 70912, ov005
12640, ov006 525344, ov007 351456). extracted/dsd/arm9_overlays/ovNNN.bin
matches ram_size for none of them.

------------------------------

Scenes are actors. The scene machinery is in arm9 and every piece of it is a
matched TU:

        writes data_02092664 = id, data_0209f5b8 = param

    Scene::SpawnIfNecessary()           0x0202e26c
        if data_02092660 == 0 and data_02092664 != 0x187:
            func_02013edc(id, param, 1)
              -> func_02042fe4  -> func_02043098(id, 0, param, 1)
                 which calls (*data_020a4bb8[id])(), the ACTOR SPAWN TABLE
                 factory. data_020a4bb8 is set to data_02090864 in
                 func_0201a054, so this is ACTOR_SPAWN_TABLE[id].

    Scene::PrepareToSpawnBoot()         0x0202e300   sets id = 0 or 0x168

    GetSceneOverlayID(id)               0x0201a7dc

        id 3, 6, 7                                     -> ov002
        id 1                                           -> ov007
        id 2, 4, 8                                     -> ov003
        id 5                                           -> ov005

    func_0201a798(ovId)   LoadOverlay, AND LoadOverlay(ov004) first when the

                          ov004 is ever loaded.
    func_0201a754(ovId)   the matching unload pair.

So:

    ov007  is entered by spawning ACTOR ID 1. symbols/actor_renames_report.txt

               from:0x02090868 kind:load to:0x02103264 module:overlay(7)
           0x02090868 is ACTOR_SPAWN_TABLE + 4, the slot for actor 1.

    ov004  is entered ONLY as a passenger of ov006. There is no scene id that
           loads ov004 by itself. Any real bring-up of the ov004 category is

-----------------------------------------

Exactly one linked arm9 caller reaches ov004 code, and it is the two
LoadFont relocations above:

        LoadFileAt(0x980e, func_ov004_020adc4c());
        data_0209d6f8 = func_ov004_020adc4c();

That blocker is removable. data_ov004_020beb60 is BSS, four bytes by ROM span

6. A MISROUTED EDGE: SPINDRIFT'S KILL-BY-INVINCIBLE PATH IS A SILENT NO-OP
---------------------------------------------------------------------------

Three ov004 TUs are counted as linked in walk_window today:

    src/func_ov004_020adc1c.c
    src/func_ov004_020adc00.c
    src/_ZN5Enemy20KillByInvincibleCharERK10Vector3_16R6Player.c

They are reached from ov081's Spindrift, per the note at the top of
hal/actor_classes_ov081.cpp.

ov002 defines a function at ONE of those three addresses and not the other
two: func_ov002_020ada40 sits at KillByInvincibleChar's 0x020ada40, and ov002
has no function boundary at all at 0x020adc1c or 0x020adc00. (It also has
func_ov002_020aea30 at Enemy::KillByAttack's 0x020aea30, which is a fourth
address, not one of the three seated here.) dsd tagged every level-overlay

    12x ov065 -> 0x020aea30   ov004: Enemy::KillByAttack   ov002: func_ov002_020aea30
     8x ov090 -> 0x020aea30
     5x ov062 -> 0x020aea30
     3x ov081, 3x ov084, 2x ov070, 1x ov091 -> 0x020aea30
     3x ov084, 2x ov062, 2x ov065, 2x ov081, 2x ov102, 1x each ov063 ov064

ov065, ov062, ov081, ov084, ov090, ov102, ov063, ov064, ov070, ov091 and

only alongside ov006 for a minigame scene. On co-residency grounds alone the
destination of every one of those calls is the ov002 body, not the ov004 one.

THE BODIES ARE NOT THE PROBLEM. This file first guessed that the three linked
ov004 TUs were ov002 bodies wearing ov004 names, and that the ov004 category's
3/276 was fictitious. THAT IS REFUTED. Both images were disassembled from
extracted/overlays, size-matched against the ROM's OVT (see section 2): the
ov004 literal pools match the matched sources exactly, and ov002 has no
function boundary at all at two of the three addresses. The three seated ov004
bodies are genuinely ov004's, and ov004's 3/276 was never fictitious at the
body level. The first version of this section was wrong and the byte evidence
is what settles it. That evidence was reachable all along; it was missed here
because this lane read extracted/dsd/arm9_overlays/ov004.bin, which is not the
overlay's RAM image (section 2), and then wrote off the resulting garbage as an
untrustworthy image instead of as the wrong file.

THE EDGE IS THE PROBLEM, AND IT IS A LIVE DEFECT, NOT AN ATTRIBUTION NIT. The

7. WHAT THE ntr LAYER ALREADY MODELS, AND THE GAP LIST
------------------------------------------------------

The 2D hardware these two overlays drive is in better shape than the brief
assumed. port/ntr already has:

    ppu.cpp       engine A text-mode backgrounds, and a full OBJ layer:
                  128 OAM entries, 1D and 2D tile mapping, the DISPCNT tile
                  boundary shift, 16- and 256-colour, affine sprites with the
                  four OAM matrix halfwords. Plus the BMP writer.
    ppu_sub.cpp   engine B, and it is the better one: sprites and backgrounds
                  resolved together per pixel by priority, sprite-vs-sprite by
                  OAM index, which is what the HUD needs.
    io.cpp        real memory mapped at the DS addresses, including palettes,
                  VRAM and OAM, with write-triggered side effects.
    gx.cpp        the geometry engine and software raster.
    texture.cpp   all seven texture formats.

Gaps, per cluster, from what the two overlays actually poke:

  a. OBJ WINDOW. CORRECTED AND LARGELY CLOSED by run link60 lane W2D; see
     port/ppu_gap_audit.txt. Two things this paragraph said were wrong.

     THE MODE IS 2, NOT 3. OAM attribute 0 bits 10-11 are 0 normal,
     1 semi-transparent, 2 OBJ WINDOW, 3 prohibited (bitmap on the DS). What
     ppu.cpp and ppu_sub.cpp skipped was mode 3, under a comment naming it the
     OBJ window, so they dropped bitmap sprites and DREW window sprites, which
     on hardware are invisible and contribute only a mask. Anything reasoning
     from "objMode 3" to a conclusion about the OBJ window is reasoning about
     the wrong field value.

     THE WINDOW REGISTERS ARE MODELLED, and were already, on BOTH engines:
     ppu_sub.cpp read_windows/window_mask and the mirror of it in
     hal/message_compositor.cpp, which is engine A's live 2D path.
     ntr/ppu.cpp is in no live path at all.

     ppu_sub.cpp now models the OBJ window for real (mask buffer, DISPCNT bit
     15, WINOUT's upper six bits, precedence WIN0 > WIN1 > OBJwin > WINOUT).
     ppu.cpp and message_compositor.cpp take the corrected skip only; neither
     can carry the mask, the second because its BG loop runs before raster_obj.
     port/tests/smoke_objwin.cpp pins the contract.

     MEASURED NEED: none yet. Zero mode-1, mode-2 and mode-3 objects on either
     engine across 1200 sampled frames of level 1 and scene 4. The title screen
     is still unmeasured for a different reason than "nobody looked": it faults
     inside InitResources before frame 0, so it reaches no scan-out at all.
  b. SEMI-TRANSPARENT SPRITES draw opaque in ppu_sub.cpp, and the colour
     special effects (BLDCNT/BLDALPHA) are only partially there. ov007's
     RequestScreenFade drives a fade; whether it goes through the brightness
     registers (which are modelled, hal/fader_wipes.cpp uses
     G2x::SetBlendBrightness) or through alpha blend (which is not) is
     unmeasured.
  c. AFFINE AND ROTATION/SCALING BACKGROUNDS. ppu.cpp and ppu_sub.cpp are
     text-mode background scan-out. Extended-affine and bitmap BG modes are
     not modelled. The title's castle00 layer is a candidate.
  d. THE 3D FONT. hal/sub_screen.cpp's LoadFont3D is a documented exception
     because the src drives the card loader and asm copies into an unhosted
     3D-font VRAM path. Both overlays render text.
  e. TOP-SCREEN BG2 TEXT. hal/sub_screen.cpp's LoadControllerModeText is a
     documented exception for the same reason: the main engine's text path is
     not hosted.
  f. TOUCH. ov004's dMgPsOpt_c::TouchIcon_c and ov007's "touch_panel" both
     read the touch panel. walk_window has a touch bridge (the last left
     click is published in framebuffer pixels) but no touch-panel register
     model.

  g. BG0 IN 3D MODE WAS COMPOSITED AS A TILE BACKGROUND. Added and CLOSED by
     run mg5 lane YTILE, which found it by chasing a player report of "blocky
     solid-colour tiles" on scene 390.

     Engine A's DISPCNT bit 3 is the BG0 2D/3D SELECTION. With it set BG0 is
     the 3D engine's output layer and BG0CNT's character and screen bases mean
     nothing. hal/message_compositor.cpp's read_bg never read the bit, so on
     every scene that set it with BG0 enabled the compositor decoded whatever
     bytes happened to sit at BG0CNT's bases into 8x8 blocks and painted them
     OVER the real artwork at BG0's priority. Nothing was missing from the
     frame; a layer was being invented into it.

     The bit is pinned by the decomp's own code, not by docs:
     src/_ZN2GX15SetGraphicsModeEiii.c is GX::SetGraphicsMode(dispMode, bgMode,
     bg0_3d) and its whole use of the third argument is `reg = (c << 3) | reg`.
     ntr/ppu.cpp's OBJ note says the same thing from the other side and
     ntr/ppu_audit.cpp's 3D section already printed the rule as prose. Three
     places in this tree described it and none implemented it.

     MEASURED, scene 390 (dScMgFlower_c), DISPCNT 0x00001508 / BG0CNT 0x0001
     (chars and screen both 0x06000000, priority 1, over BG2 at priority 3).
     Against a reference image built from the ROM's own files -- the LZ77
     decode of /MG/d_2d_mg_bg_flower_up_ncg.bin and _nsc.bin through the
     palette _ncl.bin loads at byte offset 0x60 -- the top screen went from
     44736/49152 pixels correct (91.0%, 55 of 768 tiles wrong in all 64 of
     their pixels) to 48357/49152 (98.4%, 0 tiles fully wrong). The remaining
     795 are the four HUD sprites the reference does not model.

     IT WAS NEVER FLOWER-SPECIFIC. Sampled with SM64DS_PPU_AUDIT: scene 1
     (DISPCNT 0x00011b08) was inventing 2172 px and scene 4 (0x08011d08) 8823
     px, 18% of its top screen. Every mounted LEVEL runs 0x40011803 with BG0
     disabled, so no level frame moves: level 1's selftest BMP is byte
     identical across the fix at the same .dsstate base AND span
     ([0xbcc000, 0xcb63c8), 959432 bytes), which is what
     notes/port-selftest-bmp-gate.md requires before two BMPs may be compared.

     WHAT IS STILL OPEN, and it is the other half of the same register. The
     fix stops the port inventing a layer; it does not put the real 3D layer
     in its place. The port renders 3D into the framebuffer before the
     compositor runs and the compositor only writes over it, so a 2D BG that
     on hardware sits BEHIND the 3D layer still covers it here -- on scene 390
     that is the full-screen opaque BG2 at priority 3 under the 3D layer at
     priority 1. Closing it needs a 3D coverage mask the framebuffer does not
     carry, and it is the same gap the "1st-target BG blending over the 3D
     layer" note in that file's header already records.

     ONE PROXY THAT DOES NOT WORK, recorded because a lane will reach for it:
     the distinct-colour count of the captured BMP is 188 before the fix and
     188 after. The invented tiles drew through the scene's own palette, so a
     colour census cannot see them. The reference-image comparison can.

None of a..f blocks LINKING either overlay. They block the overlay doing
anything visible once linked. That distinction is the whole shape of this
category: the code is 97% matched and the hardware is 70% modelled, and what
is missing is the MODE, not the pixels. (g is a different shape from all of
them: not a mode the port failed to model, a mode it modelled as the wrong
thing.)

----------------------------

  minigame actor id -> ov006 scene -> ov004 base class. Landing ov004 means
  landing ov006 with it: 1839 + 276 TUs, an ov006 data mount, 24 ov006 data

  rest is ov007 plus arm9. What it needs, in order:

    2. an ov007 data mount (port/ov007_syms.txt + tools/ovdata.py, the ov002

    3. the 123-symbol external closure listed in section 4. 98 of those are

9. WHAT AN ov004 OR ov007 MOUNT WOULD DO TO ovdata.py --cross
--------------------------------------------------------------

Asked for by the coordinator on the back of the ov006 lane's scout report,
which measured that a hypothetical ov006 mount would drop 985 of 1302
currently-resolving cross-mount pointers, because ovdata's contest test is
purely address-based and does not model residency. ov004 and ov007 sit in the
same shared window, so the same artefact applies to them. This is the
measurement for THIS category. It is a static simulation of cross_mode against
the 81 sidecars the current build writes, not a mount; this lane did not mount
either overlay.

The test being simulated is cross_mode's, exactly: a want is dropped when
window_count(target) > 1, where the windows are every mounted overlay's whole
DS footprint, image plus bss. A per-symbol mount and a whole-image mount
present the SAME window to that test (write_map's docstring says so), so the
mount style does not change any number here.

WHICH WINDOW, AND WHY IT DOES NOT MATTER. The two hypothetical windows were
first derived from the yaml, whose ends are wrong (section 2). All three
routes to a window have since been run: the yaml-derived one, ovdata's own
formula, and the ROM OVT truth. All three give IDENTICAL results, down to the
same three lost pointers. The conclusion below is route-independent, and the
reason is that the ends only differ well inside ov002's span, which is
contested either way. The OVT windows are ov004 0x020ad660 .. 0x020bfec0 and
ov007 0x020ad660 .. 0x02104c40; the yaml ones were 0x020c3220 and 0x02104720.

BASELINE, as built at c1a6da46d, verified against the tool's own summary line:

    215 pointers rebased across 81 mounts, 6101 left raw
    (1009 of the 6101 into a contested window, the rest arm9 or unmounted)

The windows that already contest the shared slot are ov002 (0x020ad660 ..
0x021111a0) and ov003 (0x020ad660 .. 0x020b18a0).

ADDING ov004's WINDOW (OVT 0x020ad660 .. 0x020bfec0; the yaml's
0x020c3220 gives the same three lines):

    contested            1009 -> 1182   (+173)
    resolving pointers LOST                0
    resolving pointers                   215 -> 215

ADDING ov007's WINDOW (OVT 0x020ad660 .. 0x02104c40; the yaml's
0x02104720 gives the same three lines):

    contested            1009 -> 1699   (+690)
    resolving pointers LOST                3
    resolving pointers                   215 -> 212

BOTH: identical to ov007 alone. ov004's window is a strict subset of ov007's.

READ THE +173 AND +690 CORRECTLY. They are pointers moving between two flavours
of RAW, not pointers being lost. A word that had no host provider and was left
raw as "arm9 or an unmounted overlay" is still left raw, now counted as
"contested" instead. The number that matters is the third line, and for these
two overlays it is 0 and 3.

THE THREE, in full, so the residency lane can weigh them:

    ov025  port_ov025_image+7372      -> 0x02100000  provider data_ov002_020ff480
    ov045  port_ov045_image+5500      -> 0x02100000  provider data_ov002_020ff480
    ov045  data_ov045_021126d0+76     -> 0x02100000  provider data_ov002_020ff480

All three name one ov002 address, and ov025/ov045 are level actor overlays
that are co-resident with ov002 and never with ov007, so all three are exactly
the residency false positive the scout described. A residency model recovers
them; nothing else does.

WHY THIS IS SO MUCH MILDER THAN ov006's 985. Not because ov004/ov007 are
special, but because the port resolves very few cross pointers into that slot
today: 215 across all 61 mounted overlays, and almost everything aimed into
ov002's window is already contested by ov003 or has no provider at all. The
scout's ratio does not generalise. If the residency fix is being costed on
"how much is broken today", ov004 costs nothing and ov007 costs three words.
If it is being costed on "how much would a future mount unlock", the +690
newly-contested words for ov007 are the number to look at, and 560 of them are
ov002's own.

Per-source-overlay breakdown of the +690, worst first, in full. The first

That sums to 690. The +173 for ov004 splits ov002 116, ov047 16, ov043 12,

THE OTHER DIRECTION, the wants a mount of these two would ITSELF emit, is
cheaper still:

  ov007 has four cross wants into ov002, at 0x02110210 and 0x02110101 (three
  times). Both addresses are ABOVE ov007's own footprint end of 0x02104c40
  (and above the yaml's 0x02104720 too, so this holds on either route), so an
  ov007 mount does not contest them, and neither has a provider today anyway
  (ov002 is a per-symbol mount and does not cover those addresses). Cost: zero

  ov004 has seventeen cross wants into ov001, at 0x020ab3f0, 0x020ab41c,

NOTHING WAS HACKED AROUND. No change to ovdata.py, no hand-zeroed pointers, and

figures are identical before and after it. Any future ov004/ov007 slice should
be held to the same bar until the residency question is settled in its own
