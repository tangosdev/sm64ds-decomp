§1

What a line in this document is worth

The three tiers are not degrees of confidence in the same kind of claim. They are different kinds of claim, and collapsing them into a single score would be the one mistake this page exists to avoid.

TierCountWhat makes it trueCan it be wrong?
Proven413 edgesThe class's type_info record holds a pointer to its base's record. The compiler wrote it; this is read, not inferred.Only if the pointer was misread. 0 of 413 are unresolved.
Proven root24 classesA __class_type_info record — the ABI's own encoding for “no base”.No. The record kind is the statement.
Inferred0 classesNo type_info exists, so the base comes from vptr stores in the constructor/destructor chain.Yes. A shim or an inlined base constructor can mislead it.
Contradicted0 classesThe repo's header names a real ancestor, but not the immediate base. The ROM names the immediate one.The ROM is right by construction; the header is the error.
Unplaced0 classesKnown to the repo, no type_info, and no vptr chain placed it.Nothing is claimed, so nothing can be wrong.
The ROM stores 429 type_info records and 413 base pointers, and every one of those pointers resolves — 293 of them across an overlay boundary. Where this page is silent it is because the ROM is silent, not because the reading was hard.
§2

The spine

Of the 429 classes, 338 hang off a single root. Strip out everything with fewer than two children and the framework EAD actually built is four levels deep and fits on a screen.

fBase_c is the framework root — the same name, in the same position, as in EAD's GameCube codebases. Everything the game draws, updates or scenes through descends from it, and the two great families below dActor_c account for 156 of its descendants.

§4

Where a class has two parents

Exactly 6 classes use multiple inheritance, and the ROM records the byte offset of each base subobject. The base at +0x0 is the primary — and it is not always the first one listed, which is a trap that has already cost this project one wrong reading.

§5

Where the repo's headers are wrong

Nowhere. Every class the repo both names and holds a belief about names the immediate base the ROM records. Not one header names a class absent from the ROM's ancestor chain, and — the weaker failure this section was built to catch — not one names a genuine ancestor further up the chain than the real parent.

The chain-flattening this section reports comes from modelling a class's grandparent as its parent, which happens when the intermediate has no header and the evidence for the edge is a destructor vptr store that skips it. It is therefore retired by writing the intermediate down, not by correcting the children.

Empty because the finding was acted on, not because the test was relaxed: the same comparison still runs against all 429 records. 360 of them are parented by a hand-written struct D : B in a de-bannered header rather than by a base pointer the ROM supplied, and those are the only rows that can disagree with the ROM. None does.

§7

What this document cannot tell you

The ROM's RTTI carries class names and base pointers. That is all it carries. Specifically:

Not availableWhy
Method namesNo symbol table survives in a retail ROM. Zero _Z-prefixed strings exist anywhere in the image.
Parameter typesThe type_info kinds that encode a signature (__function_type_info, __pointer_type_info) were never linked in — this program never does typeid on a function type.
Field names or layoutsRTTI records a base's offset, never its members. Sizes come from the operator new literal at each call site instead.
Original filenamesExactly one __FILE__ string survives ROM-wide — isdoverlay.c, Nintendo's debugger SDK. Game code was built with asserts stripped.
Non-polymorphic classesA class with no virtual function gets no vtable and no record, so it cannot appear on this page at all. Every class the repo's headers define does have one, so the repo currently models no class this page cannot see.
