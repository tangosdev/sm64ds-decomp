# object, so the ROM build still covers them - just not from a separate file.
# Lines starting with '#' are comments.

# --- main: the 0x0206d9dc / 0x0206da28 secondary-entry-point cluster CAME OFF THIS LIST ---
# func_0206ce90, func_0206cee0 and func_0206d868 arm_call 0x0206d9dc and 0x0206da28,
# secondary entry points 0x10 bytes inside func_0206d9cc and func_0206da18. With no
# symbol there, dsd named them with local labels (.L_0206d9dc), which no other object can
# import, so the whole run func_0206ce90..func_0206da18 used to stay in the gap.
# config/arm9/symbols.txt now gives both addresses named label rows, the same shape as
# the ITCM runtime's interior entries (_dadd_core, _dsub_core): _ZN3IRQ11SetFIQStateEb
# and _ZN3IRQ11SetIRQStateEb, the names symbols/verified.tsv records. A label is not a
# function, so neither moves the function count. With the hand-asm owners enrolled,
# tools/lcf_interior.py defines each name at its ROM address in the LCF, since mwccarm
# cannot export a second symbol from one asm block. The twelve functions are enrolled
# `complete`.

# --- rejected by mwldarm despite passing eligibility ---

# 0x020ad524/0x020ad560 -- addresses past arm9's .bss that only the ov000/ov001

# --- linked cleanly but produced the wrong bytes (dsd check modules) ---
# Eligibility proves an object is the right shape to drop in, never that it is
# the right content. Mostly C++ destructors differing by a single byte, where a
# deleting/complete variant resolves differently in a real relink than it does
# when linkcheck verifies the match in isolation.
#
# _ZN13daObjCloset_cD1Ev / D0Ev CAME OFF THIS LIST. They were here because the
# hand-written source wrote ((dActor_c *)c)->~dActor_c(), for which the compiler
# emits the D1 complete-object destructor where the ROM calls the D2 base-object
# one. include/daObjCloset_c.h now derives the class properly and both files are
# an empty daObjCloset_c::~daObjCloset_c(); the compiler picks D2 itself and
# the ROM build carries both.
#
# CleanCommonModelDataArr and func_020313d8 CAME OFF THIS LIST. Both called the
# wrong function with the right shape, which a byte compare that wildcards relocated
# words cannot see (tools/match.py's default --strict-relocs reports it).
# CleanCommonModelDataArr called _ZdlPv (0x0203cbf0) where the ROM calls the veneer
# func_0203cbc0 that tail-calls it; func_020313d8 called _ZN7Message7AddCharEc
# (0x0201b5a8) where the ROM calls func_02031b84. Both now name the ROM's callee
# and link byte-identical.
#
# Nothing is listed here now. Cast-and-call and a same-shaped wrong callee are the
# two causes to look for if anything is added.
